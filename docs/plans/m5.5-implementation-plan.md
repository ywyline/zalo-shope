## 1. 目标与非目标

### 1.1 目标

- 在现有 `PaymentProvider` 端口内实现 ZaloPay through Zalo Checkout 适配器；创建支付只生成
  服务端签名的短期 Checkout launch，不把供应商 DTO 泄漏到领域层。
- 为两个商城保留独立的 App ID、merchant reference、environment、secret reference 和
  callback/origin 配置；默认 `disabled`，未配置合法 secret reference 时不能启动真实 provider。
- 实现 HTTPS/allowlist/超时/响应大小/分类错误的受控 HTTP 客户端；保留原始字节用于回调
  HmacSHA256 `mac` 与 `overallMac` 校验，并使用恒定时间比较。
- 新增原始 body 的 Zalo Checkout webhook 接缝：先定位商城渠道，再验签、核对 App、method、
  `extradata`、provider order、整数 VND 金额和订单身份，随后通过 callback/inbox 去重并复用
  `applyPaymentProviderFact`。
- 接入主动 `getOrderStatus` 查单路径，与回调共享供应商事实转换；支持超时、限流、未知状态和
  可重试错误的稳定分类，不把 Mini App SDK 的返回值当成支付成功。
- 以契约/单元/API/集成测试证明安全边界；没有真实商户、HTTPS callback 或 Zalo Testing 真机
  证据时，报告只记为“适配器完成，外部集成 `BLOCKED/NOT_RUN`”。

### 1.2 非目标

- 不实现 ZaloPay 商户开户、真实密钥申请、生产部署、DNS/证书、回调公网暴露或外部发布。
- 不在本阶段实现退款、对账、GHN、支付恢复 UI 的完整验收；退款端口保留显式未支持/配置错误，
  不伪造成功响应。
- 不新增第二个支付供应商，不复制两套商城代码，不改变订单/库存/支付状态机和 M5.2 schema
  不变量；若供应商契约差异要求改变这些边界，先暂停并更新总计划与需求变更记录。

## 3. 数据模型、迁移与兼容

- 优先复用 M5.2 已有 `store_payment_channels`、`payment_attempts`、`provider_callbacks`、
  `inbox_messages` 和 append-only transitions；业务表不存 Private Key、Key 1/Key 2 或完整
  回调载荷。
- `private_key_secret_ref` 仅作为部署密钥管理系统的引用，由进程内 `SecretReferenceResolver`
  解析为短生命周期内存值；解析器不得写日志、API、缓存或数据库，轮换使用新 key version 后再
  受审切换渠道版本。
- 若 callback 去重需要缺失的复合唯一约束，新增仅向前、可审查的迁移，并同时补充 down.sql 的
  `55000` 业务事实门禁；没有必要时不新增字段和迁移。
- fresh、M2→current、重复 deploy 必须保持兼容；旧 COD 订单和 M5.4 test provider 不受影响。
  回滚只允许无真实支付事实的 local/test scratch，生产只允许向前修复；禁用渠道不停止已有事实
  的回调/查单处理。

## 4. 安全与网络边界

- 供应商 URL 使用显式 origin allowlist；只允许 `https`（测试契约可注入 loopback adapter，
  不得由 production 配置放宽），禁止任意 redirect 和用户可控 URL。
- 连接、首字节和总响应超时均有限制；限制 `Content-Length` 与实际 UTF-8 字节数，拒绝超大、非
  JSON、重复 JSON key（如解析器可检测）或错误 content type；上游 4xx/5xx/429/网络错误映射
  到 `ProviderIntegrationError` 的稳定类别。
- 回调读取原始 bytes 后再解析 JSON；`mac` 使用官方原始字段顺序，`overallMac` 使用已冻结的
  canonical field set；比较使用 `timingSafeEqual`，长度不一致直接拒绝。IP 只作为附加 allowlist，
  不能替代 MAC。
- callback 先按 App ID、环境、商城唯一渠道定位，失败时不返回候选商城/订单；验签后核对
  `orderId/providerOrderId`、`merchantTransId`、`amount`、`currency`、method、`extradata` 中的
  store/order/attempt/nonce 身份和回调时间窗口。未知 result code 进入 `REVIEW_REQUIRED`，不得成功。
- 通过 `provider_callbacks` 的 `(channel, environment, externalEventId/eventDigest)` 与
  `inbox_messages` 唯一键抗重放/重复投递；处理状态和错误只记录稳定分类。成功事实在事务中调用
  `applyPaymentProviderFact`，不能由 controller 直接更新订单或库存。
- 日志只记录 correlation ID、商城、渠道脱敏引用、digest 和错误类别；不记录 raw body、MAC、
  Authorization、secret 或完整手机号/地址。

## 5. 事实流与运行策略

1. worker 从支付尝试事实生成 create launch，适配器只签名返回 payload；客户端在 Zalo Mini App
   主动调用官方 Checkout SDK，SDK 返回值仅触发绑定/查单提示。
2. 客户端提交 provider order ID 与短期 launch token 后，服务端验证 token/hash、商城和尝试，
   仅保存合法 provider order 绑定；绑定接口不能确认成功。
3. webhook 或查单响应经过同一 `parseCallback/queryPayment` 规范化为 `PaymentProviderFact`，
   再以 `WEBHOOK`/`QUERY` 来源调用 `applyPaymentProviderFact`。锁顺序、库存一次性消费、迟到成功
   复核沿用 M5.4。
4. 无合法回调达到约定窗口时由 worker 受控查单；429/5xx/timeout 进入可重试 outbox，未知/金额
   不符/签名错误进入拒绝或人工复核，不能无限重试。
5. provider、渠道或 secret resolver 未满足配置时启动失败或保持 disabled；绝不回退到 test provider。

## 6. 外部依赖与阻塞项

- 两个商城各自的 Zalo Mini App/Parent App、Checkout 资格、sandbox merchant/App ID、Private Key
  secret reference、回调域名、证书和允许来源列表。
- Zalo 官方文档版本差异审查（当前冻结 2026-06-15）、ZMP SDK 2.51.8 的真机测试版本、测试成员和
  sandbox 支付/取消/失败/未决/丢回调/重复回调/查单材料。
- 在上述输入到位前，只运行离线契约与注入 HTTP 测试；不得访问真实 endpoint，不得生成看似真实的
  merchant response，不得把本地 HTTP fixture 写成生产配置。

## 7. 测试与验收矩阵

- 单元/契约：create-order MAC、callback `mac/overallMac`、原始字节/Unicode、恒定时间比较、
  extradata/amount/method/store/order/attempt 校验、状态映射、未知状态和错误分类。
- HTTP：origin/HTTPS allowlist、timeout、429/5xx/非 JSON/超大响应/redirect、重试上限、secret
  resolver 不泄漏；production 构造拒绝 test adapter 和明文 key。
- API/集成：原始 webhook body、content type/大小/rate limit、渠道商城定位、provider callback/inbox
  并发去重、伪签名/重放/跨商城/金额篡改、回调与查单竞态、成功只消费一次库存、迟到成功复核。
- 回归：M5.4 test provider、双商城 RLS、M2→current 迁移、`verify`、lint/typecheck/build、
  integration、Chromium/WebKit E2E、依赖审计和敏感信息扫描。
- 外部验收：Zalo sandbox 回调/查单与 Zalo Testing Android/iPhone 真机；在无真实材料时逐项记为
  `BLOCKED`/`NOT_RUN`，不得以 Playwright 或确定性 provider 替代。

## 8. 完成与停止条件

- 只有自动化门禁全部通过、两个商城隔离和回调幂等有证据，且真实 sandbox/真机材料齐全，才能将
  M5.5 标为完成；否则报告仅标记“适配器/契约已完成，外部集成未验收”。
- 若供应商实际契约要求改变金额、库存、状态机、商城隔离、权限或密钥保存规则，立即停止编码，
  更新本计划、总计划及相应需求/架构/数据文档并重新获得批准。
