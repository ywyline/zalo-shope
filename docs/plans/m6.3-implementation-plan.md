## 2. M6.3-A 目标与非目标

### 2.1 目标

- 在 checkout 创建订单的同一商城事务内，按“商品覆盖 → 最近主类目祖先 → 商城默认”解析当前活动、
  不可变售后政策版本，并为每个订单行写入规范 payload、SHA-256 和精确政策版本快照。
- enforcement OFF 时保持旧 checkout 兼容且不伪造历史快照；enforcement ON 时任何默认政策、活动
  assignment、解析或快照写入缺失都必须使下单事务失败。
- 实现当前商城 settings/readiness 读取和受审 enforcement 命令；启用必须重新执行服务端预检，校验
  独立权限、近期 MFA、确认词、expected version、AccessReason（平台跨商城时强制）、商城幂等、审计
  和商城/Header/查询一致性。
- 让订单物流查询、建单、取消、主动查单、callback hint、worker 和供应商事实应用显式识别
  `ShipmentPurpose`；只有 `ORDER_OUTBOUND` 可以推进原订单 `SHIP/DELIVER`。
- 对商城隔离、权限、并发、幂等、fail-closed 和非订单物流不推进订单提供自动化证据。

### 2.2 非目标

- 不创建、发布或启用任何生产售后政策；local/test fixture 不能被表述为越南合规结论。
- 不创建 `AFTER_SALE_RETURN` 或 `EXCHANGE_OUTBOUND` 运单；只先保证既有路径能安全分流。
- 不开放售后申请、审核、返件、ONLINE 退款或 COD 线下退款 API；其中申请、审核与可信返件事实属于
  M6.3-B，完整返件验收写路径及库存恢复属于 M6.4。
- 不实现证据对象存储/扫描、库存恢复、换货履约、会员中心、分享或 UI；分别属于后续切片/里程碑。
- 不改变订单、支付、退款、物流或售后状态机，不放宽 M5 真实供应商与 P0 上线硬门禁。

### 3.1 M6.3-B1 只读运行时

B1 另行只开放：

- `GET /v1/after-sales`
- `GET /v1/after-sales/{afterSaleId}`
- `GET /v1/admin/after-sales`
- `GET /v1/admin/after-sales/{afterSaleId}`

会员列表固定 `created_at DESC, id DESC`，管理员固定 `updated_at DESC, id DESC`。两者都在同一个
`REPEATABLE READ` 商城事务中先用原生 SQL 读取 `limit + 1` 个 page key，再只对白名单 ID 使用严格
Prisma `select` 加载响应所需列并按 key 重排。page key 由 PostgreSQL 返回六位微秒 UTC 文本，下一页
直接使用 `(timestamp,id)` tuple seek，不把排序时间降级为 JavaScript 毫秒精度。

`c1_` 游标由 `AFTER_SALE_CURSOR_HMAC_KEYS` 的 1–3 把唯一 base64url HMAC-SHA-256 key ring 保护；
第一把签发、全部验证，并绑定版本、商城、主体、资源、规范筛选、微秒排序键、ID 与过期时间。会员/
管理员读限流分别为每 60 秒 60/120 次，绑定商城+主体且 Redis 故障失败关闭；成功响应统一
`Cache-Control: private, no-store`。B1 不注册任何写 handler。

### 3.2 M6.3-B2a 政策控制面

B2a 只开放：

- `GET /v1/admin/after-sale-policies`
- `GET /v1/admin/after-sale-policies/{policyCode}`
- `PUT /v1/admin/after-sale-policies/{policyCode}`
- `GET /v1/admin/after-sale-policies/{policyCode}/versions`
- `GET /v1/admin/after-sale-policies/{policyCode}/versions/{versionNumber}`
- `POST /v1/admin/after-sale-policies/{policyCode}/publish`
- `POST /v1/admin/after-sale-policies/{policyCode}/disable`

应用文件为 `apps/api/src/after-sales-policy/after-sales-policy-management.{controller,service}.ts`，数据原语为
`packages/database/src/after-sale-policy-management-primitives.ts`。草稿使用规范三语 payload/hash 和 draft product replace-set，发布使用商城锁、
head 行锁与不可变版本/本地化/assignment/活动投影同事务。停用不删除历史事实；enforcement ON 时发布或停用必须保持权威
readiness，否则回滚。读写统一使用严格契约、correlation/no-store、管理员 120/30 限流和商城范围授权，稳定冲突以
`details.reason_code` 投影。

B2a 不开放凭证上传/扫描/claim/保护读取/删除 worker，不开放售后申请、审核、返件、退款或结算。B2b/B3-B7 路由仍
contract-only 或失败关闭。

## 4. 数据、迁移、兼容与回滚

- 优先复用 M6.2 已有模型、RLS、复合外键、不可变保护与 deferred enforcement guard；不改写历史
  订单，也不回填当前政策冒充历史快照。
- 四段 M6.3-A 前向迁移依次对齐最近主类目祖先的快照数据库 guard、为既有商城补稳定 OFF settings
  行、提供当前商城只读锁函数，并为后续新增商城自动 provision 同样的稳定 OFF 行。生产不创建
  默认政策，也不自动启用 enforcement。
- 若运行时实现暴露现有约束缺口，只添加可审查的向前迁移和 local/test `down.sql`；有业务事实的
  环境继续只允许向前修复。任何迁移必须加入 M2-to-current、重复 deploy、down/重新前滚和
  SQLSTATE `55000` 门禁演练。
- 应用回滚可关闭 settings 写入口并把未启用商城保持 OFF；已启用商城若回滚到没有 snapshot writer
  的应用版本，必须先通过受审命令关闭 enforcement，禁止直接改表或让 checkout 静默降级。
- shipping purpose 默认继续为 `ORDER_OUTBOUND`，兼容旧数据；所有新旧订单物流行为不变。非订单
  purpose 只停止推进原订单，不删除或改写运单/轨迹事实。
- B1 复用 M6.2/B0 售后表和 FORCE RLS，不新增业务列。前向迁移
  `20260728110000_m63_b1_after_sale_admin_read_index` 只增加管理员无 status 列表的
  `(store_id, updated_at DESC, id DESC)` 索引；应用回滚可保留该索引，受审 `down.sql` 只删除该精确
  索引。Prisma 只补记数据库既有 `after_sale_refunds(store_id, settlement_id)` 唯一约束，消除 schema
  drift 而不重复迁移。
- B1 应用回滚可取消四个 controller 注册，不删除任何售后事实。游标密钥回滚必须在最长 TTL 内保留
  所有仍可能验证有效游标的旧密钥；Redis 计数仅为短 TTL 限流状态，不是业务事实。
- B2a 前向迁移 `20260729100000_m63_b2a_policy_control_plane` 只增加 policy heads 和 versions 的两个 keyset 索引，
  不改写 RLS、政策、settings、活动投影、快照或售后事实。应用回滚可注销七个 handler 并保留索引；local/test `down.sql` 只删除精确索引。
- B2a 不扩展 RLS 为 ACTIVE-only 读，因为这会使 B1 会员无法读取售后绑定的已停用/被替换历史版本，又不能隐藏 ACTIVE head 内的草稿列。
  政策管理用应用层独立 RBAC+显式 store scope 叠加既有 FORCE RLS。
- 旧表约束允许下划线 code 与非严格 payload，新 API 仅接受连字符 code 和严格规范 payload。仓库已提供只读分批兼容性预检，并在本地测试库
  通过（`policies=0, versions=0`）；注册 staging/production 路由前必须针对精确目标库再执行并留证，不兼容则停止 rollout 并前向修复。

## 5. 风险、依赖与停止条件

- 越南业务/合规未批准美妆卫生、开封例外、期限、证据、运费和服装换码政策，所有商城
  enforcement 默认保持 OFF；没有批准时不得创建或发布生产政策。
- 真实两商城 ZaloPay/GHN、HTTPS callback、商户结算、GHN COD 回款和 Zalo 宿主仍为 M5/P0 上线
  硬门禁；本切片不能替代这些证据。
- readiness 必须基于服务端权威活动投影和可执行 checkout 预检生成 hash，不能信任客户端 ready、
  缓存旧结果或只检查“有一条默认 policy”。
- policy 解析冲突、缺失或 hash 不一致一律失败关闭；若无法在既有 M6.2 数据模型上证明解析唯一性，
  停止启用路径并先做数据/迁移设计复审。
- GHN callback 无签名，只能作为查单提示；purpose 不能来自 callback body，必须从商城隔离的本地
  shipment 事实读取。
- B1 读取的主要风险是跨商城/会员泄漏、宽投影暴露列级敏感字段、微秒排序精度丢失和密钥轮换中断。
  防护固定为显式 store/owner/RBAC + FORCE RLS、严格 `select`/response allowlist、数据库原生六位
  微秒 tuple seek，以及“新密钥置首、旧密钥保留至最长 TTL 后移除”的 1–3 把 key ring 流程。
- Redis 不可用时不得静默绕过 B1 限流；四个读取应失败关闭。B1 响应可见 settlement/evidence 的安全
  摘要不代表证据对象、退款协调或 COD 到账能力可用。
- B2a 的主要风险是草稿提前污染 checkout、并发目标覆盖、破坏 enforcement readiness、改写历史、幂等跨 policy 复用、游标跨资源重放和过度审计泄漏。
  防护固定为商城 advisory lock + head 行锁、草稿/活动投影分离、不可变版本、同事务 readiness、请求 hash 绑定 policy code、资源级游标 scope 和严格审计投影。
- B2a/settings 读写的 Redis 限流不可用时同样失败关闭。目标库未执行兼容性预检，或预检发现旧 code/payload 不兼容时，禁止注册路由或 rollout。
  本地空政策预检不能替代任何 staging/production 目标库证据。
