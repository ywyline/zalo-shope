## 1. 目标与非目标

### 目标

- 只把不可变、精确匹配的 `COD_REMITTANCE/MATCHED` 财务对账行作为 COD 原订单确认收款事实，解除
  B3 对已收款 COD 订单售后申请的失败关闭，同时拒绝缺失、差异、重复或跨商城事实。
- 让共用 `POST /v1/admin/after-sales/{afterSaleId}/refund` 从服务端订单事实选择 ONLINE 或 COD
  分支；COD 只要求目标商城直接 `store.after-sales.cod-refunds.request`、近期 MFA 和只读权限，不接受
  客户端支付方式、金额、手续费、供应商引用、库存动作或终态。
- COD 申请只按售后 `approved_total_vnd` 创建 `PENDING` settlement 并返回不可猜
  `public_settlement_number`；从 `APPROVED` 只追加 `QUEUE_REFUND`，不伪造处理中或成功。
- 提供独立受审财务回执记录入口。该入口接收规范化的外部转账观察值，但只能绑定已存在的目标商城、
  售后和 settlement；服务端精确核对金额/VND/版本，原始引用只保存 keyed digest、掩码和加密证据。
- 由另一名具备目标商城直接 `store.after-sales.cod-refunds.confirm` 且近期 MFA 的管理员确认。确认请求
  仍不接受金额、引用或终态；只有不可变回执完全匹配时，单事务写入 settlement 成功、
  `REFUND_REQUESTED/REFUND_SUCCEEDED`、确认事实和审计。
- 保持商城隔离、固定退款锁序、幂等重放、并发单胜者、敏感数据最小投影及数据库最终约束。

### 非目标

- 不执行真实银行转账、退款、ZaloPay/VNPay/GHN 调用，不接收生产凭据，不部署、不推送、不发布。
- 不把 local/test 规范化回执冒充真实供应商、银行、sandbox、staging 或 production 验收。
- 不实现返件验收、库存恢复、换货履约或完整售后 UI；这些仍属于 `P0-M6-008/P0-M6-011`。
- 不让 COD settlement 进入 M5 ONLINE `refunds`，不改变原订单、库存、物流或 M5 provider 事实。
- 不允许人工接受金额不符、缺失证据、重复引用或无法证明的历史 COD 收款。

## 2. 数据与迁移

- 新增不可变 `after_sale_cod_refund_receipts`，按商城绑定 settlement、售后、订单和服务端金额，保存
  keyed transfer digest、掩码、加密证据、发生时间、记录 actor、幂等/request hash 与 correlation。
- 新增不可变 `after_sale_cod_refund_confirmations`，保存 settlement/case 公共身份对应的确认 actor、
  expected versions、幂等/request hash 和提交时结果版本；每个 settlement 最多一项确认事实。
- 两表使用复合 FK、唯一索引、FORCE RLS、最小 runtime 列授权、不可变 trigger 和 deferred 原子性
  guard。回执记录者固定为 settlement requester；确认者必须不同。
- 放宽 COD settlement 初始形状为 `PENDING` 且无转账完成事实；只有确认事务可从
  `PENDING/REVIEW_REQUIRED` 写入与不可变回执逐字段一致的 digest/ciphertext、确认 actor/timestamp 和
  `SUCCEEDED`。ONLINE 生命周期保持不变。
- 前向迁移在发现任何既有 `COD_OFFLINE` settlement 时以 SQLSTATE `55000` 停止，因为仓库没有可安全
  回填的历史可信回执。`down.sql` 仅允许无 B7 回执、确认、settlement/audit/transition 事实的 local/test；
  产生事实后只允许向前修复。

## 3. 服务、API 与权限

- `packages/database/src/after-sale-command-primitives.ts`：COD admission 锁定并验证精确 M5 COD 回款
  对账事实，ONLINE 路径保持原有唯一成功 payment 证明。
- 新增 B7 database primitive：退款方式解析、COD request、receipt record、confirm；所有写使用
  `Serializable`、最多三次 serialization retry，显式 version/idempotency 冲突不重试。
- 固定锁序为商城/命令幂等 advisory lock -> `m62-refund:{store}:{order}` -> order -> 相关财务收款事实
  -> after-sale -> settlement/receipt -> 最终 admin/session/MFA/direct-RBAC 重验 -> 首笔业务写入。
- API 服务先用目标商城 `store.after-sales.read` 取得受 RLS 保护的支付分支，再动态要求 ONLINE 的既有
  四权限或 COD request 权限；database primitive 在全部等待锁后再次以数据库权威事实重验。
- 新增回执记录路由和已冻结的 confirm 路由，均使用 strict DTO、商城/Header/query 一致、ADMIN WRITE
  限流、no-store/correlation、稳定 4xx/409/422/503 映射。确认继续通过 case ID + settlement 公开号定位。
- 售后投影只新增 `receipt_recorded` 安全布尔值；不返回 transfer digest、加密证据、原始引用、内部回执
  或确认主键。

## 4. 兼容、回滚与外部门禁

- ONLINE B6 API、M5 refund/outbox/worker 和现有响应字段保持兼容；新响应字段为严格契约中的新增只读
  布尔值。
- `AFTER_SALE_REFUND_COMMANDS_ENABLED=false` 继续是默认值，production 配置和服务层继续拒绝启用；
  B7 不增加隐式生产角色授权。
- 应用回滚只关闭新入口并保留已提交回执、settlement、确认、transition 和 audit；数据库 down 只供
  无真实业务数据的 local/test 演练。
- 真实 COD 回款材料、真实退款转账/银行回执、两商城 sandbox/staging、部署和 production rollout
  继续 `NOT_AUTHORIZED/NOT_RUN`，不能由本切片完成状态替代。

## 5. 风险与停止条件

- M5 回款行不是 `MATCHED`、未精确绑定 ORDER_OUTBOUND shipment/order/金额、存在跨商城或重复事实时，
  COD 售后申请和结算必须失败关闭。
- 回执金额、商城、售后、订单、settlement、公开号、版本、requester 或引用唯一性任一不一致时不得确认。
- 确认权限撤销、session 失效、MFA 超时、同人确认、并发确认或同键异参必须在数据库最终重验后失败。
- 迁移预检发现既有 COD settlement、RLS/列授权/原子 guard 失败或敏感明文进入日志/audit/响应时，停止
  B7 路径，不以兼容性放宽或假回执继续。
