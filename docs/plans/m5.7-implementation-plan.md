> 状态：仓库自动化范围已收口；真实 ZaloPay/GHN 与 Zalo 宿主验收仍为 BLOCKED/NOT_RUN

> 日期：2026-07-26

## 1. 目标与非目标

### 1.1 目标

- 允许具备当前商城退款权限、近期 MFA 且完成二次确认的管理员，针对已成功线上支付创建整数
  VND 的全额或部分退款。服务端锁定支付与现有退款事实，重算可退款余额，并通过稳定内部退款号
  和 outbox 幂等调用 Zalo Checkout。
- 实现 Zalo Checkout `createRefund` 与 `getRefundStatus` 的严格 HTTP 适配，固定官方 HTTPS
  origin/path、HmacSHA256、超时、响应大小和 JSON 类型；未知、缺失或不一致响应失败关闭。
- 退款创建和主动查询都在数据库事务外调用供应商，结果通过统一退款事实命令落库。重复、并发、
  乱序和 worker 重试不得超额退款、覆盖成功终态或产生第二笔供应商退款。
- 退款成功只更新退款流水和订单支付聚合投影 `PARTIALLY_REFUNDED/FULLY_REFUNDED`，不恢复库存、
  不改变订单履约状态，也不伪装成 M6 售后流程。
- 实现商城隔离的支付、退款和失败集成任务列表、受审主动查询与 dead-letter 重试；管理端和买家端
  提供越南语、中文、英文的支付恢复、退款只读状态和异常处理反馈。
- 以现有支付/退款转换、outbox、物流 operation 和轨迹事实提供按越南业务日期筛选的对账基础。
  供应商权威查询与本地事实不一致时进入人工复核/失败任务，不自动改写成功财务事实。

### 1.2 非目标

- 不实现退货退款、换货、售后凭证、退款审批流、自动库存恢复或拒收自动退款；这些属于 M6。
- 不实现 Zalo Checkout 官方未提供的结算文件、手续费或批量日结 API，也不虚构 GHN COD 回款
  数据。外部结算文件和 GHN 回款材料未提供时，只交付逐笔查询与本地差异基础。
- 不新增支付、退款、物流或对账业务表；复用 M5.2 已冻结并迁移的 14 张表及只追加事实。
- 不调用真实商户或物流账户，不创建假退款成功、假对账差异或假供应商流水。
- 不在缺少两个商城真实凭据、HTTPS 回调和 Zalo Testing 真机证据时标记 M5.7 或整个 M5 完成，
  也不进入 M6。

## 2. 官方契约与外部阻塞

- 2026-07-26 重新核对官方文档：创建退款为
  `POST https://payment-mini.zalo.me/api/refund/create`，MAC 数据固定为
  `appId={appId}&transId={transId}&amount={amount}&description={description}&privateKey={privateKey}`；
  查询退款为 `GET https://payment-mini.zalo.me/api/refund`，MAC 数据固定为
  `appId={appId}&refundId={refundId}&privateKey={privateKey}`。
- 创建响应必须包含非空 `refundId` 和整数 `returnCode`。`1` 表示成功、`>1` 表示处理中、`<1`
  表示失败；查询文档只定义 `1` 为成功、其他为失败。未知字段不扩展成功语义。
- 官方文档没有退款 callback 或结算文件 API。处理中退款只能通过受控主动查询收敛；仓库不能把
  单笔查询结果描述为银行/商户日结对账完成。
- 两商城真实 Checkout/ZaloPay sandbox 凭据、可退款交易、商户退款能力与限额、财务日界线、
  HTTPS 环境和 Zalo Testing 真机尚未提供；真实退款与阶段验收保持 `BLOCKED/NOT_RUN`。

## 3. 数据、接口与模块

### 3.1 数据与状态

- 复用 `refunds`、`refund_transitions`、`payment_attempts`、`orders` 和 `outbox_messages`。退款
  创建锁定成功支付尝试，校验 expected payment version，并把 `REQUESTED`、初始 transition、
  审计和 `refund.create.requested.v1` outbox 在同一事务提交。
- 可退款余额统计同支付的 `REQUESTED/PROCESSING/SUCCEEDED/REVIEW_REQUIRED` 金额；未知供应商
  结果在受审解决前继续占用容量。应用计算与数据库 `refunds_capacity_guard` 双重保护。幂等键
  只保存商城/支付范围 hash，不保存原文。
- provider 创建成功将 `REQUESTED -> PROCESSING/SUCCEEDED`；查询只允许已绑定 provider refund
  ID。未知、事实不一致、成功后的倒退或无法穷举状态进入人工复核/失败任务，不覆盖成功事实。
- 退款成功按同一成功支付的累计成功退款金额投影订单支付状态；金额小于支付金额为
  `PARTIALLY_REFUNDED`，相等为 `FULLY_REFUNDED`。订单、库存、运单状态保持不变。

### 3.2 API 与 worker

- 实现冻结的管理端接口：支付列表与主动查单、创建/查询退款、退款列表、集成任务列表和受审
  dead-letter 重试。全部使用认证商城上下文、RLS、RBAC、expected version、原因、幂等键和审计。
- 退款创建要求 `store.refunds.create`、近期 MFA 和确认词；退款读取要求 `store.refunds.read`；
  查询要求 `store.payments.reconcile + store.refunds.read`；失败任务重试要求
  `store.integration-jobs.retry` 加对应领域写权限。
- 新增 `refund.create.requested.v1` 与 `refund.query.requested.v1` handler。外部调用不持有事务；
  provider 结果通过固定锁顺序和只追加 transition 落库。处理中创建结果调度有限延迟查询。
- 买家订单详情只读取本人订单关联退款的公开号、金额、标准状态和时间，不暴露管理员原因、
  provider ID、secret reference、上游响应或其他商城事实。

### 3.3 工作台与对账基础

- 管理端订单工作台增加支付尝试、可退款余额、退款创建/查询和退款时间线，并增加失败任务视图。
  危险操作有明确确认、加载、冲突、失败与重试反馈。
- 支付/退款列表支持状态、订单和业务日期筛选；物流工作台继续显示 COD 金额、费用分解、轨迹和
  operation 失败。逐笔权威查询产生的差异通过 `REVIEW_REQUIRED` 或 dead-letter 稳定错误呈现。
- 不把本地汇总称为供应商结算完成。真实供应商结算文件、手续费、GHN COD 回款和差异处置规则
  作为 M5 外部验收项保留。

## 4. 迁移、兼容与回滚

- 本阶段不新增业务表或字段。最终审查发现 M5.2 容量 guard 未计入 `REVIEW_REQUIRED`，会在供应商
  结果不确定时过早释放容量；因此追加仅替换 guard 函数的前向迁移，并提供有人工复核事实时
  拒绝回滚的 `55000` 门禁。复合外键、RLS 和运行角色列级授权保持不变。
- API 只实现已冻结的向后兼容接口；新增客户端字段为可选读取能力，不改变 M4 COD 或现有 ONLINE
  支付响应。旧应用可忽略退款列表。
- 应用回滚时保留当前与上一版 refund outbox handler，已创建退款继续查询至终态；禁用渠道只
  阻止新退款，不允许丢弃已有退款命令。
- 测试产生的退款、outbox 和审计事实只存在于自动创建并销毁的专用测试数据库。

## 5. 风险与停止条件

- 金额：只使用安全整数 VND，服务端重算余额；测试并发部分退款、重复幂等、超额和支付版本冲突。
- 商城/RBAC：支付、退款、渠道、outbox 和审计均复合绑定可信 `store_id`；测试跨商城 UUID、
  普通管理员缺权、MFA 过期和商城 header/query 不一致。
- 状态：成功退款单调，迟到失败不能降级；未知响应不映射为成功。供应商退款 ID 碰撞失败关闭。
- 安全：固定 HTTPS origin/path，拒绝 redirect，限制超时/大小/content type；错误、日志和审计
  不包含 Private Key、MAC、完整 provider body、Authorization、手机号或地址。
- 如果真实契约要求客户端发起退款、信任无签名结果、放松退款上限、存储明文密钥或改变库存/
  售后状态机，停止实施并先更新需求、数据字典、OpenAPI 和安全设计。

## 6. 测试与验收

- 单元/契约：退款 MAC、严格 DTO、状态映射、响应 shape、整数金额、未知状态、超时、非 JSON、
  超大响应、redirect 和 secret 失败。
- PostgreSQL/API：退款幂等、并发容量、支付版本、部分/全额投影、成功单调、跨商城/RLS、RBAC、
  MFA、确认、原因、任务重试和敏感字段脱敏。
- worker：创建成功/处理中/失败、查询收敛、有限重试、dead-letter、重复 outbox 与 provider ID
  碰撞；网络调用不跨事务。
- E2E/UI：双商城、三语、Chromium/WebKit 的退款创建、只读状态、失败任务和支付恢复；Web 预览
  不替代 Zalo 宿主真机。
- 仓库门禁：定向测试、`corepack pnpm verify`、`corepack pnpm test:integration`、
  `corepack pnpm test:migration:m2-upgrade`、`corepack pnpm test:e2e`、生产依赖审计、Gitleaks、
  `git diff --check` 和最终敏感信息检查。
- 外部验收：两个商城分别完成 sandbox 全额/部分退款、处理中查询、失败重试、查单差异、HTTPS
  回调恢复、GHN COD/费用材料和 Zalo Testing 真机。材料未提供前逐项为 `BLOCKED/NOT_RUN`。

## 7. 完成边界

- 仓库自动化范围只有在代码、三语 UI、文档和全部适用本地门禁通过后才能收口。
- 真实支付、退款、物流和 Zalo 宿主证据未齐时，报告只能写“仓库自动化完成，外部集成未验收”，
  不得标记 M5.7、M5 或 P0 完成，也不得自动进入 M6。
