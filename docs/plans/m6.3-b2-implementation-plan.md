## 2. 目标与非目标

### 2.1 B2a 目标

- 实现 `list/detail/draft PUT/version list/version detail/publish/disable` 七个冻结操作。
- 政策读、草稿、发布和停用分别使用 `policy.read/manage/publish/disable` 权限；发布和停用要求近期
  MFA、确认词、业务 reason、商城范围幂等键和完整审计。
- 草稿始终与当前 ACTIVE 投影隔离。ACTIVE 政策可以保存下一版草稿，但草稿中的类目/商品变化在
  发布前不得改变 checkout 解析。
- 发布在商城级政策 advisory lock 下原子创建不可变版本、三语本地化、冻结 assignment、活动投影和
  policy head；同目标被另一 ACTIVE 政策占用时稳定返回 `409`。
- 停用只移除新订单解析投影，保留不可变历史、订单快照和售后引用；enforcement 已启用时不得破坏
  readiness，必要的 settings 同步必须与命令同事务完成。
- 列表使用签名 keyset 游标和 PostgreSQL 六位微秒排序键，所有读写显式绑定当前商城、管理员主体、
  严格输入、限流、correlation ID 和 `private, no-store`。

### 2.2 B2b 目标

- 证据对象使用独立于 catalog/content 的 bucket 或凭据边界，key 固定包含环境、商城、会员无关的随机
  对象 ID 和 staged 命名空间；客户端不能选择 key。
- 校验声明 MIME、长度、SHA-256 和 magic bytes，只允许 JPEG/PNG/WebP/MP4；图片最大 10 MiB、视频
  最大 50 MiB，每单最多 6 个。
- 确认后异步进入真实恶意文件扫描；只有精确 CLEAN 结果可成为 `READY_UNCLAIMED`。扫描不可用、
  超时或结果不确定均不能放行。
- 提供 owner-scoped 状态读取，使客户端在 B3 前能够可靠观察 `PENDING/READY/UNAVAILABLE`，但不
  暴露隔离、删除或扫描内部原因。
- 提供事务内 claim 原语：B3 创建售后时锁定同商城同会员未过期对象，并一次性绑定售后；同一对象
  不得被第二个售后复用。
- 只有未过期 `READY` 可签发短期 no-store URL。管理员另需 evidence.read 且每次成功访问写审计。
- 删除 worker 使用窄 SYSTEM scope，在每次对象操作前后重锁行并复核截止点和 legal hold；原件、
  衍生物和扫描临时对象幂等删除，失败有界退避并告警。

D1-D4 已完成上述目标中的专用 adapter、规范对象 key、local/test bucket/三身份 IAM、create-only
上传、实际 bytes 长度/checksum/magic 校验、owner 状态、真实 scanner、expire/delete worker 和
local/test provider 删除补偿。B3 transaction-scoped claim、授权正文读取/逐次审计、legal hold 管理、
外部告警及全部生产 storage/scanner/retention/rollout 条件仍未完成。

### 2.3 非目标

- 不实现会员/商家售后创建、取消、审核、legacy 决定、返件、退款、COD、验收、库存恢复或换货。
- 不创建或发布任何真实越南商城政策，不启用生产 enforcement，不把 local/test fixture 作为合规结论。
- 不提供 legal hold 管理入口；普通状态响应不返回对象 key、扫描结果、删除错误或签名 URL，日志也不得记录这些敏感字段。
- 不交付买家端/管理端 UI，不调用真实支付、物流、Zalo 或其他供应商，不部署或发布。

## 3. B2a 接口、数据与事务语义

### 3.1 接口

- `GET /v1/admin/after-sale-policies`
- `GET /v1/admin/after-sale-policies/{policyCode}`
- `PUT /v1/admin/after-sale-policies/{policyCode}`
- `GET /v1/admin/after-sale-policies/{policyCode}/versions`
- `GET /v1/admin/after-sale-policies/{policyCode}/versions/{versionNumber}`
- `POST /v1/admin/after-sale-policies/{policyCode}/publish`
- `POST /v1/admin/after-sale-policies/{policyCode}/disable`

所有接口要求 token、`X-Store-Code` 与 `store_id` 一致；平台跨商城时复用中央 `X-Access-Reason` 审计。
所有 query/path/body 使用 strict schema。读取固定 `policy.read`；草稿、发布、停用权限互不隐含。

### 3.2 草稿与规范 payload

- `expected_version=0` 仅允许创建不存在的 policy code；更新要求精确正版本。创建和更新均使用商城
  范围 24 小时幂等记录，同键异参冲突。
- payload 先由严格 schema 验证，再规范化：类型按冻结枚举顺序、UUID/reason code 字典序、三语按
  `vi/zh/en` 顺序；hash 为规范 JSON 的 SHA-256。
- 新 DRAFT head 可以保存草稿类目；已有 ACTIVE/DISABLED head 的 `category_id` 表示当前已发布版本，
  草稿 PUT 只改 `draft_payload/hash` 和 draft product replace-set，不提前改 head 或活动投影。
- 类目和商品必须属于当前商城；不存在或跨商城统一拒绝，历史 ACTIVE 事实不因草稿变更受影响。

### 3.3 发布

- P0 只支持立即生效：`effective_at` 与 `published_at` 使用同一数据库事务时间；不实现计划发布。
- 事务取得 `m62-policy:{store_id}` advisory lock 并锁定 policy head；校验 expected version 后从规范草稿
  创建下一不可变 version、三语本地化和 PRODUCT/CATEGORY/STORE_DEFAULT assignments。
- 目标键在服务层规范排序；商城级 lock 与数据库唯一索引共同保证并发发布不会最后写入覆盖。
- 事务更新 head 为 ACTIVE/current version，原子替换仅属于本 policy 的活动投影并写审计。DISABLED
  policy 只能通过发布新不可变版本重新变为 ACTIVE。
- 若 enforcement 已启用，发布后必须重新计算权威 readiness，并在同一事务同步 settings 的默认
  policy/version/hash/check actor；不能留下 checkout 全量失败的半同步状态。

### 3.4 停用

- 只允许 ACTIVE policy，按 expected version 和商城幂等键执行；历史 version/assignment/snapshot
  永不删除。
- 原子移除该 policy 的活动投影并把 head 设为 DISABLED。若商城已 enforcement 且停用会失去默认或
  造成任何解析不 ready，整个事务回滚并返回稳定 `409`。
- 可安全停用时重新同步 enforcement readiness，写精确 before/after、业务 reason、actor 和 correlation
  审计。

### 3.5 读取与游标

- policy heads 固定 `(updated_at DESC, id DESC)`；版本固定 `(published_at DESC, id DESC)`。
- 复用 B1 的 `c1_` 独立 HMAC key ring，但 resource 分别绑定
  `ADMIN_AFTER_SALE_POLICIES`/`ADMIN_AFTER_SALE_POLICY_VERSIONS`，并绑定管理员、商城、过滤和
  policy code；任何跨资源/跨政策重放返回统一 `400`。
- 在单个 `REPEATABLE READ` 事务内先取 `limit + 1` 六位微秒 page keys，再按白名单 ID 严格投影。

## 4. B2b 接口与内部能力

冻结的外部接口为：

- `POST /v1/after-sales/evidence-uploads`
- `POST /v1/after-sales/evidence-uploads/{evidenceId}/confirm`
- `GET /v1/after-sales/evidence-uploads/{evidenceId}`（B2 前向补充的 owner-scoped 状态）
- `GET /v1/after-sales/{afterSaleId}/evidence/{evidenceId}`
- `GET /v1/admin/after-sales/{afterSaleId}/evidence/{evidenceId}`

确认接口保持 `202/PENDING`，不得同步伪造扫描成功。API 事务只验证 owner/version/对象元数据并可靠
排队扫描身份；worker 重新读取对象、验证 magic/checksum 后调用真实 scanner，再在窄 SYSTEM 事务中
投影结果。scan、expire、retry-delete 和 delete-result 消息只携带商城/evidence ID/version，不信任消息
中的状态、对象 key 或截止点。
