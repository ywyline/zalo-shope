## 2. 目标与非目标

### 2.1 目标

- 注册 `POST /v1/after-sales/evidence-uploads`、
  `POST /v1/after-sales/evidence-uploads/{evidenceId}/confirm` 和 B2 前向补充的
  `GET /v1/after-sales/evidence-uploads/{evidenceId}`。
- 三个接口都绑定有效会员 token、当前 `X-Store-Code`、token `store_id`、owner、correlation ID 和
  Redis member read/write 限流；跨商城、跨会员和已知异商城 UUID 均不能探测事实。
- 初始化使用严格 MIME/大小/checksum/文件名 DTO、24 小时商城+会员幂等、D0 配额锁和规范 ORIGINAL
  key；随后由 D1 upload 身份签发 create-only 目标。响应返回完成上传所需的严格 header allowlist，
  不返回对象 key、bucket、凭据或内部截止点。
- 确认前通过 D1 read 身份执行 HEAD + `If-Match` GET，对实际 bytes 重新计算长度/checksum 并验证
  JPEG/PNG/WebP/MP4 magic；成功后 D0 在同一事务确认并排队 scan v1。D2 worker 仍从权威 ledger
  重新读取并复验同一对象，HTTP 校验不构成 `CLEAN`。
- 确认固定返回 `202/PENDING`，不能同步伪造扫描成功。owner 状态读取只投影
  `PENDING/READY/UNAVAILABLE`；`READY_UNCLAIMED` 仅在 claim deadline 前投影 READY，失败、隔离、
  删除和内部错误统一折叠为 UNAVAILABLE。
- 新增显式 `AFTER_SALE_EVIDENCE_MEMBER_UPLOADS_ENABLED=false` 门禁。启用时必须同时具有 D1 S3、
  D2 ClamAV 和逐环境显式 upload TTL、未认领数量/字节配额；缺项或非法组合启动失败。生产值仍需
  越南业务、隐私/DPO 与合规审批，仓库示例和 local/test 基线不是法律结论。

### 2.2 非目标

- 不修改售后、支付、退款、库存、物流或 COD 状态机，不创建 after-sale case，不 claim 凭证。
- 不签发保护读取 URL，不开放管理员 evidence.read，不写管理员读取审计。
- 不消费 expire/delete 消息，不执行物理删除、legal hold、删除补偿或外部告警。
- 不创建生产 bucket/IAM/KMS/lifecycle/versioning/Object Lock，不启用生产政策或 enforcement。
- 不交付 UI、Zalo 宿主流程、真实用户文件、部署、推送或发布。

## 3. 接口、数据与事务语义

### 3.1 初始化

- controller 严格解析 `Authorization`、`X-Store-Code`、`Idempotency-Key`、correlation ID、空 query 和
  `EvidenceUploadRequest`；认证和 write limiter 在任何 evidence 查询/写入前完成。
- service 在 capability 门禁通过后调用 D0 初始化。数据库先锁 `(store_id,member_id)` 配额，再写
  evidence、ORIGINAL ledger、expire outbox 和幂等事实；对象 key 只在内部传给 D1。
- D1 签名发生在数据库提交后。签名临时失败返回稳定 `503`；同一幂等键可重试并为仍有效的同一
  evidence 重新签名，不重复占用配额。数据库 upload deadline 与 URL deadline 分离，响应使用实际
  签名 deadline。
- contract-only 响应原先缺少签名所需 header。D3 在尚无运行调用方的前提下前向修正为必需
  `upload_headers` allowlist；客户端必须原样发送，不允许任意 provider metadata 进入公共响应。

### 3.2 确认

- 数据库先 owner-scoped 加载未确认、未过期且 expected-version 匹配的声明和受数据库 guard 保护的
  规范 ORIGINAL identity；该读取不信任 URL、客户端 key 或 provider metadata。member 不获得
  SYSTEM-only ledger 的 SELECT，D2 worker 仍从权威 ledger 独立重读并复核身份。
- D1 对象验证在数据库事务外执行，避免持锁跨网络；验证后确认事务重新取得 quota/evidence 锁并复核
  owner、商城、版本、状态和 deadline，再原子写 confirmed/generation/version 与 scan outbox。
- 对象缺失、声明与真实内容不一致或已过期统一返回稳定冲突，不泄露 provider/key/checksum/magic
  细节；storage 配置、网络、超时或不确定失败返回 `503`。幂等 replay 只复用已确认事实，不重新扫描
  或重复排队。

### 3.3 状态

- owner 状态读取使用 FORCE RLS 与显式 `store_id/member_id/id` 条件，并使用数据库时钟判断独占截止。
- 未确认/扫描中的有效 PENDING 返回 PENDING；已过 upload deadline 的未确认对象即使 expire worker
  尚未投影，也返回 UNAVAILABLE；未过期 READY_UNCLAIMED 返回 READY + claim deadline。
- claimed READY 的兼容投影使用 ordinary access deadline；其他内部状态和任何到期状态统一
  UNAVAILABLE。响应 schema 复验且固定 `Cache-Control: private, no-store`、`Referrer-Policy:
no-referrer` 和 `X-Correlation-Id`。

## 6. 风险、依赖与停止条件

- **签名与数据库非原子**：数据库先提交后签名；失败通过同键重试重签同一 create-only key 收敛，不能
  在 provider 成功后再用第二事务创建数据库身份。
- **TOCTOU/对象欺骗**：确认前真实验证，D2 扫描时再次以 ETag/If-Match 读取并同流复验；只有 D2
  精确 CLEAN 能进入 READY_UNCLAIMED。
- **能力误开**：D3 独立布尔开关默认 false；storage/scanner/TTL/配额任一不完整时配置或请求失败关闭。
- **状态泄露**：公共投影与错误仅使用 allowlist，不返回 object key、checksum、scanner 版本/签名、
  隔离原因、删除错误或 provider 原文；日志与测试同时检查敏感 marker。
- **无清理 consumer**：D3 不实现 expire/delete worker，因此完整 B2b 仍未完成。测试产生的对象必须
  显式清理；生产 rollout 继续阻塞，不能用 D3 仓库实现接收真实用户文件。

若真实 MinIO 上传/复验、真实 ClamAV 收敛、跨商城/owner 隔离、幂等、限流失败关闭或敏感信息检查
任一不能稳定通过，停止 D3 完成声明，保持开关默认 false。
