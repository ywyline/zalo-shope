## 2. 目标与非目标

### 2.1 目标

- 严格消费 `after-sale.evidence.expire.requested` v1 和
  `after-sale.evidence.delete.requested` v1；消息 payload 继续精确只有
  `store_id/evidence_id/expected_version`，不能携带或授权对象 key、截止点、hold 或 provider 事实。
- 为 expire 和 delete 建立 D2 同等级的 lease-bound 数据库边界：网络前后使用 evidence SYSTEM scope
  重锁 outbox/evidence/ledger，并复核商城、消息 version/status/owner/严格未到期 lease、evidence
  version/status、权威截止点、legal hold 与完整活动对象集合。
- expire 到期后原子进入 `DELETION_PENDING` 并排队当前 version 的 delete；旧、提前、已 hold 或已收敛
  消息不得推进状态。领域写入后 generic complete 崩溃时，重领旧消息只能 `SUPERSEDED`。
- delete 只从 D0 规范 ledger 加载 ORIGINAL、DERIVATIVE、SCAN_TEMPORARY 的活动对象，并用 D1
  delete-only 凭据逐个幂等删除。provider 成功与明确 `NoSuchKey` 均为成功；网络/供应商失败只保存稳定
  code，并使用 D0 至少 60 秒、最多 6 小时、第 5 次告警条件、第 8 次耗尽的领域模型。
- provider 删除成功而数据库提交崩溃时，重试以 not-found 幂等成功完成；部分对象成功、部分失败时，
  ledger 暂不清空，后续重试重新删除完整权威集合并最终原子收口。
- 增加 expire/delete 持久、有界 dead-letter 候选轮询；reconciliation 重锁权威事实，仅重排当前版本、
  形成安全领域失败或返回 `SUPERSEDED/HELD/EXHAUSTED`，不把 dead letter 当作授权。
- 删除 worker、删除 dead-letter 轮询与 scanner 分离配置和注册；scanner 关闭后仍可继续清理既有对象。
  capability 默认关闭，启用必须同时具备独立 S3 storage/delete 凭据、明确重试参数和足够 outbox lease。
- 关闭时先停止 outbox/dead-letter 领取并等待在途 provider 删除与数据库提交，随后才销毁共享 storage
  client 与 Prisma；日志不得包含对象 key、provider 正文、凭据、签名 URL、checksum 或文件正文。

## 3. 冻结状态、租约与失败语义

### 3.1 expire 状态推进

expire handler 只接受严格 event v1 与当前 PROCESSING lease。数据库原语按固定顺序锁 outbox 后锁
evidence，并在锁等待后用 `clock_timestamp()` 再次复核 lease。只有 message expected version 等于
evidence version、状态具有权威清理截止点、无 legal hold 且数据库当前时间达到截止点时，才调用 D0
transaction-local 原语进入 `DELETION_PENDING` 并同事务排队 delete。

- version/status 已推进、对象已删除或消息已被新权威 identity 取代：`SUPERSEDED`，由 generic outbox
  完成旧消息。
- legal hold 当前有效：`HELD`，不删除、不改写原始截止点；未来解除 hold 的受审能力必须排队当前权威
  expire/delete，本 D4 不提供该管理入口。
- 数据库时钟尚未到 deadline：`NOT_DUE`，handler 以数据库返回的剩余时间有界重试，不能静默完成并
  丢失清理任务。
- 成功：`DELETE_SCHEDULED`；状态推进和 delete outbox 任一失败时整个事务回滚。

### 3.2 delete 网络与提交

delete loader 只在当前 lease、当前 expected version、`DELETION_PENDING`、无 hold 时返回权威活动
ledger 快照。每个对象包含 id、version、role、store/evidence 和规范 object key；provider 删除身份按
role 严格校验：

- ORIGINAL：`{environment}/{store_id}/staged/{evidence_id}/original`
- DERIVATIVE：`{environment}/{store_id}/derived/{evidence_id}/{safe_name}`
- SCAN_TEMPORARY：`{environment}/{store_id}/scan/{evidence_id}/{safe_name}`

上传声明、扫描读取和受保护读取继续只接受 ORIGINAL 规范路径；扩展删除身份不得扩大上传/read 权限。
所有 provider 调用在数据库事务外执行，并在提交前全部 settled。成功提交重新锁 outbox/evidence/ledger、
复核 lease 与完整 `(object id, version)` 集合，再同事务清空所有 ledger key/hash 保留、清理兼容 key 与
敏感扫描字段并把父 evidence 置为 `DELETED`。

任一 provider 调用失败时，失败提交也必须重锁并复核相同 lease/evidence/ledger identity，再调用 D0
领域失败原语。旧 lease、version 漂移、hold 变化或 ledger 增删/版本变化均不得提交成功或失败。稳定
错误冻结为 `EVIDENCE_DELETE_PROVIDER_UNAVAILABLE` 或 `EVIDENCE_DELETE_IDENTITY_INVALID`；不保存
provider 原始错误。第 5 次失败只记录/日志输出稳定 warning condition，第 8 次记录 exhausted，并明确
只形成本地可观测事实，不声称外部告警已送达。

### 3.3 崩溃与重复投递

- expire 状态提交后、generic complete 前崩溃：旧 expire 重领返回 `SUPERSEDED`，不重复排队 delete。
- provider 全部删除后、数据库提交前崩溃：重领后 provider 明确 not-found 仍算成功，随后可提交 ledger。
- provider 失败投影后、generic complete 前崩溃：旧 delete 版本已过期，重领返回 `SUPERSEDED`；只有
  新领域 delete event 可执行下一次 provider attempt。
- 网络期间 lease 到期或被其他 worker 重领：旧 worker 的成功/失败提交均以 `OUTBOX_LEASE_LOST` 拒绝。
- 网络期间 legal hold、evidence version/status 或任一 ledger identity 变化：旧结果不得写入。

## 6. 风险、依赖与停止条件

- **旧 worker 写入**：所有领域提交绑定当前 outbox lease，锁等待后重读数据库时钟；lease 截止相等即
  拒绝，generic complete 不能修复先前越权领域写入。
- **部分物理删除**：ledger 只在全部 provider 删除成功且复核通过后原子清空；重试利用 not-found 幂等
  收敛，不把部分成功伪装成 `DELETED`。
- **对象集合漂移**：提交必须精确匹配 loader 的全部活动对象 id/version；新增、删除或版本变化均拒绝。
- **scanner 与清理耦合**：storage 构造和删除 handler 注册只依赖独立 deletion capability；禁用新上传/
  scanner 不得自动停止既有数据清理。
- **generic outbox 事件混领**：产生 scan/expire/delete 的会员能力只有 scanner 和 deletion handler 同时
  注册才可启用，避免未注册事件被通用 worker 作为 unsupported 永久死信。
- **长删除超过 lease**：删除请求并行且全部 settled，配置预算至少覆盖单次 storage timeout、前后两个
  2 秒事务和 5 秒提交余量；若目标 provider 无法满足预算，停止 rollout 并另行设计 heartbeat。
- **删除供应商语义**：只有成功或明确 `NoSuchKey` 可收口。普通 404/403、NoSuchBucket、网络及未知
  错误继续失败关闭；AWS 最小 IAM 与 versioning 语义必须在 staging 单独验收。
- **敏感信息泄漏**：handler/reconciler 只记录稳定 code、store ID、计数与 outcome；对象 key、provider
  正文、凭据、checksum、签名 URL 和正文不得进入日志、审计、错误响应或快照。

任一 lease 丢失、legal hold、跨商城、对象集合漂移、部分删除补偿、第五/第八次失败或关闭 drain 无法
稳定通过时，不得标记 D4 完成。

## 7. 测试与验收

### 7.1 单元与静态

- config 默认关闭；启用时缺 storage、retry 参数、max attempts 非 8、delay 越界、lease 预算不足均
  失败关闭。scanner disabled + deletion enabled 可解析，会员上传启用但 deletion disabled 必须拒绝。
- provider 删除分别接受三种规范 role 路径；role/path/store/evidence/environment 不一致、路径穿越和
  控制字符拒绝；upload/read 仍拒绝 derivative/scan 路径；明确 NoSuchKey 幂等成功。
- expire/delete handler 严格校验 aggregate/event/version/payload/lease；provider 失败映射、全部 settled、
  `SUPERSEDED/NOT_DUE/HELD`、第五次 warning、第八次 exhausted 和日志脱敏覆盖。
- lifecycle dead-letter 按商城有界轮询、单条失败不阻断批次、配置关闭无副作用、module destroy 等待在途。

### 7.2 数据库与真实基础设施集成

- `PENDING/READY_UNCLAIMED/READY/FAILED/QUARANTINED` 到期进入删除；未到期不丢任务；legal hold 阻止
  删除且不修改普通访问/retention 截止，解除并产生权威消息后可继续收敛。
- 真实 MinIO ORIGINAL/DERIVATIVE/SCAN_TEMPORARY 全部物理删除后父行才 `DELETED`；明确 not-found、
  重复投递和 provider 成功后 DB 提交崩溃可恢复，最终无活动 ledger key 或对象残留。
- provider 部分失败形成 `DELETE_FAILED` 与当前 version 的延迟 delete；第五次形成持久 warning condition，
  第八次 exhausted 且不再自动排队；稳定错误无 provider 正文。
- 错 owner/message version、lease 到期/换 owner、网络期间 legal hold/evidence version/ledger 漂移均拒绝
  成功和失败提交；A 租约丢失后 B 的权威结果不被 A 覆盖。
- 双商城已知 UUID、payload store/aggregate 篡改、跨商城 ledger/provider identity 在网络调用前拒绝。
- expire/delete dead letter 对当前事实重排/失败收敛；旧 version 返回 `SUPERSEDED`，hold/exhausted 保持
  安全事实；重复轮询不重复 transition、领域 attempt 或消息。
- 实际 Nest 关闭顺序证明 outbox 与两个 evidence dead-letter 服务均 drain 后才销毁 storage/Prisma。
