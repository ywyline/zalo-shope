# M6.3-B2b-D5 Protected Evidence Read Plan

> Status: `COMPLETE` - default-disabled repository implementation and local/test
> protected-read validation; production enablement remains blocked
>
> Scope: repository implementation and local/test validation only
>
> Depends on: M6.3-B2b-D0 through D4
>
> Requirement basis: `REQUIREMENTS.md` sections 3, 4, 14.3, 20, 21, and 23; `AGENTS.md` sections 3, 4, 6, 9, 10, 12, and 14.

## 1. Goal and non-goals

### Goal

Complete the remaining B2b protected-read boundary before a future B3 after-sales
application can bind buyer evidence. The API must issue a short-lived URL only for an
already claimed, clean `READY` ORIGINAL object that remains available to an authorized,
non-revoked caller at commit time. A legal hold preserves retention and deletion state;
it does not shorten the ordinary access window.

Two runtime operations are in scope:

- member protected read for evidence bound to the current member's after-sales case;
- administrator protected read with `store.after-sales.evidence.read`, explicit
  cross-store reason where applicable, and one safe audit record for every successful
  URL response.

### Non-goals

- B3 after-sales creation, cancellation, evidence claim caller, policy evaluation,
  review, return, exchange, refund, COD, or inventory behavior;
- legal-hold administration, deletion dead-letter administration, alert delivery,
  UI, Zalo-host behavior, production rollout, or production IAM/KMS/versioning/Object
  Lock/lifecycle certification;
- returning object keys, checksums, scanner details, provider bodies, credentials, or
  signed URLs in logs or audit records;
- any change to evidence lifecycle write authority, object-ledger visibility, or
  retention rules. D5 must not broaden a member's `UPDATE` policy merely because
  PostgreSQL evaluates row locks through that policy.

## 2. API and data behavior

### Member operation

`GET /v1/after-sales/{afterSaleId}/evidence/{evidenceId}` accepts the existing member
Bearer token and `X-Store-Code`. It is limited to the authenticated member and current
store. The evidence must be bound to the supplied after-sales case, be claimed,
`READY`, retain a non-null evidence-header object key, and be before its
`ordinary_access_deadline_at`. The D0 deferred original-binding guard guarantees that
this header key matches the unique active ORIGINAL ledger object; member/admin D5 reads
do not query the system-only object ledger. Legal hold does not independently deny a
still-live ordinary read.

### Administrator operation

`GET /v1/admin/after-sales/{afterSaleId}/evidence/{evidenceId}` accepts the established
admin headers and `store_id` query parameter. It requires
`store.after-sales.evidence.read`; `AdminService.authorize` retains the existing
current-store scope and writes the existing `platform.cross_store.accessed` audit when a
cross-store super-admin supplies a D5-safe `X-Access-Reason` incident reference in the
fixed `Protected evidence incident <TICKET>` form. Free text is rejected before either
audit is written, so it cannot carry a URL, object key, checksum, scanner result or
provider detail. The D5 successful-read audit is separate and occurs exactly once per URL
returned.

Both operations return a strict response containing only `url` and `expires_at`. The
response sends `Cache-Control: private, no-store`, `Referrer-Policy: no-referrer`, and
the correlation identifier. All cross-store, cross-member, wrong-case, unclaimed,
expired, non-`READY`, deleting, deleted, missing header object key, and otherwise
unavailable facts map to the same non-enumerating `404`. A legal hold remains opaque but
is not itself an unavailable fact while the ordinary access deadline is live.

## 3. Authorization and concurrency protocol

Signing is a network operation and must not hold a database transaction open. Each
request follows this sequence:

1. Authorize the caller, consume the existing after-sales read rate limit, and read an
   eligible evidence snapshot using a store-bound transaction.
2. Ask the D1 S3 adapter to sign the ORIGINAL object. The adapter receives a maximum
   expiry derived from the snapshot's `ordinary_access_deadline_at`; it rejects a
   non-positive lifetime and never signs a derivative or scan-temporary object.
3. Re-open a store-bound transaction and call the D5 authorization-aware
   security-definer lock function. It is owned by the cluster-level
   `zalo_shop_evidence_read_guard`, a `NOLOGIN`, `NOINHERIT`, `NOSUPERUSER`,
   `NOCREATEDB`, `NOCREATEROLE`, `NOREPLICATION`, `NOBYPASSRLS` role with no role
   memberships; it has a fixed search path and `row_security=on`. It first locks and
   revalidates the exact transaction-local store, actor, access-session ID, Bearer
   expiry, ACTIVE store and actor, and non-revoked/non-expired persisted session. For a
   member it also revalidates membership in the current store. For an administrator it
   locks and revalidates either the current-store `store.after-sales.evidence.read`
   assignment or the `platform.stores.cross_access` decision used for a cross-store
   request. Only then does it invoke the restricted evidence `FOR SHARE` lock. The
   legacy evidence-only function is no longer executable by `zalo_shop_runtime`.
   After the evidence lock is actually acquired, the function checks the database clock
   again against the Bearer, session, signed URL, and ordinary-access deadlines, so
   waiting behind a lifecycle writer cannot return an expired URL. It returns only the
   minimal D5 snapshot fields and retains its locks until commit. This remains the narrow
   exception required because PostgreSQL applies an `UPDATE` RLS policy to a direct
   `SELECT ... FOR SHARE`; it neither writes evidence nor exposes the object ledger.
   The caller compares the returned fields to the signed snapshot. A legal-hold-only
   version increment is not a denial because hold affects physical deletion rather than
   the ordinary access window.
4. For an administrator, write the allowlisted audit action in that same revalidation
   transaction. A write failure rolls back the revalidation transaction and prevents
   the URL response. The audit may include actor/store/case/evidence identifiers,
   correlation ID, and the fixed-format incident reference, but never the URL, object key,
   checksum, scanner result, provider response, or file content.
5. Return the signed URL only after the revalidation transaction commits.

The adapter fixes its signing timestamp to the preceding whole second, then uses the
smaller of the configured protected-read TTL and the remaining database access lifetime.
Its reported expiry is therefore never later than the database deadline even if presign
work itself takes time. A URL is not issued if the resulting lifetime is zero seconds or
less. The second database check ensures the URL response is not authorized after an
expiry, deletion transition, or rebinding. Hold does not invalidate a still-live ordinary
access window.

## 5. Compatibility, rollout, and rollback

The capability defaults to disabled, so D0-D4 behavior remains unchanged until all
existing S3/read credentials and D5 configuration checks are satisfied. Existing upload,
scanner, and deletion behavior stays independent of protected-read enablement.

The discovery phase found that direct `FOR SHARE` revalidation is rejected for a member
under D0's intentionally narrow claim policy. D5 therefore uses a forward-only,
authorization-aware locking boundary owned by the non-bypass guard role, rather than
weakening the member `UPDATE` policy. Existing business data is unchanged. Production
rollback is configuration-first: set the protected-read capability to `false`, then
allow in-flight requests and issued URL TTLs to finish. Do not delete evidence records,
storage objects, lifecycle outbox messages, audits, or the cluster-level guard role.
Only local/test databases with no
`after-sale.evidence.protected_read.issued` audit facts may run the exact reverse order
`48 -> 47 -> 46 -> 45 -> 44`; migrations 48 and 47 reverse only their audit-fact guard
and do not restore a weaker function. Each issued-read audit must fail fast. The reverse
scripts only remove current-database D5 function, policy, and grant artifacts.
Production and any database with an issued-read audit fact use a reviewed forward repair
only.

## 6. Risks, external dependencies, and failure policy

- A signed URL may outlive an authorization change occurring after the final transaction
  commits by at most its bounded, short TTL; it cannot pass the database deadline. The
  final authorization and post-lock expiry rechecks close the corresponding pre-commit
  race. This residual bearer-URL window is reduced by `no-store`/`no-referrer`, exact
  authorization, and short expiry.
- Storage signing failure, Redis failure, disabled capability, invalid configuration,
  or audit failure is fail-closed (`503` where appropriate) and returns no URL.
- The definer function is owned by a non-login, non-inheriting, non-bypass-RLS guard
  role with no superuser capability or role memberships. It runs with `row_security=on`
  and a fixed search path; its narrowly scoped grants and role-specific policies permit
  only the needed lock read, while its SQL manually checks all session identity and
  requested scope facts before returning the minimum snapshot. Tests must prove direct
  member/runtime row locking and ordinary writes stay denied, the function cannot cross
  member/store/case scope, and the `FOR SHARE` lock conflicts with a lifecycle write.
- The production deployment path is blocked unless a controlled PostgreSQL `rolsuper`
  maintenance executor is available for migrations 44, 45, 47, and 48. The application
  runtime role must not receive this privilege as a workaround.
- Evidence state races, scope mismatches, missing header object keys, and invalid or
  expired access facts are non-enumerating `404` responses. Legal hold does not cause a
  `404` before the ordinary access deadline.
- Production use remains blocked pending separate evidence that provider IAM keeps read,
  upload, and delete identities distinct; production uses HTTPS and explicit KMS; bucket
  versioning/Object Lock/lifecycle and legal-retention semantics are approved; and an
  operational rollout owner accepts the residual bearer-URL window.

- requested URL TTL truncation under signing latency, non-positive remaining TTL

- safe error mapping and no sensitive URL/key/checksum/provider data in audit inputs;

  Redis rate-limit failure/limit behavior;

  ORIGINAL URL, and rejection of derivative/scan-temporary identities;

## 8. Completion criteria

D5 is complete only when the two protected-read operations are default-disabled,
authorized, non-enumerating, ORIGINAL-only, deadline-bounded, race-revalidated across
migrations 44-48, and covered by the stated tests; the scoped locking function does not
broaden member write authority; administrator returns are audited atomically with the
final authorization check; documentation and OpenAPI are synchronized; and all
applicable repository gates have passed. Completion must be reported as repository plus
local/test validation, not production readiness.

These criteria are satisfied for repository implementation and local/test validation as
recorded in the D5 completion report. Production storage certification, risk acceptance,
deployment, and rollout remain outside this completion status.
