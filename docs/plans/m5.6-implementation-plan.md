## 1. 目标与非目标

### 1.1 目标

- 在现有 `ShippingProvider` 端口内实现 GHN sandbox/production 适配器，覆盖服务列表、报价、
  建单、取消、主动查单、面单和未签名 webhook hint 解析；所有外部请求使用商城独立的
  ShopId 与 secret reference。
- 管理员只可为当前商城 `PENDING_FULFILLMENT` 订单创建一个活动运单。服务端重载不可变订单
  地址、订单行物理属性、默认履约仓库、COD 金额和渠道配置，不接受请求传入金额、地址、
  重量、供应商单号或费用。
- 外部建单、取消和查询通过版本化 outbox 在数据库事务外执行；稳定内部公开号同时作为 GHN
  `client_order_code`，重试复用且不制造第二张活动运单。
- 将 GHN 状态规范化为内部运单状态并去重轨迹。只有权威主动查询事实可以推进订单发货/签收；
  webhook 只能调度查询。拒收、退回、异常和未知/倒退状态进入保守处理，不自动退款、恢复库存
  或完成订单。
- 提供商城隔离的管理端运单操作、受审短期面单访问和买家物流轨迹读取，并覆盖越南语、中文、
  英文的加载、空、失败和重试状态。

### 1.2 非目标

- 不实现第二家物流商、拆单/部分发货、批量发货、自动退款、退货库存恢复、COD 回款对账或
  ERP/WMS；这些能力分别属于后续 M5.7、M6 或 P1。
- 不创建 GHN 测试运单、调用真实 GHN endpoint、生成看似真实的供应商响应，也不把注入式
  HTTP 契约测试描述为 sandbox 验收。
- 不从 GHN 未签名 webhook 直接写入权威运单或订单状态，不在 API/日志/审计 diff 中暴露
  GHN Token、完整手机号、联系人或地址。
- 不以默认重量、默认尺寸或管理员补传值修复旧订单；缺失可信物理事实时明确阻断建单。

## 2. 已冻结供应商契约与外部阻塞

- 供应商固定为 GHN；sandbox origin 为 `https://dev-online-gateway.ghn.vn`，production origin
  为 `https://online-gateway.ghn.vn`。路径和状态映射沿用 `ghn-contract.ts` 冻结版本。
- 请求只使用服务端解析的 `Token`、`ShopId` 与仓库/订单事实。origin 采用显式 allowlist，禁止
  redirect，并限制总超时、响应字节、JSON content type 和整数范围。
- GHN webhook 官方契约没有签名字段，固定为 `UNVERIFIED_HINT`。只有 hint 唯一定位到已绑定
  渠道和运单后才追加去重事实并排队主动查询；query 结果仍需核对商城、ShopId、
  `client_order_code` 和 provider shipment ID。
- 真实测试账户、两个商城独立 ShopId/Token secret reference、测试仓库/退货地址、可用服务、
  COD 能力、测试订单、面单与 webhook 环境尚未提供。相关外部验收保持 `BLOCKED/NOT_RUN`。

## 3. 数据模型与可信事实

### 3.1 仓库履约资料

- 新增 `warehouse_fulfillment_profiles`，以 `(store_id, warehouse_id)` 为主键并复合外键绑定同
  商城仓库。联系人、电话和详细地址使用现有敏感字段加密机制；省/区/坊代码与名称、启用状态、
  版本和时间戳作为受审配置保存。
- 资料默认不存在且不能由 seed 虚构。建单只选择同商城、启用、默认履约仓库及其完整资料；
  缺失或无效时返回稳定配置错误。普通读取只返回完整性状态和掩码，不回显密文或 secret。
- 迁移为仅新增；资料修改不回写已经创建运单的加密地址快照。

### 3.2 订单物理属性快照

- `order_items` 新增 `weight_grams`、`length_millimeters`、`width_millimeters`、
  `height_millimeters` 可空列及正整数约束。M5.6 部署后创建的新订单必须从服务端 SKU 事实复制
  四项字段；任何 SKU 缺项都阻断结算/下单并返回稳定错误。
- 列保持可空仅为兼容既有订单，迁移不回填当前 SKU 值，避免把可变商品资料伪装成历史快照。
  旧订单缺失任一物理字段时禁止创建 GHN 运单并进入人工资料修复流程；生产只允许经审计的
  向前修复，不允许由建单请求补传。
- 运单创建时按订单行数量计算总重量，并以保守装箱规则形成不可变 `parcel_snapshot`：重量为
  行重量乘数量之和；长宽高采用经过范围校验的订单快照维度。本阶段每单一个包裹，不建立
  未经业务确认的体积压缩或多箱算法。

### 3.3 运单与可靠命令

- 复用 `store_shipping_channels`、`shipping_quotes`、`shipments`、`shipment_items`、
  `tracking_events`、`shipping_operations`、`provider_callbacks` 和 `outbox_messages`。
- 数据库部分唯一索引保证同订单最多一张非终态活动运单；运单项必须覆盖每个订单行的全部数量。
  `provider_shipment_id` 只能由 provider create/query 响应写入。
- 运单保存创建时加密目的地址、包裹、服务、COD 和仓库快照。outbox payload 只含
  `store_id/shipment_id/operation_id/version`，不含 PII、金额明细、密钥或供应商授权头。
- `shipping_operations` 记录 CREATE/CANCEL/QUERY/LABEL 命令状态与稳定错误分类；外部调用前后
  各使用短事务，不跨网络持有数据库锁。

## 4. 模块与接口变化

### 4.1 集成层

- `packages/integrations/src/ghn-shipping-provider.ts`：受控 HTTP、GHN DTO 严格解析、Token/ShopId
  头、报价/建单/取消/查单/面单和 callback hint。
- `packages/integrations/src/shipping-provider-resolver.ts`：按商城渠道和 environment 解析唯一 GHN
  provider；secret reference 复用受限解析器，不支持明文 Token 或非测试 fallback。
- `ghn-contract.ts` 和契约测试：服务 code/type ID、状态、整数 VND/gram/cm、未知响应、429/5xx、
  超时、非 JSON、超大响应和 redirect。

### 4.2 数据库、API 与 worker

- `packages/database` 新增仓库履约资料、运单命令、权威 provider fact、轨迹去重和订单转换原语；
  所有入口设置事务级商城上下文并按固定顺序锁定运单、订单和 operation。
- `apps/api` 实现冻结的管理端报价/建单/取消/同步/面单、买家订单物流查询和 GHN webhook hint。
  管理端写操作执行 RBAC、近期 MFA、二次确认、reason、expected version、幂等键和审计。
- `apps/worker` 注册 `shipment.create.requested.v1`、`shipment.cancel.requested.v1`、
  `shipment.query.requested.v1` handler；provider 调用在事务外，结果只通过数据库事实命令落库。
- 面单 API 每次读取均审计；只返回受 allowlist 约束、短于 GHN token 生命周期的代理/短期访问，
  不向浏览器返回 Token 或任意上游 URL。

### 4.3 客户端与文档

- 管理端订单详情增加运单创建、取消、同步、面单和轨迹状态；买家订单详情展示三语规范化轨迹。
  复用现有设计系统与主题变量，移动端优先处理加载、空、错误、重试和危险操作确认。
- 同步 OpenAPI、数据字典、架构、环境示例与完成/进度报告。示例配置保持 provider disabled，
  不包含 ShopId、Token、真实地址或手机号。

## 5. 状态机与事务边界

1. 建单命令在短事务中校验商城/RBAC/订单 `PENDING_FULFILLMENT`/expected version、可信地址与
   物理快照、默认仓库、渠道和全量订单行；创建 `CREATION_PENDING` 运单、operation、items、
   审计和 outbox 后提交。
2. worker 在事务外解析 provider 并调用 GHN；成功响应必须匹配稳定 `client_order_code`，再在
   新事务中写 provider ID、`PENDING_PICKUP`、轨迹和 operation 结果。建单成功不代表已发货。
3. webhook hint 只去重并追加 query outbox。主动 query 返回 `IN_TRANSIT` 或
   `OUT_FOR_DELIVERY` 时最多触发一次订单 `SHIP`；返回 `DELIVERED` 时必要时先补 `SHIP`，再触发
   `DELIVER`。所有转换复用订单领域合法转换规则并只追加时间线。
4. `REFUSED/RETURNING/RETURNED/EXCEPTION` 只更新运单和轨迹并提示人工处理。
   `DELIVERED/RETURNED/CANCELLED` 后的倒退以及未知状态设置 `REVIEW_REQUIRED`，不推进订单。
5. 取消命令先记录 operation/outbox；只有 GHN 权威响应确认取消后更新运单。已经揽收、签收、
   退回或复核中的运单不能通过管理员请求本地强制取消。

## 6. 迁移、兼容和回滚

- 新迁移只增加仓库履约资料、订单行可空快照列、约束、RLS、复合外键和运行角色最小权限。
  不创建渠道、仓库资料、运单、报价或轨迹，不回填旧订单物理字段。
- fresh database、M2-to-current、重复 deploy 与现有 COD/ONLINE 流程必须兼容。应用发布顺序为
  schema、双读兼容代码、新订单强制快照、worker，最后在外部验收后逐商城启用 GHN。
- `down.sql` 仅供无真实业务事实的 local/test scratch；检测到新订单物理快照、仓库履约资料、
  shipping channel secret reference、运单、轨迹或物流 operation 时以 SQLSTATE `55000` 拒绝。
  生产和已有事实环境只允许向前修复。
- 回滚应用时保留 schema 与当前/上一版 outbox 消费能力；禁用渠道只阻止新建外部单，不能丢弃
  已有运单的查询、回调提示或终态处理。

## 7. 风险与安全门禁

- 多商城：渠道、仓库、订单、运单、operation、outbox、轨迹和审计均使用可信 `store_id` 复合
  绑定；测试跨商城 IDOR、RLS、ShopId 碰撞和 webhook 候选泄漏。
- PII：联系人、电话、详细地址只在调用 GHN 前短暂解密；日志、错误、outbox、审计和普通 DTO
  禁止包含原文。测试异常路径和 provider error 不回显请求 body/Authorization。
- 网络：固定 HTTPS origin/path、拒绝 redirect、限制 DNS/连接/总超时与响应字节；不接受请求
  URL、label URL 或 callback 字段作为任意代理目标。
- 幂等与状态：并发建单、worker 重试、重复 hint/query、乱序轨迹、取消竞态和 delivered 跳步均
  由数据库唯一约束、expected version、行锁与只追加事件共同保护。
- 业务真实性：缺凭据、地址、重量、服务或供应商能力时明确失败；不允许固定成功、默认重量、
  假费用或静默 fallback。固定运费降级只有在商城已有批准策略且响应明确标识来源时才可使用。

## 8. 测试与验收矩阵

- 单元/契约：GHN DTO、状态映射、未知/倒退状态、parcel 计算、整数/范围、service 解析、callback
  hint、敏感字段过滤和错误分类。
- HTTP：HTTPS/origin/path allowlist、Token/ShopId、timeout、429/5xx、redirect、content type、
  非 JSON、重复/缺失字段、超大响应和 secret resolver 不泄漏。
- PostgreSQL 集成：迁移/RLS/复合外键/最小授权、跨商城、活动运单唯一、全量 shipment items、
  operation/outbox 幂等、轨迹去重、状态并发、SHIP/DELIVER 只执行一次和 down `55000` 门禁。
- API：认证/RBAC/MFA/确认/reason/expected version、IDOR、金额/地址/重量/供应商 ID 篡改、
  webhook hint 去重、label SSRF/审计、稳定错误和 PII 脱敏。
- E2E/UI：双商城、三语、Chromium/WebKit、管理端建单/同步/取消/面单状态、买家轨迹，以及加载、
  空、失败和重试；Web 预览不替代 Zalo 宿主真机。
- 仓库门禁：定向测试、`corepack pnpm verify`、`corepack pnpm test:integration`、
  `corepack pnpm test:migration:m2-upgrade`、`corepack pnpm test:e2e`、生产依赖 audit、Gitleaks、
  `git diff --check` 和最终敏感信息检查。
- 外部验收：两个商城 GHN sandbox 报价、建单幂等、取消、查单、面单、webhook hint、轨迹、COD
  和测试设备证据。凭据与测试材料未提供前逐项保持 `BLOCKED/NOT_RUN`。

## 9. 完成与停止条件

- 仓库自动化范围只有在实现、迁移、文档、三语 UI 和全部适用门禁通过后才可收口；真实 GHN
  sandbox 与 Zalo 宿主验收未完成时，不得将 M5.6 或 M5 标为完成。
- 若 GHN 实际契约要求信任未签名 webhook、改变金额/订单/库存/物流状态机、存储明文凭据或
  放松商城隔离，立即停止实现并更新本计划、总计划、数据字典和安全设计后重新确认。
