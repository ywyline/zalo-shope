## 1. 目标与非目标

### 目标

- 在管理员售后退款命令中实现服务端金额计算和商城/订单/支付/售后隔离。
- 提取可复用的 transaction-scoped M5 refund 创建原语，保持既有 M5 管理 API 行为兼容。
- 在同一 Serializable 事务内原子创建 ONLINE settlement、M5 refund、退款 transition/outbox、唯一售后 link，
  并追加售后 `QUEUE_REFUND`/`REFUND_REQUESTED` 事实。
- 为 M5 refund provider 结果建立版本化售后同步 outbox；重复、乱序和不确定结果必须幂等或失败关闭。
- 将 `REFUND_SUCCEEDED`、`REFUND_FAILED`、`REFUND_CANCELLED` 与 `REQUIRE_REVIEW` 由明确 SYSTEM actor 写入，
  不冒用人工审核身份。
- 保持能力默认关闭；完成 local/test 单元、数据库、API、worker、迁移和静态门禁。

### 非目标

- 不调用真实 ZaloPay 或其他支付 provider，不使用生产密钥，不部署或发布。
- 不实现 COD 到账证明/双人结算（B7）、退件验收与库存恢复（M6.4）、换货履约或 UI。
- 不开放人工恢复 `REVIEW_REQUIRED`、不把查询耗尽或 provider UNKNOWN 标记为成功。
- 不改写历史订单、历史退款或既有 M5 provider 契约。

## 3. 数据与接口变化

- 复用 `after_sale_settlements` 的 `ONLINE_ORIGINAL`、`after_sale_refunds` 唯一 link 和现有 `refunds` 表；不建立第二套 ONLINE 退款账。
- settlement 金额固定为售后 `approved_total_vnd`，只接受服务端计算结果；不得接受客户端 amount/payment branch。
- settlement 的 request hash 绑定 actor、store、case、expected version、reason、path 和幂等键；同键异参稳定冲突。
- M5 refund 使用同一 payment attempt，link 在同一事务创建；已存在 link、退款容量、支付状态或订单商城不匹配均失败关闭。
- `refund.create.requested` 与新增 `after-sale.refund.sync` 消息只携带 `store_id`、`refund_id`、版本/身份字段，不信任 payload 中的金额或状态。
- provider `SUCCEEDED/FAILED/CANCELLED` 只在锁定 M5 refund 与售后聚合后按当前权威状态收敛；金额、provider reference、版本或 link 不一致进入 `REVIEW_REQUIRED`。
- 现有 M5 refund 管理 API、幂等键、provider 适配器和订单支付状态投影保持兼容。

## 4. 迁移、兼容与回滚

- 本阶段不新增数据库迁移；复用 M6.2/B0 已有 settlement/link、SYSTEM actor/event allowlist、RLS 和 outbox guard。
- runtime 不能直接写 settlement/link/售后 transition；应用命令在既有窄 guard 和同一 Serializable 事务内完成原子事实写入。
- `down.sql` 只允许 local/test 且不存在 B6 settlement、link、refund-sync operation/transition/audit 事实时执行，事实存在返回 SQLSTATE `55000`。
- 应用回滚先保持 B6 capability disabled，继续消费已创建的 M5 refund/provider 事实；不得删除或逆转资金记录。
- 已创建退款事实的环境只允许向前修复，不能通过回滚清理 settlement、refund 或 outbox。

## 5. 风险、依赖与停止条件

- 真实 provider sandbox、回调和对账仍是外部门禁；本阶段只能证明仓库/local-test 协调，不宣称支付集成完成。
- M5/M6 锁顺序必须固定为幂等锁 → order → payment attempt → refund → after-sale → settlement/link，发现无法证明时停止实现。
- 任一金额/商城/支付状态不一致、provider UNKNOWN、查询耗尽或重复 provider reference 必须进入 review 或稳定失败，不能自动成功。
- B6 不得扩大普通管理员跨商城能力；仅目标商城的 `store.after-sales.review` 与退款权限、近期 MFA 和审计可写。

## 7. 实施收口

- B6 已实现默认关闭的管理员 ONLINE 退款路由、M5 transaction-scoped refund 原语、settlement/link 原子协调、版本化售后同步 outbox 与无条件注册的 worker handler。

## 8. 2026-08-01 基线审计加固

企业工作流迁移后的最终差异审查发现两项收口缺口：初版命令在取得售后聚合锁后才进入 M5 共享订单退款
锁，与既有 M5/B3 锁序相反；四项直接权限仅在服务层事务前检查，没有在锁等待后以数据库权威事实重验。
本切片因此保持 `In Progress`，在不新增 schema/迁移和不扩大产品范围的前提下完成以下修复：

- 先读取只读售后身份，再取得既有 `m62-refund:{store}:{order}` advisory lock、订单和成功支付锁，最后锁定
  售后聚合；随后复用 transaction-scoped M5 refund 原语，消除 order/after-sale 反向等待。
- 在同一 Serializable 事务内以 `FOR SHARE` 锁定 ACTIVE 商城/管理员、有效 session、近期 MFA 和目标商城
  四项直接权限；权限/session/时钟在第一笔业务写入前最终重验，撤销与命令提交严格串行。
- 新增并发回归：命令等待共享订单锁时不得提前持有售后行锁；等待期间撤销 `store.refunds.create` 后命令
  必须原子返回 `AFTER_SALE_AUTHORIZATION_DENIED`，且不得留下 settlement/refund/transition/audit。

上述修复属于 B6 安全与并发完成定义，不是新功能，也不改变 default-disabled/production 拒绝边界。全部
定向、integration、迁移和仓库门禁重新通过前，不得恢复 B6 `COMPLETE` 状态。
