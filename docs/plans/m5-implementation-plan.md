## 1. 目标与非目标

### 1.1 目标

- 在 M4 COD 链路之外开放商城隔离的 `ONLINE` 下单，接入一种已确认的线上支付沙箱，
  Mini App 通过 Zalo 官方 Checkout 能力由用户主动发起支付。
- 服务端创建支付单并以整数 VND 核对金额、币种、商城、订单和状态；客户端跳转或 SDK
  返回值只用于提示和触发服务端查询，不能确认支付成功。
- 支持签名回调、主动查单、丢回调补偿、退款基础和支付对账；重复、乱序或重放事件不能
  重复消费库存、推进订单或退款。
- 接入一家已确认的越南物流商沙箱，支持报价、创建/取消运单、面单、轨迹、签收、拒收、
  退回和人工补偿；供应商状态必须映射为内部统一状态。
- 建立带 `store_id` 的 transactional outbox、inbox/回调去重、有限重试、死信/人工重放和
  可观测失败元数据。
- 为买家端提供移动优先、三语的支付发起/处理中/失败/恢复与物流轨迹体验；为管理端提供
  支付、退款、物流和补偿工作台，并继续复用双商城同一套代码。

### 1.2 非目标

- 不同时接入多个线上支付或多个物流商；未选中的供应商只保留稳定端口，不编写声称可用的
  适配器。
- 不实现退货退款、换货、售后凭证和售后政策状态机；这些属于 M6。M5 退款仅覆盖支付流水
  基础、受权管理员主动退款和供应商结果同步，不自行决定退货或恢复库存。
- 不实现积分、KOL/KOC、OA 营销通知、高级 COD 风控、ERP/WMS 或电子发票。
- 不信任客户端金额、运费、商城、支付状态、物流状态、供应商单号或退款结果。
- 不把测试适配器用于非 `test` 环境，不以固定成功响应替代供应商沙箱契约和真机证据。

## 2. 当前基线与必须保持的不变量

- M4 只允许 `COD` 创建订单；`ONLINE`、`PENDING_PAYMENT` 和现有支付状态枚举是兼容端口，
  不代表已有支付集成。
- 在线支付下单继续复用 M4 服务端最终报价、加密地址/价格/政策/券快照、购物车转换、库存
  预留绑定、优惠券核销、商城/会员幂等键和 `SERIALIZABLE` 有界重试。
- 每个外部业务事实必须同时绑定可信 `store_id` 和内部稳定 ID。商城归属从认证上下文、已绑定
  订单和服务端渠道配置解析，不能从回调查询参数或客户端请求直接采信。
- 金额只使用整数 VND；支付单、退款、COD、物流报价和对账差异不得使用二进制浮点数。
- 支付成功只由服务端验签回调或主动查单确认。同一成功事实只消费一次库存，并通过显式订单
  状态机留下只追加转换记录。
- 外部 HTTP 调用不得持有数据库事务或行锁；数据库事实先提交，再通过幂等命令和 outbox
  调用供应商。供应商响应必须在新的短事务内按版本/状态重新校验后落库。
- 供应商原始交互按数据最小化保存：密钥、完整卡数据、授权 Header、手机号和地址禁止进入
  原始流水；必要原文加密并设置保留期限，常规日志仅记录内部 ID、脱敏供应商引用和错误类别。

## 3. 先决决策与配置边界

### 3.1 必须由业务方确认的供应商

1. P0 线上支付渠道已确认为 ZaloPay，通过 Zalo Checkout 的 `ZALOPAY_SANDBOX`/
   `ZALOPAY` 方法接入。Zalo Checkout 负责 Mini App 支付入口与 Checkout Server API，不能
   替代 ZaloPay 商户协议、服务端 MAC、回调、退款和对账责任。
2. P0 物流商已确认为 GHN；沙箱接入必须覆盖报价、预计时效、创建/取消运单、面单、轨迹和
   GHN 能力范围内的 COD 字段。
3. 两个商城使用独立渠道配置和密钥引用；即使底层法人相同，也不共享可被普通商城管理员
   读取的凭据或可跨商城使用的签名上下文。

M5.1 按 2026-07-24 读取的 Zalo Checkout 官方文档（页面标记最后更新 2026-06-15）和 GHN
官方 API 文档冻结契约。供应商后续文档变更必须先做差异审查，不得静默改变签名、状态码、
退款、回调、面单或 SLA 语义。

### 3.2 配置原则

- 新增商城范围的支付/物流渠道配置，保存渠道代码、环境、启停状态、能力、公开商户引用、
  加密密钥引用、回调版本、超时和重试策略；禁止把真实密钥直接写入业务表、示例配置或前端。
- 密钥由部署密钥管理系统注入服务端，数据库只保存不可逆指纹或 secret reference。密钥轮换
  支持当前/上一版本短期并存和明确的启用时间，不允许通过管理端回显。
- `test` 使用可编程但严格限制 `NODE_ENV=test` 的契约适配器，可注入成功、失败、超时、乱序、
  重复和未知状态；staging/production 配置不得回退到测试适配器。
- 测试、staging、production 的商户 ID、端点、回调域名、密钥和队列命名完全分离。

### M5.3：Outbox、Inbox 与可靠 worker

- 业务事务内追加版本化 outbox；worker 采用 `FOR UPDATE SKIP LOCKED`、租约、有限指数退避和
  抖动处理，不在失败时删除事实。
- 外部回调先按供应商原始请求验签，再解析商户/事件身份；inbox 以供应商、账户、环境、事件
  ID 去重。无稳定事件 ID 的供应商使用经审查的规范化摘要并保留原始时间戳/nonce 防重放。
- 区分可重试、永久失败和人工复核；达到上限进入明确死信状态，后台受权操作可重新入队，
  每次操作追加审计而不是覆盖历史。

完成记录：本阶段已实现版本化、商城绑定且限制敏感键/大小的 outbox 追加原语，逐商城
`FOR UPDATE SKIP LOCKED` 短租约 worker、过期租约恢复、有限指数退避与抖动、分类死信、
inbox 数据库并发去重/状态命令，以及带商城/领域权限、近期 MFA、二次确认、原因和 expected
version 的审计重放。当前与上一探针事件版本仅在 `NODE_ENV=test` 注册，非 test 构造硬失败；
没有调用供应商、启用渠道或创建支付/物流成功事实。下一步只进入受限 M5.4。

### M5.4：线上支付核心与测试适配器

- `ONLINE` 下单在 M4 原子事务中创建 `PENDING_PAYMENT` 订单、库存预留、首个支付尝试和
  `payment.create.requested.v1` outbox；订单返回前不伪造供应商支付载荷。
- worker/应用服务在事务外调用 `PaymentProvider.createPayment`，以内部支付尝试 ID 作为稳定
  幂等引用，保存经校验的 Checkout SDK 载荷或支付跳转信息及过期时间。
- 回调/主动查单共同进入同一支付事实命令。成功时锁定支付尝试与订单，核对商城、VND 金额、
  币种和当前状态，只执行一次库存 `CONSUME`，再记录
  `PENDING_PAYMENT -> CONFIRMED -> PENDING_FULFILLMENT` 两个显式订单转换。
- 失败的单次支付尝试不自动关闭仍可重试的订单；买家可在订单支付窗口内创建新尝试。订单
  过期或取消时终止可终止的支付尝试并释放预留，迟到成功进入人工复核/自动退款策略，禁止
  复活终态订单。
- 测试适配器覆盖成功、失败、超时、重复、乱序、金额/商城篡改和未知状态，并在非测试环境
  构造时硬失败。

完成记录（2026-07-26）：本阶段已按受限路径实现 ONLINE 原子下单、首个/重试支付尝试、
`payment.create.requested.v1` handler、确定性 test-only provider、短期 launch 完整性校验、统一
支付事实命令、一次性库存消费、两段订单转换、取消/过期协调和迟到成功复核。未新增数据库迁移，

边界见 `docs/reports/m5.4-completion-report.md`。真实 ZaloPay/Checkout SDK、HTTPS 回调、sandbox、

## 5. 预计数据模型与关键约束

最终名称和字段已在 M5.1 冻结并由 M5.2 迁移实施；以下模型继续约束 M5.3-M5.7 的运行时实现。

### 5.1 渠道与支付

- `store_payment_channels`：商城、渠道、环境、状态、能力、公开商户引用、secret reference、
  签名版本、配置版本和审计时间；商城/渠道/环境唯一，强制 RLS。
- `payment_attempts`：商城、订单、渠道配置、公开支付号、尝试序号、整数 VND 金额、币种、
  内部状态、脱敏供应商引用、创建幂等键、过期时间和版本；`(store_id, id)`、
  `(store_id, order_id)` 使用复合外键，公开支付号全局不可猜且唯一。
- `payment_transitions`：只追加的前后状态、标准化事件、来源、供应商事件引用、操作者、原因、
  correlation ID 和时间。
- `provider_callbacks`：商城、渠道配置、环境、供应商事件 ID/摘要、接收时间、验签结果、
  防重放字段、处理状态、加密/脱敏载荷引用、错误类别和重试元数据；只追加，去重键包含渠道
  账户和环境。
- `refunds`、`refund_transitions`：商城、支付尝试、订单、公开退款号、请求/成功整数 VND、
  状态、供应商引用、幂等键、原因、发起管理员和只追加转换。数据库约束保证累计成功及处理中
  金额不超过原成功支付金额。

支付尝试内部状态至少区分 `CREATED`、`PROVIDER_PENDING`、`SUCCEEDED`、`FAILED`、
`EXPIRED`、`CANCELLED`、`REVIEW_REQUIRED`；退款至少区分 `REQUESTED`、`PROCESSING`、
`SUCCEEDED`、`FAILED`、`CANCELLED`、`REVIEW_REQUIRED`。未知供应商状态不得映射为成功。

### 5.2 物流

- `store_shipping_channels`：商城、供应商、环境、状态、能力、公开账户引用、secret reference、
  服务配置、超时和配置版本。
- `shipping_quotes`：商城、订单或结算会话、地址/仓库摘要、服务代码、整数 VND 费用、预计
  时效、来源、供应商引用、请求 hash 和过期时间；过期报价不能直接用于下单。
- `shipments`：商城、订单、仓库、内部运单号、渠道配置、标准状态、脱敏供应商运单号、服务
  代码、COD 整数 VND、地址/包裹快照、创建/取消幂等键、版本和时间。
- `shipment_items`：商城、运单、订单行和数量，为未来拆单保留完整约束；M5 API 强制单活动
  运单覆盖全部可履约数量。
- `tracking_events`：商城、运单、供应商事件键、内部状态、原始状态代码、三语可映射描述键、
  发生/接收时间、脱敏地点和载荷引用；按供应商事件键去重且只追加。
- `shipping_operations`：报价、建单、取消、查轨迹、取面单和人工补偿命令的幂等事实与失败
  分类，不用覆盖业务实体来记录重试。

物流内部状态沿用需求：`PENDING_PICKUP`、`IN_TRANSIT`、`OUT_FOR_DELIVERY`、`DELIVERED`、
`REFUSED`、`RETURNING`、`RETURNED`、`EXCEPTION`、`CANCELLED`。供应商未知状态记录并告警，
不得直接污染订单状态。

### 5.3 可靠消息

- `outbox_messages`：商城、聚合类型/ID、事件类型/版本、幂等键、最小化载荷、状态、可见时间、
  租约、尝试次数、最后错误类别和时间；同一业务命令的事件键唯一。
- `inbox_messages`：商城、来源、渠道账户、环境、外部消息键、处理状态、载荷摘要、接收/完成
  时间和错误类别；唯一约束承担并发去重，应用内缓存不能作为唯一防线。
- 队列消息、Redis 键、日志字段和 worker 指标必须包含 `store_id`，但指标标签不得使用订单号、
  运单号或会员 ID 等高基数字段。

## 6. 领域状态与事务边界

### 6.1 支付与订单

| 事实                 | 支付尝试结果          | 订单处理                                              | 库存处理                |
| -------------------- | --------------------- | ----------------------------------------------------- | ----------------------- |
| 创建在线订单         | `CREATED`             | `PENDING_PAYMENT`                                     | 保持预留                |
| 供应商受理           | `PROVIDER_PENDING`    | 不变                                                  | 不变                    |
| 首次合法成功         | `SUCCEEDED`           | `PENDING_PAYMENT -> CONFIRMED -> PENDING_FULFILLMENT` | 只消费一次              |
| 单次失败、仍可重试   | `FAILED`              | 保持 `PENDING_PAYMENT`                                | 保持至订单支付窗口      |
| 订单超时/主动取消    | `EXPIRED`/`CANCELLED` | `CLOSED`/`CANCELLED`                                  | 只释放一次              |
| 终态订单收到迟到成功 | `REVIEW_REQUIRED`     | 不复活                                                | 不消费；按策略查单/退款 |
| 退款成功             | refund `SUCCEEDED`    | 更新支付聚合；订单业务状态不越级                      | M5 不自动恢复           |

`order.payment_status` 是支付聚合的服务端投影，不替代支付尝试和退款流水；M5.1 必须明确增加
部分退款/全部退款投影及其兼容策略。订单状态只能通过领域事件推进，不能由控制器、回调 DTO
或供应商状态直接赋值。

### 6.2 物流与订单

- 建单成功不等于已发货；只有供应商已揽收或经授权人工确认的合法事实才能触发 `SHIP`。
- 所有活动运单达到内部 `DELIVERED` 后才触发订单 `DELIVER`；M5 单活动运单限制使该聚合规则
  明确。`DELIVERED -> COMPLETED` 的自动/人工时点在 M5.1 按商城售后窗口策略冻结。
- `REFUSED`、`RETURNING`、`RETURNED` 和 `EXCEPTION` 只记录物流事实并进入人工/后续售后
  流程，不自动退款、恢复库存或标记订单完成。
- 取消运单先校验供应商能力和当前状态；本地取消请求不能先行伪造成供应商取消成功。

## 7. 接口、端口与权限面

### 7.1 供应商端口

`PaymentProvider` 至少覆盖创建支付、查询支付、验证并规范化回调、取消可取消尝试、创建/查询
退款和拉取对账。`ShippingProvider` 至少覆盖报价、创建/取消运单、获取面单、查询轨迹、验证并
规范化回调和拉取可用对账。端口输入只使用内部规范模型，输出使用可穷举状态和分类错误；
供应商 DTO 只能存在于 `packages/integrations` 的具体适配器内。

### 7.2 预计 API

- 买家：创建/查询在线支付尝试、查询支付结果、订单物流与轨迹；所有接口从认证会员和订单
  关系获取商城，不接受任意 `store_id`。
- 回调：`POST /v1/webhooks/payments/{provider}`、
  `POST /v1/webhooks/shipping/{provider}`；不使用会员/管理员认证，但必须执行供应商验签、
  时间戳/nonce 防重放、账户/环境解析、请求大小限制和稳定快速应答。
- 管理端：支付/退款查询与查单补偿、退款命令、物流报价/建单/取消/面单/轨迹同步、失败任务
  查询和受审重放。所有写入要求 `Idempotency-Key`、商城授权和审计原因。
- Checkout SDK 的客户端载荷是短期、最小化、不可跨商城复用的服务端响应；不得包含密钥或
  允许客户端改写金额/订单引用的自由字段。

### 7.3 预计权限

- 支付：`store.payments.read`、`store.payments.reconcile`、`store.refunds.create`、
  `store.refunds.read`。
- 物流：`store.shipments.read`、`store.shipments.create`、`store.shipments.cancel`、
  `store.shipments.label.read`、`store.shipments.reconcile`。
- 渠道配置和失败任务重放属于更高风险权限，与普通订单查询分离；超级管理员跨商城操作仍需
  显式目标商城、原因和审计。
- 退款、密钥轮换、人工确认已揽收/签收和死信重放必须二次确认；是否要求 MFA freshness 在
  M5.1 权限矩阵中冻结。

## 8. 迁移、兼容与回滚

- M5 采用仅新增的向前迁移；已有 COD 订单、M4 API 和状态语义保持兼容，渠道默认关闭。
- 先部署 schema/读兼容代码，再启用 worker，最后按单商城开启支付/物流渠道；任一阶段可通过
  商城配置停止新建外部单，但不能停止处理已有支付、退款、回调和运单至终态。
- 迁移需兼容 fresh database 和已有 M2/M3/M4 事实数据库，不回填虚构支付或物流记录。
- `down.sql` 仅允许无 M5 业务事实的 local/test 环境。检测到支付尝试、回调、退款、运单、
  轨迹、outbox/inbox 或渠道密钥引用时以 SQLSTATE `55000` 拒绝；生产只允许向前修复。
- 应用回滚必须保留兼容 worker 处理旧版本 outbox 和供应商回调；事件 schema 带版本，消费者
  至少支持当前和上一部署版本。回滚不能删除或重写外部业务事实。

## 9. 外部依赖、风险与未决项

进入 M5.5 真实供应商联调和 M5.7 外部验收前至少需要：

1. 明确的支付供应商、官方沙箱文档版本、测试商户、签名/验签材料、回调 IP/证书策略、退款
   和对账能力、金额/订单号限制及测试卡/钱包。
2. 明确的物流供应商、测试账户、服务地区、仓库/退货地址、服务代码、重量尺寸规则、COD、
   面单格式、轨迹/回调、取消和对账能力。
3. 两个商城的 Zalo Mini App/Parent App 测试配置、Checkout SDK 资格、测试成员和 HTTPS 回调
   域名；凭据只通过批准的密钥渠道提供，不写入对话、文档或版本库。
4. 业务确认两个商城的支付方式开关、支付超时、退款审批限额、物流服务选择、固定运费降级
   策略、发货/完成时点，以及 COD 金额/地区/风险规则。
5. 财务确认部分退款、手续费、舍入、对账日界线和差异处置；本项目仍统一以整数 VND 记录
   业务金额，供应商若使用不同最小单位必须在适配器边界显式无损转换。

主要风险包括供应商测试/生产契约不一致、回调没有稳定事件 ID、支付成功与取消并发、迟到
成功、退款超额、物流乱序/重复、供应商限流、密钥轮换窗口、地址/手机号进入外部请求后的
隐私责任以及 Zalo 审核政策变化。每项必须通过契约测试、数据库唯一约束、状态锁、审计和
人工补偿共同控制，不能只靠前端或内存锁。

## 10. 测试与验收

- 单元：支付/退款/物流状态映射，未知状态拒绝，订单转换，整数 VND，可退款余额，回调时间
  窗口，签名规范化，退避和敏感字段脱敏。
- 契约：选定供应商成功、失败、超时、限流、无效 JSON/内容类型、超大响应、重复/乱序、未知

  面单授权、轨迹和异常重试；Chromium/WebKit 不能替代 Zalo 宿主真机。
- 外部验收：Zalo 测试版本、支付沙箱回调/查单/退款、物流测试单/面单/轨迹/取消，记录账户
