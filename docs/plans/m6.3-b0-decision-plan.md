## 1. 背景与停止条件

M6.3-A 最终复核后，M6.3-B 的冻结 OpenAPI、纯领域状态机、M6.2 数据库 guard 和既有 M5 退款运行时
之间仍存在不可同时满足的约束。根据 `AGENTS.md`，售后、退款、物流、库存和权限边界在计划明确前
不得直接编码或用绕过 trigger/RLS 的方式制造可用路径。

开始任何 B 写 API 前必须同时满足：

- M6.3-A 的生产依赖审计取得可审查结果，并完成其独立报告状态更新。
- 本计划的业务决策、切片顺序和迁移范围获得明确批准。
- 返件 transition、SYSTEM actor、退款协调和验收/库存边界不存在互相矛盾的契约。
- 涉及证据、COD 或供应商的功能具备真实适配入口；没有时保持失败关闭或不开放路由。

## 2. 目标与非目标

### 2.1 目标

- 冻结售后准入、逐行政策、金额、证据、返件、验收、退款和 COD 的唯一可执行语义。
- 修正 OpenAPI/domain/schema/RLS 之间的冲突，只通过前向迁移收口数据库边界。
- 建立窄权限 SYSTEM principal、事务内 M5 Refund 复用和可靠售后结果协调设计。
- 把 M6.3-B 拆成可独立回滚、测试和验收的只读、申请、审核、返件、退款与 COD 切片。

### 2.2 非目标

- 本切片不创建 controller/service/worker 或生产配置；仅允许本计划列明的前向数据库修复。
- 不决定越南卫生、开封、证据、退货运费或服装换码的生产政策内容。
- 不把 Web E2E、测试适配器或手工数据库写入当作支付、物流、扫描、COD 到账或 Zalo 真机证据。
- 不把售后状态并入 `orders.status`，不建立与 M5 平行的 ONLINE 退款账。

## 3. 已批准决策与冻结默认值

### 3.1 售后准入与交付时间

冻结语义：各售后类型的准入只使用服务端订单、支付和物流事实；多运单时每个订单行的权威
`delivered_at` 必须由 `shipment_items` 关联的 `ORDER_OUTBOUND` 运单证明。

推荐默认值：按 `shipment_items` 解析每个订单行已签收的 `ORDER_OUTBOUND` 运单；同一行存在冲突或
旧订单无法证明交付时间时进入 `legacy_policy_review`，不能用当前时间或订单更新时间推断。

### 3.2 多政策订单行

一次申请可含多行，而当前售后 header/响应只有一个 policy snapshot。

推荐默认值：P0 的单个售后单只接受解析到同一 policy/version/hash 的订单行；不同政策拆为多个售后单。
若业务要求一次聚合多政策，必须先扩展规范 payload/hash、响应和数据库 guard，不能任取第一行政策。

### 3.3 数量、金额与审核

冻结语义：允许逐行部分批准；客户端不得提交批准金额，商品金额由服务端按统一整数 VND 余数算法计算。

推荐默认值：扩展审核契约为逐行 `approved_quantity`，锁定订单行后按剩余可用数量/金额计算；覆盖全部
剩余数量时取得全部余数。创建与批准都使用同一安全整数 VND 算法，且批准额不得超过申请额和 M5
退款容量。运费权益独立、每订单最多一次。

### 3.4 原因与证据

冻结语义：reason code 必须来自冻结政策 allowlist，`evidence_required` 与 reason-code 条件均由服务端解析。

推荐默认值：先完成证据上传、magic bytes/大小/数量校验、恶意文件扫描、claim、短期授权读取和删除
补偿切片；在扫描能力可用前，要求证据的政策一律不允许创建售后，不能以未扫描对象或静态成功结果放行。

### 3.5 返件状态机

当前冲突：会员只能经 RLS/guard 追加 `CANCEL`，但冻结 API 又要求会员提交返件时追加
`START_RETURN`/`RETURN_SHIPPED`；返件初态 `SUBMITTED` 与 `RETURN_SHIPPED` 要求的权威
`IN_TRANSIT/DELIVERED` 事实也不一致。

推荐默认值：会员在排他截止点前提交返件时，同一事务创建并占用 `SUBMITTED` 返件记录、追加
`START_RETURN`，把聚合从 `APPROVED` 推进到 `RETURN_PENDING`；该命令不得追加
`RETURN_SHIPPED`，也不得把买家填写的承运商或运单号当作在途/签收事实。运输中与签收只能由可信
物流查询或受审管理员核验事实推进。B0 同步修正 domain/OpenAPI/RLS/event allowlist，并用前向迁移
替换冲突 guard；不得给会员直接写权威物流状态的权限。

### 3.6 验收与 M6.4 库存边界

当前 `inspect-return` 允许 `RESTOCK_SELLABLE` 并要求 exactly-once 库存动作同事务，但批准路线图把库存
恢复放在 M6.4。

推荐默认值：将完整 `inspect-return` 写路由整体移动到 M6.4；M6.3-B 只提供返件/待验收读取和物流事实。
如果要保留在 B，必须明确把最小库存恢复原语、并发容量 guard 和相应迁移纳入 B 的批准范围。

### 3.7 SYSTEM principal

返件到期与退款结果协调需要系统事件；当前 `StoreContext` 只有 member/admin，售后 transition guard 又
要求真实管理员 FK，现有 worker 固定 UUID 无法安全通过。

推荐默认值：新增明确的 `SYSTEM` transaction actor 与数据库 allowlist，只允许
`RETURN_EXPIRED`、`REFUND_SUCCEEDED`、`REFUND_FAILED`、`REFUND_CANCELLED`、
`REQUIRE_REVIEW`，以及从 `REFUNDED` 确定性收口到 `COMPLETED` 的 `COMPLETE`；禁止审核、
legacy 决定、COD 确认和其他人工动作。审计记录系统主体，不能冒用申请管理员。

### 3.8 ONLINE Refund 协调

当前 M5 `createRefundCommand` 自开事务，不能与售后 settlement/link/transition 原子提交；M5 状态变化也
没有可靠售后同步事件。`REVIEW_REQUIRED` 无出口，查询耗尽只 dead-letter，`CANCELLED` 运行时不可达。

推荐默认值：

1. 从 M5 提取 transaction-scoped refund 创建原语，旧 M5 API 保持兼容包装。
2. 售后事务原子写 settlement、M5 refund/transition/outbox、精确 link 和 `REFUND_REQUESTED`。
3. M5 状态变化同事务追加版本化售后同步 outbox；无条件注册的 coordinator 读取最新权威事实并收敛。
4. 在人工对账、查询耗尽和取消语义获批前，保持 `REVIEW_REQUIRED` 不可恢复，不开放虚假 resume 路径。

### 3.9 COD 到账证明

推荐默认值：保留“申请人与确认人不同、确认人近期 MFA”的双人控制，但在真实转账证明写入接口/适配器
存在前，settlement 只能为 `PENDING/REVIEW_REQUIRED`，不开放“已到账”成功按钮。

### 3.10 读取与公共契约

推荐同时冻结：

- 响应中的 `reason_detail` 允许 legacy/null；新申请请求仍按契约要求非空详情。
- 会员政策文案按 `preferredLocale -> vi` 回退；管理员显式 locale 或商城默认 `vi`。
- `c1_` 游标使用独立可轮换 HMAC key，绑定版本、商城、主体、过滤条件、排序键和过期时间；篡改稳定 400。
- 售后公开号使用至少 128-bit 随机大写 base32/hex，并收紧为 `^ASC-[A-Z0-9]{16,32}$`。
- HTTP 安全 correlation ID 必须贯穿事务、transition、audit、日志和错误响应。
- 售后限流使用 60 秒窗口并绑定商城与主体：会员读 60 次、会员写 10 次、管理员读 120 次、管理员写
  30 次；超限返回不泄露资源存在性的安全 `429`。售后冲突码进入公开错误 allowlist。

## 4. 推荐实施切片

1. **B0 契约与前向修复**：批准上述决策，更新 domain/contracts/OpenAPI、数据字典、权限矩阵、架构；
   新增前向迁移与受限 local/test `down.sql`，完成 M2-to-current、fresh、重复 deploy、down-forward 和
   SQLSTATE `55000` 演练。
2. **B1 只读运行时**：会员/管理员列表与详情、响应 projector、签名游标、locale、脱敏、限流、
   correlation ID；先不开放写路由。
3. **B2 政策控制面与证据能力**：政策草稿/发布/停用/历史；证据上传、扫描、claim、授权读取与删除补偿。
4. **B3 申请与取消**：会员申请/取消、商家主动创建，含资格、窗口、逐行容量、幂等和审计。
5. **B4 审核、legacy 决定与到期 worker**：初审、一次性 legacy 决定和 SYSTEM 到期竞争。
6. **B5 返件可信事实与待验收读取**：不开放验收写路径；完整验收与库存恢复在 M6.4 整体实现。
7. **B6 ONLINE 退款**：M5 事务原语重构、原子请求、版本化同步和不确定结果收口。
8. **B7 COD 双人结算**：真实证明来源、异人确认、近期 MFA 和对账状态。

每个切片必须独立更新计划状态和报告；前一切片完成不自动授权后一切片。

## 6. 兼容、迁移与回滚

- 只新增前向迁移；生产及已有售后事实环境不执行 down。
- local/test `down.sql` 必须在存在新 actor、transition、settlement、证据或运行时事实时以 `55000` 拒绝。
- B1 只读应用可回滚而不删数据；写入口上线后只能关闭新申请并继续处理已有 outbox/settlement 至终态。
- M5 transaction-scoped 重构不得改变既有退款 API、幂等 key、容量、provider 或订单支付投影。
- 新旧 outbox 至少支持当前和上一 event version；协调事件只携带身份，不信任 payload 状态/金额。

## 7. 测试与验收

- 单元：状态转换、逐行金额余数、政策聚合、签名游标、公开号、locale 和错误映射。
- 数据库：RLS/复合 FK、SYSTEM event allowlist、返件/到期竞争、数量/金额容量、M5/M6 锁序与 settlement 链接。
- API：双商城、跨会员 404、RBAC/MFA、AccessReason、严格 DTO、同键异参、限流、脱敏和 correlation ID。
- worker：乱序/重复消息、提交后崩溃、lease 丢失、重试耗尽、provider disabled 下纯协调仍可收敛。
- 迁移：M2-to-current、fresh、重复 deploy、down-forward、fingerprint 和事实存在时 `55000`。
- 阶段门禁：定向与完整 integration、`corepack pnpm verify`、相关 E2E、生产依赖审计、Gitleaks、
  `git diff --check` 和独立高风险差异审查。
