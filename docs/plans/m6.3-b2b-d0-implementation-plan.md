## 1. 授权、结论与切片边界

用户于 2026-07-29 再次要求读取总需求和仓库规则并按严谨工作流继续下一阶段。B2a 完成后的
下一阶段是 B2b，但完整 B2b 同时依赖独立对象存储权限边界、真实恶意文件 scanner、受保护短期读取、
生产保留政策和外部运行证据，当前不能安全地一次交付。因此本轮只授权 **B2b-D0**：建立可审查的
数据库生命周期、窄 SYSTEM 身份、规范对象 ledger、会员配额并发控制和可靠 outbox/reconciliation
底座。

D0 明确不做以下动作：

- 不注册或启用任何凭证 HTTP 路由；既有 OpenAPI 继续标记为 contract-only。
- 不连接对象存储，不签发上传/下载 URL，不复用 catalog/content bucket、凭据或 provider token。
- 不提供 scanner adapter，不调用 scanner，不使用永远返回 `CLEAN` 的 mock 冒充生产能力。
- 不注册 scan/expire/delete worker，不发送外部告警，不处理真实用户文件。
- 不启用生产配置、生产政策、售后 evidence capability、部署、推送或发布。
- 不授权 B3-B7、M6.4、UI 或生产 rollout。

D0 完成后，`uploadValidationAvailable/malwareScanningAvailable/claimAvailable/protectedReadAvailable/
deletionCompensationAvailable` 仍不得因“表、原语或测试已存在”而变成可用。完整 B2b 的任一外部能力
不可用时，未来要求凭证的 B3 申请继续稳定失败关闭且不得创建售后单。

## 2. 目标与非目标

### 2.1 目标

- 在 `after_sale_evidence_files` 上补齐上传截止、确认、扫描请求/完成、扫描 generation、scanner 结果
  来源、普通访问截止和删除重试耗尽元数据，并由数据库约束保护字段组合。
- 新建规范 `after_sale_evidence_objects` ledger，逐个记录原件、衍生物和扫描临时对象；对象 key 只存在
  于受商城隔离保护的数据库事实和未来专用 provider，不进入队列、普通响应、日志或错误。
- 新增独立 `after-sale-evidence-lifecycle` SYSTEM scope 和稳定 SYSTEM actor；它与
  `after-sale-transition`、管理员和会员身份互不替代。
- 冻结会员未认领配额的并发锁与计算口径，防止两个并发事务同时越过数量或字节上限。
- 确认元数据与 scan outbox 在同一数据库事务提交；提交后崩溃仍可派发，事务失败不留下已确认但
  未排队的对象。
- 冻结 scan/expire/delete 的最小消息、expected-version/generation 竞争语义、有界删除退避、
  dead-letter 安全终态和 reconciliation 入口。
- 为下一切片的真实存储、scanner、保护读取和 worker 提供窄的 transaction-scoped 数据库原语，
  但本切片本身不宣称这些能力可用。

### 2.2 非目标

- 不新增或修改面向会员/管理员的请求、响应、错误码或路由；owner-scoped 状态 GET 和受保护读取仍
  属于后续 B2b 切片。
- 不实现真实 MIME/magic/checksum 对象读取校验。D0 只保存并约束未来由专用存储适配器验证后的
  元数据；数据库测试输入不能作为真实文件验证证据。
- 不实现 B3 售后创建或把 claim 接入售后事务。D0 仅保留/收紧 claim、访问和保留字段的不变量，
  后续 B3 仍须使用同商城、同会员、锁行且一次性的 transaction-scoped claim 原语。
- 不提供 legal hold 管理入口，不改变 hold 的治理授权。hold 只阻止物理删除，不延长普通访问期限。
- 不迁移、读取或删除任何真实对象，不把 local/test fixture、Web E2E 或手工 SQL 当作外部能力证明。

## 3. 生命周期参数与生产停止条件

以下值只冻结为 **local/test 建议值和自动化验收基线**：

| 参数             |              local/test 建议值 | 冻结语义                                                   |
| ---------------- | -----------------------------: | ---------------------------------------------------------- |
| 未确认上传窗口   |                        15 分钟 | `upload_deadline_at` 为排他截止点；到点后不能确认          |
| CLEAN 后认领窗口 |                        24 小时 | `claim_deadline_at` 为排他截止点；到点后不能 claim         |
| 普通读取窗口     |                          30 天 | claim 后写入 `ordinary_access_deadline_at`；到点统一不可读 |
| 物理保留窗口     |                          90 天 | claim 后写入 `retention_deadline_at`；hold 只推迟删除执行  |
| 每会员未认领数量 |                          12 个 | 同商城同会员、未 claim 且尚未 `DELETED` 的事实均计入       |
| 每会员未认领字节 |                        200 MiB | 按服务端接受的声明 `byte_size` 求和，不能依赖客户端余额    |
| 删除最大尝试     |                           8 次 | 第 8 次失败进入耗尽事实，不再自动生成无界重试              |
| 删除退避         | 60 秒起，指数增长，最多 6 小时 | 使用有界、可测试的服务端时间；队列消息不携带截止点         |
| 删除告警阈值     |                    第 5 次失败 | 写持久 transition/可观测告警条件；D0 不冒充外部告警已送达  |

这些值不是越南法律结论，也不得作为 production 隐式默认值。生产启用前，upload/claim/access/
retention、配额、删除重试和告警参数必须由越南业务、隐私/DPO 与合规人员批准，并在每个环境显式
配置；缺项、非法组合或未留审批证据时能力检查必须失败关闭。特别是
`ordinary_access_deadline_at < retention_deadline_at`，legal hold 不得重写任一原始截止点。

D0 数据库原语接收服务端已验证的绝对时间/策略值，测试显式传入上表值；仓库不得在生产代码中用
上述值兜底。未确认 `PENDING` 使用 upload 截止点，`READY_UNCLAIMED` 使用 claim 截止点，已 claim
`READY` 使用 retention 截止点。`FAILED/QUARANTINED` 的清理截止值必须由后续获批策略显式提供，
D0 不自行推断生产保留期。

## 4. 数据模型与权限冻结

### 4.1 `after_sale_evidence_files` 生命周期元数据

在保留 M6.2 内部状态和既有归属字段的基础上新增：

- `upload_deadline_at`、`confirmed_at`。
- `scan_requested_at`、`scan_completed_at`、正向递增的 `scan_generation`。
- `scanner_engine`、`scanner_engine_version`、`scanner_signature_version`；只有未来真实 scanner 的
  规范结果可以填写，D0 不制造生产值。
- `ordinary_access_deadline_at`，与 `retention_deadline_at` 分离。
- `delete_exhausted_at`；未耗尽时必须为空，耗尽后不得再写下一自动删除时间。

关键形状固定为：

- 初始化只能是无 `after_sale_id` 的 `PENDING`、`scan_generation=0`、未确认、无扫描结果、无访问/
  retention/删除耗尽事实，并带未来的上传截止点。
- 确认只能在上传截止前、精确 expected version、同商城同会员和原件 ledger 元数据一致时发生；同一
  generation 的重放幂等，异参或过期确认拒绝。
- 每次请求重新扫描必须先递增 generation，再可靠排队；旧 generation、旧 expected version 或乱序
  结果不得覆盖当前事实。
- 只有真实规范结果的精确 `CLEAN` 可以进入 `READY_UNCLAIMED`；恶意进入 `QUARANTINED`，超时、
  provider 不可用、无法判断或非 allowlist 结果进入 `FAILED`，均不得投影为公开 READY。
- claim 后才允许同时写 `claimed_at`、`ordinary_access_deadline_at` 和 `retention_deadline_at`；访问到期
  不改变 legal hold，也不能因对象仍保留而继续读取。
- `DELETED` 只在 ledger 中所有对象均有删除事实后成立；只有此时可清空兼容 key 投影。数据库中的
  checksum、大小、转换、截止点、尝试次数和删除时间继续保留并受 RLS 保护。

### 4.2 规范对象 ledger

`after_sale_evidence_objects` 是 D0 起的新写路径权威对象清单：

- 每行必须有 `store_id/evidence_file_id/object_role/object_key/object_key_hash/version`；角色只允许
  `ORIGINAL/DERIVATIVE/SCAN_TEMPORARY`。
- 原件每个 evidence 最多一个；活动扫描临时对象每个 evidence 最多一个；衍生物逐行记录，不再把
  任意 JSON 数组作为删除完成依据。
- key 由服务端产生，固定匹配
  `{environment}/{store_id}/staged/{evidence_id}/original` 或后续受控衍生命名空间；客户端不能提交、
  拼接或覆盖 key。`object_key_hash` 必须等于 key 的 SHA-256，用于不暴露 key 的一致性校验。
- 删除逐对象幂等记录：未删除时 key 非空且 `deleted_at` 为空；删除成功或供应商确认对象不存在后，
  清空 key、保留 hash 并写 `deleted_at`。不得仅凭队列成功或父行状态清空 key。
- ledger 使用复合外键、唯一索引、FORCE RLS 和商城维度索引。会员只能在初始化原件的受限路径写入；
  衍生物、扫描临时对象和所有删除事实只允许 evidence SYSTEM scope。普通会员/管理员 API 不直接读取
  ledger。

M6.2 的 `object_key/derivative_object_keys/scan_temporary_object_key` 暂保留为兼容投影，不再允许成为
新原语判断“应删除哪些对象”的唯一来源。后续删除这些列前必须先证明所有调用方已切换到 ledger，
本轮不做破坏性删列。

### 4.3 SYSTEM scope、RLS 与 transition

- 事务上下文必须同时设置 `actor_type=system`、
  `system_scope=after-sale-evidence-lifecycle`、当前 `store_id`、稳定 evidence SYSTEM actor 和
  `correlation_id`。普通 `withStoreTransaction`、`after-sale-transition` scope 或管理员 UUID 均不能
  写入 SYSTEM 生命周期事实。
- evidence SYSTEM actor 是专用 `AuditActorType.SYSTEM` 身份，不引用或冒用 `admin_users`。
- SYSTEM allowlist 只包含扫描请求/结果、到期、删除重试/成功/失败/耗尽和 reconciliation 所需的
  生命周期事件；不得 claim、设置/解除 legal hold、审核售后、修改归属或执行其他人工动作。
- `after_sale_evidence_transitions` 保持 append-only，补齐 correlation ID，并记录精确 from/to 状态、
  event、actor、稳定错误类别和 generation/version 关联。运行角色不得直接 INSERT/UPDATE/DELETE
  transition，也不得直接更新宽生命周期列绕过 guard。
- 所有查询、quota 锁、outbox、ledger、transition 和 reconciliation 都显式绑定 `store_id`；已知其他
  商城 UUID 不能用于探测或更新本商城事实。

## 5. 事务、队列与竞争语义

### 5.1 会员配额并发锁

初始化上传前先取得 `(store_id, member_id)` 的 transaction-scoped quota lock，再计算同商城同会员且
`after_sale_id IS NULL`、尚未 `DELETED` 的数量和 `byte_size` 合计。锁必须先于 evidence 行锁取得；
批量 evidence 行按 UUID 稳定顺序锁定。超限事务不创建 evidence、ledger 或 outbox。

`PENDING/READY_UNCLAIMED/FAILED/QUARANTINED/DELETION_PENDING/DELETE_FAILED` 即使已过业务截止点，
在物理删除完成或成功 claim 前仍占未认领配额，避免通过制造待清理对象绕过容量。claim 与最终删除
必须在同一 quota lock 下释放占用；reconciliation 可重新按权威行聚合校验，不能相信缓存计数。

并发验收要求在 `11 -> 12` 个、接近 `200 MiB` 的边界同时发起两个事务，最多一个成功；商城或会员
不同的锁不互相共享配额。

### 5.2 确认与 scan outbox 原子性

确认事务固定执行：quota lock → evidence 行锁 → ORIGINAL ledger 行锁 → 校验 owner/store/上传截止/
expected version/声明 MIME、长度、SHA-256 与未来 provider 已验证元数据 → 写 `confirmed_at`、
`scan_requested_at`、递增 `scan_generation` 和 evidence version → 追加 transition → 插入 scan outbox。
任一步失败整笔回滚。

outbox 冻结如下：

- `aggregate_type = AFTER_SALE_EVIDENCE`，`aggregate_id = evidence_id`，`event_version = 1`。
- event type 只使用 `after-sale.evidence.scan.requested`、
  `after-sale.evidence.expire.requested`、`after-sale.evidence.delete.requested`。
- 三类 payload 必须 **精确** 为 `store_id/evidence_id/expected_version`；禁止额外携带 status、对象 key/
  hash、MIME、checksum、扫描结论、generation、截止点、legal hold、错误正文或供应商数据。
- idempotency identity 绑定商城、evidence、event type 和权威 generation/version；同身份异 payload
  冲突，重复确认不能生成第二条同 generation 扫描任务。
- worker 未来只能把消息当作定位提示；处理前必须按 store/evidence 锁定数据库并重新读取 generation、
  状态、ledger、截止点和 hold。消息中的 expected version 不匹配时不得强行更新。

初始化与每次权威截止点变化必须在同一事务安排相应 expire 身份；进入 `DELETION_PENDING` 时同事务
安排 delete 身份。旧版本消息到达时安全完成为 superseded/no-op，由权威状态决定是否需要当前版本任务，
不得让旧消息把新状态倒退。

### 5.3 扫描 generation 与结果投影

D0 只提供“接受未来受信 scanner 规范结果”的数据库边界，不提供结果来源。未来 worker 在网络事务前
锁行并读取 current generation/version，在网络事务外扫描，再用相同 generation 和新的 expected version
提交结果。期间发生重扫、到期、claim、hold 或其他版本变化时，旧结果返回稳定 stale/no-op，不能放行。

scanner 超时、不可用、恶意或不确定均失败关闭。只有同时匹配 generation、对象 ledger、声明元数据、
magic/checksum 验证和精确 `CLEAN` 的结果可以写 READY；D0 的单元/集成测试直接调用结果投影原语，
只证明状态竞争语义，不能列为 scanner 验收证据。

### 5.4 删除退避、耗尽与 reconciliation

- expire/delete 每次外部对象操作前后都必须重锁 evidence 与 ledger，并重新检查 expected version、
  当前截止点和 legal hold。hold 在排队后激活同样阻止删除提交；解除 hold 不修改原截止点，reconciler
  对已到期事实重新排队。
- 删除按 ledger 的稳定顺序处理全部活动对象。供应商“已不存在”与本次删除成功同样可形成幂等删除
  事实；超时/未知不得当作成功。
- 删除失败递增父行 `delete_attempt_count`，按 60 秒起、最多 6 小时的指数退避写
  `next_delete_attempt_at`。第 5 次形成持久告警条件；第 8 次写 `delete_exhausted_at`、清空下一自动尝试
  时间并保持 `DELETE_FAILED`，对象 key 仍受保护保留。
- outbox lease 丢失的旧 worker 不能提交状态或对象删除事实。进程在数据库提交后崩溃由 outbox 重领；
  在外部删除后、数据库提交前崩溃时，下一次以 provider not-found 幂等收敛。
- reconciliation 只读/锁定权威数据库和 DEAD_LETTER outbox：scan dead-letter 必须把仍待扫描对象收敛
  为不可 READY 的安全失败并安排清理；expire dead-letter 仍按数据库截止点让普通访问失败，并在无 hold
  时重新形成当前版本删除任务；delete dead-letter 进入 `DELETE_FAILED`，达到上限写 exhausted 事实。
  不允许通过通用管理员 replay 绕过 generation、截止点或 scope。
- reconciliation 自身必须幂等、商城隔离并写 SYSTEM transition/correlation；它不能把 DEAD_LETTER
  直接标成业务成功，也不能删除审计事实。

## 7. 迁移、兼容与回滚

- D0 使用单独前向迁移，不重写政策、售后、支付、物流、库存或历史订单事实。由于 B2b 路由从未启用，
  迁移在 evidence files/transitions 或 `after-sale.evidence.*` outbox 已有事实时以 SQLSTATE `55000`
  失败；不得猜测真实对象的确认时间、扫描 generation、访问期限或 ledger 内容。
- 任一 staging/production 目标库必须先运行只读 preflight，归档 evidence/transition/outbox 计数和不兼容
  摘要。非空时停止 rollout，制定受审前向修复；本地空库结果不能替代目标库证据。
- Prisma schema 与迁移保持枚举、列、索引、RLS、函数和 grant 一致。旧 key 列暂保留兼容；D0 新原语
  以 ledger 为权威，不允许出现父行 `DELETED` 而 ledger 仍有活动 key 的半状态。
- 应用回滚不会注销外部路由或 worker，因为 D0 未注册这些入口。若数据库中已存在 D0 runtime 事实，
  必须保留兼容原语/reconciler 直到安全终态，不能靠回滚删除对象、outbox、transition 或审计。
- `down.sql` 只允许无真实业务数据的 local/test 人工执行，并在 D0 evidence/ledger/transition/outbox/
  reconciliation 事实存在时以 `55000` 拒绝；通过后只删除本迁移精确新增对象并恢复 M6.2 约束、索引
  和 grant。生产及任何已有凭证事实环境只允许向前修复。
- 迁移必须进入 M2→current、fresh、重复 deploy、down→forward、fingerprint 与事实门禁演练；重复部署
  不得重复枚举、policy、trigger、索引或函数。

## 8. 风险、依赖与未决事项

- 最大风险是把数据库排队误认为真实文件能力。防护是无 HTTP/worker/provider、capability 继续 false、
  OpenAPI 继续 contract-only，并在报告中把外部验收标为 `NOT_RUN/BLOCKED`。
- 现有 M6.2 宽 UPDATE/grant、管理员身份投影和 JSON key 可能允许绕过新 ledger。D0 必须用窄
  SYSTEM scope、列权限、RLS 和 trigger 收口；若无法证明旧写法都被阻止，停止交付。
- 配额查询与 claim/删除释放若锁序不一致会导致超限或死锁。所有入口固定先 quota lock，再按稳定顺序
  锁 evidence/ledger/outbox；并发测试必须覆盖边界。
- 延迟、重复、乱序、lease 丢失和扫描 generation 竞争可能让旧任务覆盖新事实。所有 mutation 绑定
  store、expected version、current generation 和权威状态；stale 只能 no-op/reconcile。
- object key、checksum、scanner 细节和删除错误属于敏感安全数据。它们不能进入消息、公开状态、普通
  审计 before/after、日志或错误；测试需用 marker 验证无泄漏。
- 通用 outbox 管理重放当前不具备 evidence 专属权限/语义，D0 不开放管理员 replay。未来人工恢复必须
  单独设计近期 MFA、专权、reason、generation 复核和完整审计。
- 生产 retention、隔离恶意对象的保留期、告警接收方和真实供应商 SLA 尚未批准；D0 不为这些问题
  写隐式结论。

完整 B2b 仍受以下独立门禁阻塞：专用 evidence bucket/prefix、catalog/content 完全不可访问的最小
upload/read/delete IAM、生产 KMS 与 lifecycle；真实 scanner 及超时/恶意/不确定语义；受保护短期
URL、每次管理员读取审计；获批的生产 TTL/配额/删除/告警配置；以及真实 provider 下的提交后崩溃、
重复、乱序、lease 丢失和重试耗尽证据。

## 9. 测试与验收矩阵

### 9.1 单元与静态契约

- evidence SYSTEM context 固定 scope/actor、不可变且拒绝空 store/correlation；不能传给普通售后
  SYSTEM allowlist。
- TTL/配额/退避策略输入拒绝负数、溢出、access 不早于 retention、max attempts 与告警阈值冲突。
- 三类消息序列化后键集合精确等于 `store_id/evidence_id/expected_version`，敏感 marker 不出现。
- scan generation、错误类别、第五次告警和第八次耗尽的纯计算覆盖边界。

### 9.2 数据库与并发集成

- 双商城/跨会员已知 UUID、错误 scope/actor、管理员冒充 SYSTEM、SYSTEM 越 allowlist、直接 transition
  或宽列 UPDATE 均被 RLS/trigger/列权限拒绝。
- 初始化形状、对象 key 路径/商城/evidence 绑定、hash、单 ORIGINAL、活动 SCAN_TEMPORARY 唯一、
  ledger 与父行复合 FK/删除完整性。
- 12 个/200 MiB 配额边界和两个并发事务；失败事务不留下 evidence/ledger/outbox。
- 确认与 scan outbox 原子提交；提交后崩溃可见 PENDING message，模拟 outbox 失败时 confirmed/
  generation/version 全部回滚；同 generation 重放与异参冲突。
- CLEAN、恶意、超时、不可用、不确定、重复和乱序结果；旧 generation/expected version 不能成为 READY。
- upload/claim/access/retention 排他截止，hold 不延长读取且阻止删除；解除后 reconciliation 重排。
- 原件/衍生物/扫描临时对象全部删除后才能 DELETED；外部成功后数据库崩溃以 not-found 重试收敛。
- 删除 60 秒→6 小时退避、第 5 次告警、第 8 次 exhausted 与 DEAD_LETTER 三类数据库安全收口。
  真实 worker lease 丢失、provider 操作后数据库崩溃和外部告警仍属于后续切片的阻塞验收，D0 未宣称通过。

### 9.3 迁移与全仓门禁

- M2→current、fresh、重复 deploy、down→forward、fingerprint 通过；非空 evidence/transition/outbox
  preflight 和 `down.sql` 事实门禁稳定返回 `55000`。
- 运行定向 unit/integration、完整 `corepack pnpm test:integration`、`corepack pnpm verify`、
  `corepack pnpm audit --prod --audit-level high`、OpenAPI 结构回归、交付候选 Gitleaks、
  `git diff --check` 和独立高风险差异复审。
- D0 无 UI、真实对象、scanner、provider 或 Zalo 宿主，专项浏览器 E2E 为 `NOT_APPLICABLE`；对象存储、
  scanner、保护 URL、外部告警与生产配置验收必须记录为 `NOT_RUN/BLOCKED`，不能宣称通过。

## 10. 完成定义与后续授权

D0 只有在目标 schema/迁移/原语/测试与文档全部完成、适用门禁通过、差异复审未发现商城泄漏、宽
SYSTEM 权限、消息敏感数据、无界删除或虚假 scanner 路径时，才可单独标记仓库实施 `COMPLETE`。

D0 `COMPLETE` 仍只表示“数据库生命周期与可靠排队底座完成”。它不等于 B2b、B2、M6.3、M6 或 P0
完成，也不授权下一个切片。后续至少需要另行计划并批准：

1. 专用 evidence 存储配置、bucket/IAM/KMS/lifecycle 与真实上传校验。
2. 真实 scanner adapter、隔离语义和 worker 运行证据。
3. owner 状态读取、B3 transaction-scoped claim、受保护 URL 和管理员专权审计。
4. 过期/删除 worker、外部告警、生产参数审批与逐环境 rollout。
