# M6.3-B1 售后只读运行时实施计划

> 状态：`COMPLETE`；B1 四个只读接口已完成并通过适用门禁
> 日期：2026-07-28；完成于 2026-07-29
> 授权边界：仅 B1 四个只读接口；不授权 B2-B7、生产政策启用、供应商调用、部署、推送或发布

## 1. 目标与非目标

### 1.1 目标

- 实现 `GET /v1/after-sales` 与 `GET /v1/after-sales/{afterSaleId}`，会员只能读取当前
  `X-Store-Code` 下本人的售后数据。
- 实现 `GET /v1/admin/after-sales` 与 `GET /v1/admin/after-sales/{afterSaleId}`，管理员必须具备
  `store.after-sales.read`，且 Header 商城、`store_id` 与授权商城一致；平台管理员跨商城时还必须提供
  受审的 `X-Access-Reason`。
- 交付严格响应 projector、三语政策文案回退、敏感字段脱敏、`c1_` HMAC 签名游标、60 秒读限流及
  `X-Correlation-Id` 贯穿。
- 以真实 runtime 数据库角色和 Redis 覆盖跨商城、跨会员、RBAC、游标 scope、脱敏与限流。

### 1.2 非目标

- 不开放申请、取消、审核、返件提交、验收、退款、COD、证据上传/下载或任何其他写路由。
- 不实现政策草稿/发布/停用、证据扫描/claim/清理、worker、供应商适配器或 UI。
- 不改变售后、退款、库存、物流或验收状态机；完整验收和 exactly-once 库存恢复仍属于 M6.4。
- 不启用任何商城的政策 enforcement，不创建生产政策或第三方凭据。

## 2. 冻结接口与行为

### 2.1 查询和排序

- 会员列表严格接受 `cursor/limit/type/status`，固定按 `created_at DESC, id DESC` 排序，并在 SQL 条件中
  同时包含 `store_id/member_id`。
- 管理员列表严格接受 `store_id/cursor/limit/locale/order_id/member_id/type/status`，固定按
  `updated_at DESC, id DESC` 排序，并在 SQL 条件中显式包含 `store_id`。
- 两类列表均读取 `limit + 1` 行判断是否存在下一页；下一游标绑定最后一条已返回记录，避免恰好一页时
  产生无意义空页。
- `created_at/updated_at` 是 PostgreSQL `timestamptz(6)`；keyset 位置由数据库返回六位微秒 UTC 字符串，
  下一页在 SQL 中以 `(timestamp, id)` 行值比较。禁止先转成仅毫秒精度的 JavaScript `Date` 再回灌 seek，
  以免同一毫秒内记录重复或丢失。
- 会员详情显式按 `store_id/member_id/id` 查询；跨会员、跨商城和不存在统一 `404`。管理员详情显式按
  `store_id/id` 查询，无权商城先由中央授权拒绝为 `403`。

### 2.2 locale 与历史政策

- 会员按认证会员 `preferredLocale -> vi` 选择不可变政策版本文案。
- 管理员按显式 `locale -> 商城 default_locale -> vi` 选择文案。
- 非 legacy 售后从绑定的不可变政策版本/本地化事实读取 `policy_code/version/name/summary/
buyer_instructions`；缺少目标语言时只回退越南语，不读取当前活动政策替代历史事实。
- 非 legacy 售后若缺少绑定的不可变政策、版本或越南语本地化事实，projector 必须失败关闭；不得返回
  `null`，也不得读取当前活动政策伪造历史文案。
- legacy 售后返回 `legacy_policy_review=true`，政策标识、版本、locale 和文案均为 `null`。

### 2.3 安全响应投影

- 仅返回 OpenAPI `AfterSale` allowlist；解密后的 `reason_detail` 允许历史 `null`，不返回 ciphertext、
  `review_reason`、管理员原因/ID、幂等 hash、policy hash、供应商原始 payload 或内部资金引用。
- evidence 仅投影 `PENDING/READY/UNAVAILABLE`。`READY_UNCLAIMED` 使用未过期
  `claim_deadline_at`，`READY` 使用未过期 `retention_deadline_at`；其余内部扫描、隔离、删除状态及所有
  已过期对象统一 `UNAVAILABLE` 且 `access_expires_at=null`。
- 返件只返回 `carrier_name/masked_tracking_number/status/submitted_at`，不返回 tracking digest 或提交人。
- settlement 只返回公开号、方式、公开状态、整数 VND、公开退款号及时间；不返回内部 ID、申请/确认人、
  transfer digest、加密凭证或 provider 原始响应。
- timeline 只返回公开 `event/status/created_at`，不返回内部 reason、actor 或 correlation。
- 数据库详情查询同样使用显式 `select` allowlist，只取 projector 必需列；不使用会把 evidence 对象 key/
  scan、settlement 转账密文、timeline actor/reason 或 header 内部 hash 读入进程的宽关系 `include`。
- 四个成功响应统一返回 `Cache-Control: private, no-store`，避免带原因详情的会员/管理员数据被共享缓存。

### 2.4 游标、限流与 correlation

- 游标保持 `c1_` 语法，payload 使用紧凑且严格的版本化结构，签名使用 HMAC-SHA-256。
- 新增独立 `AFTER_SALE_CURSOR_HMAC_KEYS`，值为逗号分隔的 1-3 把唯一 base64url 密钥；每把密钥解码后
  至少 32 字节。第一把密钥始终用于签发，key ring 中全部密钥均用于验证。轮换时先把新密钥放到首位并
  保留仍可能验证有效游标的旧密钥，待最长 TTL 后再移除已退役密钥；key ring 始终不得超过 3 把。
- 游标绑定版本、`store_id`、subject type/id、resource、规范筛选 hash、排序时间、tie-breaker UUID 和
  `expires_at`。签名失败、过期、错主体/商城/resource/筛选均统一 `400 INPUT_INVALID`。
- 游标默认 TTL 为 15 分钟，可通过 `AFTER_SALE_CURSOR_TTL_SECONDS` 在 60-3600 秒范围调整；不接受客户端
  指定过期时间。
- Redis 限流固定 60 秒：会员读 60 次，scope=`store_id:member_id`；管理员读 120 次，
  scope=`store_id:admin_id`。超限返回安全 `429` 与 `Retry-After`，不查询目标资源；Redis/限流器不可用时
  失败关闭并返回通用 `503 UPSTREAM_UNAVAILABLE`，不复用证据能力专用的 `503` 语义，也不承诺
  `Retry-After`。
- controller 使用 HTTP 中间件生成/校验后的 request ID；售后读取事务、授权审计（如发生）、成功 Header、
  错误体和日志使用同一个安全 correlation ID。四个 GET 均接受可选 `X-Correlation-Id`；不安全值不传播，
  响应 Header 中的服务端最终值为准。

## 4. 数据模型、迁移与兼容

- 复用 M6.2/B0 的 `after_sales` 及子表、复合 FK 和 FORCE RLS；不增加或改写业务列。
- 会员索引已覆盖 `(store_id, member_id, created_at DESC, id DESC)`；管理员按 status 过滤时复用
  `(store_id, status, updated_at, id)`。管理员 status 可选，因此 B1 新增
  `(store_id, updated_at DESC, id DESC)`，保证无 status 的最近更新列表无需扫描后全量排序。
- Prisma schema 当前漏记数据库在 M6.2 已有的 `UNIQUE (store_id, settlement_id)`；B1 只补
  `@@unique([storeId, settlementId])` 消除 schema drift，既有数据库索引不重复迁移。
- 新响应 schema 是既有冻结 OpenAPI 的实现，不更改业务状态或金额语义。OpenAPI 为四个 GET 补齐严格
  输入 `400`，并将 runtime 状态更新为 B1 已实现；其余路由继续明确 contract-only。
- 新环境变量只涉及应用启动配置；本地/测试有独立占位值，生产占位值会被配置校验拒绝。

## 5. 回滚方案

- B1 没有业务数据写入。回滚应用版本并移除四个 controller 注册即可停止读取运行时，不删除任何售后
  事实；新增管理员读取索引可保留，也可在确认无 B1 流量后执行受审 `down.sql` 只删除该索引。
- 密钥轮换回滚时，把原主密钥恢复到 key ring 首位，并在游标 TTL 内保留所有仍可能签发过有效游标的
  密钥；不得在仍有有效游标时移除其验证密钥，否则客户端会收到稳定 `400` 并需从第一页重试。
- 限流器仅保存短 TTL Redis 计数，不是业务事实；回滚无需数据迁移。

## 6. 风险、未决项与外部依赖

- **高：跨商城/跨会员泄漏。** 使用中央 RBAC、显式 `store_id/member_id` 条件、FORCE RLS 和真实 runtime
  角色负向测试共同防护；不得只依赖前端 Header 或 RLS 单层。
- **高：敏感字段过度投影。** projector 采用新对象 allowlist 并用严格 response schema 复验；测试在
  原始记录写入 marker 后断言响应序列化结果不含 marker。
- **中：游标被篡改或跨 scope 重放。** HMAC、过期、全部 scope 字段和规范筛选 hash 一并验证；所有失败
  走同一 400，不区分原因。
- **中：密钥轮换导致分页中断。** 使用 1-3 把 key ring，第一把签发、全部验证，并把 TTL 限制在一小时
  内；运维必须按“新密钥置首、保留旧密钥、等 TTL、再移除退役密钥”执行。
- **中：列表携带完整详情造成负载。** 遵守已冻结 `AfterSalePage.items=AfterSale[]` 契约，限制单页最多
  100，使用关系批量读取、`limit + 1` 和主体限流；后续若需 summary 契约必须另行变更，不在 B1 偷改。
- **中：时间精度造成 keyset 重复/漏读。** cursor 保存数据库六位微秒排序键，SQL 原生比较；以同一毫秒
  多行的两页遍历回归测试冻结。
- **中：Redis 不可用。** B1 不允许静默绕过限流；故障在查询目标资源前失败关闭为
  `503 UPSTREAM_UNAVAILABLE`，不携带 `Retry-After` 契约，并由现有基础设施健康检查/告警处理。
- **低：历史非规范政策快照。** 仅从绑定的不可变版本本地化读取文案；非 legacy 售后缺少绑定政策、
  版本或越南语本地化事实时失败关闭，不返回 `null`，并由测试冻结不得读取当前活动政策伪造历史文案。
- 外部依赖仅为现有 PostgreSQL、Redis 和认证/RBAC 基础设施；无 Zalo、支付、物流或对象存储调用。
