## 2. 已实施范围

- Zalo Checkout 退款创建/查询使用固定官方 HTTPS 端点、HmacSHA256、商城独立渠道和 secret
  reference，并限制超时、响应大小、content type、redirect 与严格 JSON shape。
- 退款命令要求当前商城权限、近期 MFA、输入式确认、原因、支付版本和幂等键。服务端锁定成功
  支付与现有退款，使用安全整数 VND 重算余额；供应商引用、状态和金额不接受客户端输入。
- 官方退款创建接口没有供应商幂等键，创建 outbox 固定 `max_attempts=1`。网络结果不确定进入
  `REVIEW_REQUIRED`，禁止自动再次创建；只有已取得供应商退款 ID 的处理中事实允许有限查询。
- 退款成功只投影订单支付状态为 `PARTIALLY_REFUNDED/FULLY_REFUNDED`，不改变订单履约、运单、
  库存或 M6 售后状态；成功终态不能被迟到失败或引用碰撞覆盖。
- 管理端提供商城隔离的支付、退款、主动查询、等待重试和 dead-letter 视图及受审重放；任务
  元数据同时按支付、退款、物流领域 read 权限过滤，不返回 payload、aggregate 或完整供应商引用。
- 买家订单详情只返回本人退款公开编号、整数金额、标准状态和时间。越南语、中文和英文界面提供
  加载、空、错误、等待和重试反馈，长编号在移动端稳定换行。
- 当前“对账”严格限定为逐笔供应商权威查询、本地异常与死信视图，不声称完成商户日结或 COD
  回款对账。

## 3. 最终安全修复与迁移

- 最终差异审查发现，原任务列表只要拥有任一领域 read 权限便可看到同商城全部任务元数据。
  服务端现按 `payment.*`、`refund.*`、`shipment.*/shipping.*` 前缀限制领域可见性，并把相同条件
  应用于游标查询；`store.integrations.read` 仍可读取全部脱敏任务。
- 原 M5.2 容量 guard 未将 `REVIEW_REQUIRED` 计入占用，可能在供应商结果不确定时过早释放金额。
  应用、管理端和数据库现共同统计 `REQUESTED/PROCESSING/SUCCEEDED/REVIEW_REQUIRED`，在受审
  解决前保持失败关闭，防止创建第二笔后超额退款。
- 收尾 API 审查发现，dead-letter 重试虽强制校验 `Idempotency-Key`，但原控制器没有把它传入
  可靠消息原语。现在商城/任务范围的键哈希和请求哈希只写入审计：同键同请求返回当前稳定事实，
  同键改参返回幂等冲突，不同键不能再次重放已离开 dead-letter 的任务，原始键不入库。
- M6.2 锁序复审发现，M5 与 M6 会并发占用同一订单退款权益。退款创建、供应商事实、人工复核和
  主动查单现于订单/支付行锁前取得数据库规范化的共享 advisory lock；受控并发回归同时确认 M5/M6
  等待者均未提前持有 order/payment 行锁，避免反向锁序和跨领域超额占用。
- 前向迁移 `20260727001000_m57_refund_review_capacity_guard` 只替换
  `app_security.enforce_refund_capacity()`；存在人工复核退款事实时，local/test `down.sql` 以
  SQLSTATE `55000` 拒绝。生产和已有事实环境只允许向前修复。
