## 1. 阶段结论

D4 已完成默认关闭、与 ClamAV scanner 解耦的 expire/delete worker，把 D0 生命周期与规范对象 ledger、
D1 delete-only storage 身份和通用可靠 outbox 接成 local/test 删除补偿链路。数据库原语在 provider 调用
前后绑定当前租约、商城、父 evidence version/status/legal hold 与完整活动对象集合；真实 PostgreSQL +
MinIO 已证明 ORIGINAL、DERIVATIVE、SCAN_TEMPORARY 的幂等删除和无残留。

该结论只允许将 **D4 repository implementation + local/test deletion worker validation** 标记
`COMPLETE`。D4 没有 B3 售后创建/claim、会员或管理员凭证正文保护读取、管理员逐次读取审计、legal
hold 管理、dead-letter 管理 API、外部告警接收方、production IAM/KMS/versioning/Object Lock/lifecycle
验收、部署或 rollout。MinIO 的当前对象删除不能冒充生产历史版本物理删除证明。

## 2. 已实现范围

- 新增 `after-sale.evidence.expire.requested` v1 与 `after-sale.evidence.delete.requested` v1 handlers；
  payload 精确只接受 `store_id/evidence_id/expected_version`，消息不能携带对象 key、截止点或 hold。
- expire 原语先锁 outbox 再锁 evidence，并在锁等待后用数据库当前时钟复核严格未过期 lease。只有当前
  version、权威状态、无 hold 且截止已到才进入 `DELETION_PENDING` 并同事务排队 delete。
- 提前 expire/delete 使用数据库返回的 `nextAttemptAt` 计算、受删除最大退避限制的 outbox 重试；持久
  lifecycle dead-letter reconciliation 可按当前权威事实重排，不依赖短轮询耗尽后丢任务。
- delete loader 只从 SYSTEM-only ledger 加载 ORIGINAL、DERIVATIVE、SCAN_TEMPORARY 的完整活动集合；
  provider 调用使用独立 delete-only 凭据并行执行并等待全部结果。
- success 和 failure 提交均重新锁消息、父行与 ledger，精确匹配 outbox owner/version/lease、父 version/
  status/hold 以及全部 `(object id, version)`。ledger 漂移抛状态冲突交给通用 outbox 重试，不能普通完成。
- provider 成功或已不存在可收口；部分失败保留全部 ledger，按至少 60 秒、最多 6 小时指数退避形成
  新领域 delete event。第 5 次记录稳定本地 warning condition，第 8 次耗尽且停止自动排队。
- `DELETE_FAILED` 重试推进到 `DELETION_PENDING` 后若进程崩溃，同一消息仅在已有失败计数且父 version
  精确为 payload expected version + 1 时恢复；provider 已删除但数据库提交前崩溃依靠幂等 not-found
  重试完成。
- 生命周期 dead-letter 服务按活动商城有界轮询；关闭时 outbox/dead-letter 先停止领取并等待在途，
  storage client 在 application shutdown 阶段才销毁。
- `AFTER_SALE_EVIDENCE_DELETION_WORKER_ENABLED` 默认 `false`。启用要求 D1 S3/delete 凭据、固定 8 次
  重试参数和足够 outbox lease；scanner 与会员上传 producer 只有删除 consumer 同时可用时才允许启用。
- D4 不新增 schema、RLS、grant、trigger、enum、STORE 权限或迁移，M2→current 保持 43 段。

## 3. 安全与事务不变量

- handler 只构造固定 `after-sale-evidence-lifecycle` SYSTEM context；商城来自被验证的 outbox 行，
  数据库查询和提交始终显式绑定 `context.storeId`，跨商城 context 在网络调用前失败。
- loader 返回的 work 不是提交授权。网络期间 lease 到期/换 owner、legal hold、父 version/status 或任一
  ledger identity 漂移时，旧 worker 的 success/failure 都不能写入。
- provider 删除身份按 role 校验规范路径。扩展删除权限没有扩大 create-upload、HEAD/GET 验证或
  protected-read；这些入口仍严格 ORIGINAL-only。
- provider 错误只映射为稳定 `EVIDENCE_DELETE_PROVIDER_UNAVAILABLE` 或
  `EVIDENCE_DELETE_IDENTITY_INVALID`。日志不记录对象 key、provider 正文、checksum、凭据、签名 URL 或
  文件内容。
- success 仅在全部 provider 操作成功或明确已不存在后，原子清空全部活动 ledger key、保留最小审计行/
  hash，并清理父行兼容 key 与敏感扫描字段后进入 `DELETED`。

## 5. 已知限制与生产阻断项

1. **版本化对象未证明物理删除**：当前 adapter 不携带 VersionId。production versioning/Object Lock 下
   普通 DELETE 可能只写 delete marker；必须在精确 provider/staging 冻结历史版本与 legal retention 语义。
2. **只有本地告警条件**：第 5 次 warning 和第 8 次 exhausted 已持久/日志化，但没有外部告警接收方、
   on-call 路由或送达证据，不能声称运营告警完成。
3. **legal hold 管理未实现**：D4 会尊重当前 hold 并拒绝漂移提交，但没有受审的设置/解除入口。未来解除
   hold 必须排队当前权威 expire/delete identity。
4. **保护读取和 B3 claim 未实现**：`store.after-sales.evidence.read` 仍无运行时，READY 凭证还不能由
   售后创建事务 claim，也没有管理员逐次读取审计。
5. **没有 heartbeat**：启动配置只证明已知 storage timeout 与两次 2 秒事务、5 秒提交余量被 lease
   覆盖。目标 provider 若无法稳定满足预算，必须停止 rollout 并另行设计续租。
6. **无专用 OpenAPI 3.1 语义 linter**：当前只证明严格 YAML 与本地引用完整。

## 6. 回滚与后续

- 首先将 `AFTER_SALE_EVIDENCE_MEMBER_UPLOADS_ENABLED=false` 停止新对象，再停止 scanner producer，最后
  关闭 deletion worker 并等待在途 provider 删除与数据库提交。不能直接卸载 handler 让既有消息作为
  unsupported 进入死信。
- D4 无 down migration。已有 `DELETION_PENDING/DELETE_FAILED`、ledger、transition 和 outbox 事实必须
  保留，由兼容 worker/reconciler 前向收敛；清库、删除 bucket 或卷不能冒充业务补偿。
- 下一阶段仍需单独规划并授权 B3 transaction-scoped claim 或保护读取/审计。production storage、
  legal hold 管理、外部告警与 rollout 必须在各自目标环境取得证据后才能启用。
