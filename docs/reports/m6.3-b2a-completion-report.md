## 2. 已实现事实

### 2.1 商城、RBAC、MFA 与 HTTP 边界

- 所有路由要求管理员 token、`X-Store-Code` 和 query `store_id` 一致；平台跨商城继续由中央授权分支要求并审计
  `X-Access-Reason`。提供了 Access-Reason 时也会严格校验，不忽略非法 header。
- 列表/详情/版本仅要求 `store.after-sales.policy.read`；草稿仅要求 `policy.manage`；发布和停用分别仅要求
  `policy.publish/disable`。权限互不隐含。
- publish/disable 使用敏感操作授权，要求近期 MFA、动作确认词、10-500 字符 reason、expected version 和 Idempotency-Key。
- B2a 政策读/写分别消费管理员 120/30 次每 60 秒档位，key 绑定商城+主体；Redis 不可用时在目标读写前失败关闭为
  `503 UPSTREAM_UNAVAILABLE`。settings GET/PUT 已在本轮进入同一 READ/WRITE 档位。
- B2a 七路成功响应和收口后的 settings 成功响应使用 `Cache-Control: private, no-store` 与安全
  `X-Correlation-Id`。稳定 `409` 冲突仅在公共错误的 `details.reason_code` 中投影白名单代码。
- HTTP/结构化日志会脱敏 `Idempotency-Key` 与 `X-Access-Reason`，不把幂等凭据或跨商城业务理由写入日志。

### 2.2 草稿、发布、停用与历史

- 政策 content 要求严格三语、冻结售后类型/运费枚举、合法窗口、不重复的目标/reason code 与有界数量。规范化固定类型顺序、
  小写 UUID、reason code 字典序、`vi/zh/en` 和目标顺序，再对规范 JSON 计算 SHA-256。
- `expected_version=0` 只创建不存在的 policy code；更新必须精确匹配正版本。新 DRAFT head 可保存草稿类目；已发布 head 的草稿
  只更新 draft payload/hash 和 product replace-set，不提前修改当前 category/head 或 checkout 活动投影。
- publish 在商城 `m62-policy:{store_id}` advisory lock 下再对 policy head `FOR UPDATE`，校验当前商城类目/商品、草稿
  payload/hash/product set 和目标占用，原子创建不可变 version、三语 localization、冻结 assignment、活动投影和 ACTIVE head。
- `published_at` 与 `effective_at` 使用同一数据库 `CURRENT_TIMESTAMP`，不实现计划发布。同目标被其他 ACTIVE policy 占用时稳定冲突，
  不使用“最后写入胜出”。
- disable 只允许 ACTIVE head，移除该 policy 的新订单解析投影并标记 DISABLED，不删除 version、assignment、订单快照或售后引用。
  重新启用只能通过发布新的不可变版本。
- publish/disable 会在同事务重算并同步 settings readiness。enforcement ON 时任何失去默认政策、目标不完整或 hash 不一致都使整个命令回滚。
- 读取重新验证草稿 canonical payload/hash/product set/head，以及版本 payload/hash/标量/三语/assignment/时间。损坏或跨 scope 事实失败关闭，
  不构造部分响应。

### 2.3 幂等、分页与审计

- 草稿、发布和停用使用商城+操作范围的 24 小时幂等记录；只保存 key hash，请求 hash 绑定 policy code 与规范 body。过期记录按数据库时间清理，
  同键异参稳定冲突，已保存响应必须再通过严格 schema 复验才可重放。
- settings 幂等记录同样按数据库当前时间清理 24 小时过期项；settings 审计保存 actor/创建更新时间、readiness actor/时间及完整 before/after，
  不以应用进程时钟或不完整审计快照替代数据库事实。
- policy heads 固定 `(updated_at DESC,id DESC)`，versions 固定 `(published_at DESC,id DESC)`。列表在单个 `REPEATABLE READ` 事务中先读
  `limit + 1` 个 page key，再对白名单 ID 投影；分页键保留 PostgreSQL 六位微秒。
- `c1_` HMAC 游标复用 B1 key ring，但将 heads/versions 绑定为不同 resource，并绑定商城、管理员、筛选、排序和 policy code。篡改、跨资源或跨 policy 重放统一拒绝。
- 草稿 create/update 审计保存严格 policy before/after；publish/disable 还同时保存 settings readiness 的完整 before/after、业务 reason、actor 与 correlation ID。

## 3. 数据库、RLS、迁移与兼容性

- 新迁移 `20260729100000_m63_b2a_policy_control_plane` 只增加：

  - `after_sale_policies(store_id, updated_at DESC, id DESC)`
  - `after_sale_policy_versions(store_id, policy_id, published_at DESC, id DESC)`

  它不创建或改写 policy/settings/assignment/snapshot/after-sale 事实，不变更任何 RLS。`down.sql` 仅供 local/test 受审删除这两个精确索引。

- 保留现有 tenant RLS 是明确决策。拟议的 ACTIVE-assignment-only 政策 SELECT 会让 B1 会员无法读取售后已绑定、后来被停用或替换的历史版本，却仍无法隐藏
  ACTIVE head 行内的 `draft_payload`。因此本轮不做 RLS 改写；管理面由独立应用 RBAC、显式 store scope、严格投影和 FORCE RLS 叠加保护。
- 旧数据库约束允许带下划线的 policy code 和仅保证 object 类型的 payload，而新 API 只接受连字符 code 与严格规范 payload。仓库新增
  `corepack pnpm --filter @zalo-shop/database preflight:m63-b2a`，在只读 `REPEATABLE READ` 中分批复验 code、draft/hash/products/head、所有不可变版本/三语/assignment/标量和
  `effective_at=published_at`。
- 预检事务显式设置 `row_security=off`。该设置不绕过 RLS，而会让可能被策略过滤的连接以 `42501` 失败；因此误用
  `DATABASE_RUNTIME_URL` 不会产生零行假通过。定向复验已证明本地 migration owner 成功、runtime RLS 连接失败关闭。
- 该预检已在本地 `.env.test` 目标库通过，结果为 `policies=0, versions=0`。这只证明当前本地测试库无不兼容政策；任何 staging/production 路由 rollout 前仍必须针对精确目标库重新执行并留证。发现旧事实不兼容时停止 rollout，先形成受审前向修复，不得静默隐藏旧政策。

## 6. 关键决策与风险

1. **不改写 RLS**：这不是缺少隔离，而是保留历史售后可读的必要决策。管理员权限靠独立 RBAC、显式商城 scope、严格投影和 FORCE RLS 叠加保护。
2. **旧政策兼容性**：新 API 比旧 DB CHECK 更严。本地空政策预检已通过，但不代表任何其他数据库；目标库未预检不得 rollout。
3. **普通索引部署**：两个索引使用普通 `CREATE INDEX`。本轮未部署到生产目标库；生产若已有大量政策/版本，上线前需评估表规模、锁等待和维护窗口，必要时另行批准并发索引方案。
4. **Redis 失败关闭**：政策和 settings 管理在 Redis 故障时返回 503。这是防止静默绕过限流的有意可用性取舍；上线前需 Redis 容量、健康检查和告警证据。
5. **管理操作风险**：publish/disable 可直接改变新订单的政策解析，因此必须保持独立权限、近期 MFA、确认词、reason、幂等、审计和 readiness 失败回滚。这些不能由 UI 确认弹窗代替。
6. **生产政策未授权**：仓库能力不是越南业务/法律批准。本轮没有创建、发布或启用任何真实政策；所有商城 enforcement 必须继续 OFF，直到业务/合规评审、双商城配置和上线门禁全部通过。
7. **OpenAPI 工具限制**：YAML 与全部本地引用已经结构检查，但仓库没有专用 OpenAPI 3.1 语义 linter；未来引入该工具时必须把语义校验加入门禁。
8. **本机 lint 内存**：默认约 2 GiB 堆不足以完成本次全仓 ESLint；临时 4 GiB 复验通过。此结论不修改生产运行参数，但 CI/开发机需保留足够 lint 内存。
