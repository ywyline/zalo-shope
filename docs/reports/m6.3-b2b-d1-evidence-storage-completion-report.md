## 2. 已实现范围

- `packages/config` 增加默认 `disabled` 的 `EVIDENCE_STORAGE_*` 配置。启用 S3 mode 时，evidence
  bucket、upload/read/delete access key 与 secret 必须彼此独立且不得复用 catalog/content 配置；
  production 还要求 HTTPS、非仓库 placeholder、`aws:kms` 和 KMS key ID。
- `packages/integrations/src/after-sale-evidence-storage.ts` 提供独立
  `AfterSaleEvidenceObjectStorageProvider`：create-only 上传目标、HEAD + 有界流式 GET 校验、短期
  `private, no-store` 读取目标和幂等删除。错误只暴露稳定
  `CONFIGURATION/INVALID_IDENTITY/NOT_FOUND/METADATA_MISMATCH/CONTENT_MISMATCH/
UPSTREAM_UNAVAILABLE` 分类。
- 上传的 `x-amz-checksum-sha256` 通过 unhoistable header 强制进入签名而不提升到 query。删除只有成功
  响应或明确 `NoSuchKey + 404` 才幂等收口；`NoSuchBucket`、普通 `404`、网络与未知错误均失败关闭。
- 上传目标同时把 Content-Length、Content-Type、`If-None-Match: *` 与 checksum header 绑定签名；
  bucket 配置拒绝相邻点、IP 地址形式和其他不受支持的 DNS 形状。
- HEAD/GET 启用 provider checksum mode，异常或不符合协议的流统一 abort/destroy；upload/read/delete
  client 共享同一已校验 endpoint/region 配置，避免配置漂移。
- 对象身份只接受
  `{environment}/{store_id}/staged/{evidence_id}/original`，并逐段校验 environment、商城 UUID、
  evidence UUID、路径和声明元数据。
- `docker-compose.yml` 与 `infra/minio/` 使用 bootstrap root 创建固定且互相隔离的 content/evidence
  bucket、content 身份和 upload/read/delete 三组 evidence 身份；应用与测试不使用 root。
- `tests/integration/m63b2b-d1-evidence-storage.test.ts` 使用真实 MinIO bytes 覆盖四种允许格式、签名
  header 防篡改、create-only、metadata/content 欺骗、反向 IAM、幂等删除和最终无残留。

## 5. OpenAPI 与 capability 边界

- `initializeAfterSaleEvidenceUpload`、`confirmAfterSaleEvidenceUpload`、会员保护读取和管理员保护读取
  继续为 `contract_only_m6_3_b2_to_b7`；D1 不加入 implemented operation 清单。
- `uploadValidationAvailable` 不能仅因 adapter 单测/MinIO 集成通过而在业务运行时置为 true，因为没有
  HTTP confirm 调用链。
- `protectedReadAvailable` 不能仅因内部签名 GET 存在而置为 true；没有会员/管理员授权、审计和无差别
  错误的 HTTP 调用方。
- `deletionCompensationAvailable` 不能仅因 `removeObject` 存在而置为 true；没有消费 D0 ledger/outbox
  的 worker、网络后重锁或 provider 崩溃补偿。
- `malwareScanningAvailable` 和 `claimAvailable` 继续不可用。magic bytes 不是恶意文件扫描，D0 claim
  原语也没有 B3 调用方。

## 6. 已知限制与生产阻断项

1. **版本化 bucket 的物理删除未解决**：D1 delete-only adapter 不接收 version ID。bucket 一旦曾启用
   版本化，普通 DELETE 可能只创建 delete marker，不能证明旧正文已物理删除。因此本地固定 evidence
   bucket 强制“版本控制从未启用”；生产 versioning/Object Lock/lifecycle 与历史版本清理方案冻结前，
   rollout 必须阻塞。
2. **AWS 最小 read IAM 的不存在对象语义未验收**：没有 list 权限的最小 read 身份在 AWS 上对不存在
   key 可能返回 `403` 而非 `404`。D1 会失败关闭，但稳定 `NOT_FOUND`/`UPSTREAM_UNAVAILABLE` 映射仍需
   在目标 provider/staging 验证，不能沿用 MinIO 结果。
3. **MinIO 不等于 production S3**：checksum、`If-None-Match`、SSE-KMS、超时、错误正文、IAM 与
   lifecycle 必须在受控 staging 重新验收。
4. **配置门禁不是生产证明**：production 要求 HTTPS 与 KMS 配置，只证明启动输入失败关闭，不证明
   bucket 侧 KMS policy、key grants、lifecycle、备份或恢复已正确配置。
5. **内部 URL 能力没有产品授权**：adapter 能生成短期 URL，但没有 HTTP 调用方；完成报告、日志和
   测试快照不得记录签名 query、凭据、对象 key 或供应商正文。

## 7. 回滚与后续

- 应用回滚保持 `EVIDENCE_STORAGE_PROVIDER=disabled` 即可；D1 没有数据库事实或已注册调用方。
- 本地 MinIO bootstrap 可幂等重跑，但不得通过递归删除 bucket 作为应用回滚。测试对象只按随机前缀
  在 `finally` 使用 delete 身份清理。
- 若未来已有真实 evidence 对象，必须沿用 D0 ledger 和兼容 worker 收敛，不得依靠应用回滚、bucket
  删除或数据库清空。
- 下一切片 D2 scanner/worker、HTTP、B3-B7、生产配置或 rollout 均需重新计划并取得用户授权。
