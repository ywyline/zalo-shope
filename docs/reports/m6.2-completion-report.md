# M6.2 售后、会员与分享数据基础完成报告

> 状态：数据、RLS、迁移与数据库完整性范围已完成自动化收口；M6.3 运行时和生产 rollout 未开始
>
> 日期：2026-07-28
>
> 范围：`docs/plans/m6-implementation-plan.md` 的 M6.2；不包含运行时 API、worker、买家/管理 UI、
> 生产政策、政策快照 enforcement 启用、真实供应商调用、部署或发布

## 1. 结论

M6.2 已完成版本化售后政策与订单行快照、售后聚合及明细事实、证据、结算、库存/换货关联、
会员收藏/历史、最小隐私请求和分享的数据基础。30 个商城模型/表全部使用商城隔离关系和 FORCE
RLS；运行角色的可写面已收缩到列级授权及按 actor/owner 划分的命令路径。十一段前向迁移已完成
fresh deploy、M2-to-current、重复部署、down/重新前滚和有事实回滚拒绝演练。

本结论只覆盖数据事实边界。M6.3 尚未开始，M6 新增的售后、收藏/浏览历史、隐私请求和分享
controller/service/worker/UI 均未交付。所有商城的政策快照 enforcement 保持 OFF，仓库没有生产政策、
checkout 快照 writer、readiness API 或受审启用命令；现有无快照订单不能按当前政策伪造历史。

## 2. 已交付

- Prisma 新增 30 个商城模型/表并补齐与 SQL 复合外键一致的关系；订单、订单行、会员、政策版本、
  SKU、仓库、支付、退款、库存和分享目标不能跨商城或在同商城内错对象拼接。
- 30 张 M6 表启用并强制 RLS。收藏、历史、隐私和会员售后/凭证路径除商城上下文外，还校验当前
  actor 类型和 owner；无商城上下文默认拒绝。
- 政策草稿、不可变版本、发布 assignment、活动解析投影和订单行快照分离。数据库精确绑定
  policy/version/code/number/canonical payload/hash，并以 deferred guard 在 enforcement 启用后要求
  新订单行同事务存在快照。
- 售后数量和金额容量、同 case 累计 settlement、COD 双人确认及完整到账事实、ONLINE settlement
  与 M5 Refund 的订单/支付/金额精确链接，以及全局公开号由约束和事务 guard 保护。
- 库存恢复必须对应原订单 SKU、验收版本、仓库、`RESTORE` movement 和累计可售数量；换货预留、
  replacement SKU/数量/仓库及 `EXCHANGE_OUTBOUND` 运单必须一致。
- 凭证 claim、访问截止、retention、legal hold、删除排队/重试/成功相互独立；隐私 transition 的
  event/from/to 必须与当前 header 投影一致。业务事实使用只追加或受限状态列更新，不能覆盖历史。
- `shipments` 新增 `purpose` 与售后关联；旧运单和普通建单默认 `ORDER_OUTBOUND`，数据库校验
  `AFTER_SALE_RETURN`/`EXCHANGE_OUTBOUND` 与售后类型及归属。
- 普通/legacy 售后安全初态、当前管理员一次性 legacy 决定、只追加 transition/header 原子投影、
  settlement 聚合状态锁、返件/到期/拒绝/转退款与共享 shipment 并发均由初始第六段 guard 关闭旁路。
- 后续五段前向修复区分待审请求与已批准容量占用，要求订单级批准金额存在精确不可变 allocation，
  并让 M5 Refund 与 M6 审批/结算使用同一规范化 advisory key 及固定 order/payment 行锁顺序。缺失
  `app.actor_type` 的 definer capacity guard 在读取受保护聚合前以 `42501` fail closed；只有已批准或
  已有验收、结算、库存、换货副作用的案例继续占用订单级批准额度。
- 凭证要求 NULL-safe CLEAN 扫描结果并按截止点重试删除；COD digest/加密凭证不能为空；库存恢复
  绑定原订单已消费 reservation、最新验收和唯一 RESTORE movement；换货 INSERT/每次 UPDATE 都重查
  聚合状态。跨 RLS definer trigger 固定 owner/search path，PUBLIC/runtime 直接 EXECUTE 已撤销。
- 权限迁移只登记 12 项 STORE 权限，不自动给生产角色扩权；local/test seed 只显式授权测试角色，
  不创建政策、售后、结算、库存、隐私或分享业务事实。

已部署并取得证据的迁移不回写 checksum；复审发现的缺口均通过后续迁移向前修复。第五段迁移把原先
较宽的 actor policy 拆为独立 SELECT/INSERT/UPDATE 路径，只允许会员创建和读取本人售后、执行有界的
待审核取消、认领本人凭证，以及创建/读取/取消本人隐私请求。会员不能写内部 settlement、库存或换货
事实。

售后取消和隐私 header 投影由固定 `search_path` 的 `SECURITY DEFINER` trigger function 完成，以便在
撤销运行角色直接状态列更新权限后仍原子投影合法 transition；这些函数的直接 EXECUTE 已同时从
PUBLIC 和 `zalo_shop_runtime` 撤销，运行角色只能通过受 RLS、事件、owner 和状态 guard 的事实写入
触发，不能把 definer 函数当旁路调用。

初始第六段向前修复在此基础上锁定售后聚合，禁止终态晚到行/运单、受污染 legacy 决定、错误 settlement
状态、NULL COD/扫描事实、超额或重复库存恢复，以及转退款后换货重新推进；共享 shipment 与返件提交
同拒绝/到期/转换串行化。相关跨 RLS 函数同样固定 definer owner/search path 并撤销直接 EXECUTE。

后续五段不回写已部署定义：容量、allocation、锁序和 actor scope 缺口均以前向替换函数修复；M5
`refund-primitives` 在取得订单/支付行锁前使用同一数据库规范化 advisory key，退款创建、供应商事实、
人工复核和主动查单路径保持一致。

十一段 `down.sql` 只允许无 M6 事实的 local/test scratch。存在政策快照、售后、结算、凭证、库存、
收藏/历史、隐私或分享事实时以 SQLSTATE `55000` 拒绝；生产和已有事实环境只允许向前修复。

## 5. 风险边界确认

| 风险项             | M6.2 数据层证据                                                    | 保留边界                                                               |
| ------------------ | ------------------------------------------------------------------ | ---------------------------------------------------------------------- |
| 多商城与会员 owner | 复合外键、30 表 FORCE RLS、actor/owner policy、运行角色写路径收缩  | M6.3 仍须实现服务层 store/member 判权、RBAC、MFA、幂等和审计           |
| 政策与历史订单     | 不可变版本/assignment/快照精确绑定，启用后 deferred commit guard   | enforcement 全部 OFF；无生产政策、checkout writer/readiness 或 rollout |
| 金额与退款         | 聚合状态锁、累计容量、COD 非空双人事实、M5 Refund 精确链接         | ONLINE/COD 运行时协调、真实退款、结算和财务流程尚未实现或验收          |
| 库存与换货         | 原消费 reservation、验收、movement、累计恢复及每次履约状态 guard   | M6.4 命令、worker、失败补偿和真实换货履约尚未开始                      |
| 凭证与隐私         | owner、NULL-safe scan、claim/hold/删除重试、append-only transition | 对象存储、扫描、清理 worker、短期访问 URL 及 M7 隐私履约尚未实现       |
| 物流 purpose       | 默认订单 purpose、聚合状态锁及 reject/expire/convert 并发 guard    | 既有 M5 查询/命令/callback/worker 尚未全面 purpose-aware               |
| 会员与分享         | 收藏/历史/隐私/分享表、owner RLS、目标复合关系和最小交互事实       | 买家运行时、三语 UI、Deep Link、Zalo 主动分享和真机矩阵尚未交付        |

shipping purpose 是进入 M6.3 前必须关闭的运行时风险：当前 M6.2 不创建非订单运单，因此尚未触发；
M6.3 在创建任何 `AFTER_SALE_RETURN`/`EXCHANGE_OUTBOUND` 前，必须让既有 M5 订单物流读取、创建/
取消/查单、callback 和 worker 显式按 purpose 分流，且只有 `ORDER_OUTBOUND` 可以推进原订单
`SHIP/DELIVER`。

## 6. 外部阻塞、Git 与下一阶段

美妆卫生、开封例外、期限、证据、运费承担和服装换码政策仍需越南业务/合规批准；没有批准时不得
创建或发布生产政策。真实对象存储/扫描/删除、COD 退款渠道和到账凭证、GHN 返件/换货、Zalo 分享
真机、生产迁移锁等待和近生产容量均未由本阶段验收。

M5.5-M5.7、整个 M5 和 P0 继续保持未完成。真实两商城 ZaloPay/GHN、HTTPS callback、商户结算、
GHN COD 回款和 Zalo 宿主证据仍是上线硬门禁；M6.2 的仓库自动化不能替代这些外部证据。

本阶段未提交、未推送、未部署、未发布，未写入生产凭据或真实业务数据，也未清理用户本地忽略
文件。M6.2 完成不自动授权 M6.3；下一阶段必须先实现 checkout 快照 writer/readiness、受审逐商城
enforcement 控制面和 shipping purpose 分流，再进入售后申请、审核、返件和结算协调。
