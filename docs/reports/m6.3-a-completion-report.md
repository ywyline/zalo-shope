## 1. 结论

M6.3-A 的目标代码、四段前向迁移和配套契约/文档已经落地。checkout 现在按“商品覆盖 → 最近
主类目祖先 → 商城默认”解析不可变政策版本；商城 enforcement 为 OFF 时不写任何订单行政策快照，
为 ON 时在创建订单的同一事务写齐全部订单行快照并对任何缺失失败关闭。settings GET/PUT 已具备
当前商城隔离、独立权限、敏感写入控制、并发/幂等和审计边界。既有物流读取、命令、callback hint、
worker 与供应商事实应用已显式传递本地可信 purpose，只有 `ORDER_OUTBOUND` 能推进原订单。

当前候选已通过定向单元、数据库、集成、迁移演练、`corepack pnpm verify`、21/21 浏览器 E2E、
交付候选 Gitleaks、`git diff --check` 与生产依赖 high 门禁，因此 M6.3-A 标记完成。npm 审计结果为

不授权 M6.3-B、生产 enforcement、部署或发布。

## 2. 已实现范围

### 2.1 checkout 政策解析与快照

- 解析优先级固定为商品覆盖、最近主类目祖先、商城默认，并同时受应用 writer 与数据库快照 guard
  约束；不以最后写入或客户端选择隐式决胜。
- 规范 payload 与 SHA-256 精确绑定政策 ID/code、不可变版本号和 assignment。readiness hash 还绑定
  版本化运行时能力 `m63-a:product-nearest-category-default:canonical-payload-v1`，应用升级不能沿用
  不兼容 writer 的旧 ready 事实。
- checkout 锁定每商城稳定 settings 行，与开关命令串行。OFF 明确写零个快照；ON 必须在订单事务内
  写齐全部订单行快照，解析、payload/hash 或写入任一失败都会回滚整笔下单。
- 不回填旧订单，不用当前政策伪造历史；无快照订单仍走受审 legacy policy review。

### 2.2 settings readiness/enforcement 控制面

- 仅开放 `GET /v1/admin/after-sale-settings` 与 `PUT /v1/admin/after-sale-settings`。
- GET 要求 `store.after-sales.policy.read`；PUT 独立要求
  `store.after-sales.policy.enforce` 和近期 MFA。两者都校验管理员令牌、`X-Store-Code` 与查询
  `store_id` 的商城一致性，并把 `X-Access-Reason` 传入授权上下文；平台跨商城访问时 reason 必填且
  另行审计。
- PUT 要求与 enable/disable 动作匹配的确认词、reason、expected version，并在同一事务重新计算
  readiness，不接受客户端 ready、policy ID 或 purpose 选择。
- 幂等键按商城和 `after-sale.policy.enforce` operation 隔离，只保存 hash，保留 24 小时；同键同参
  返回原结果并标记 replay，同键异参稳定冲突。
- 成功开关记录精确 settings before/after、reason、管理员、商城与 correlation ID 审计；并发序列化
  冲突有稳定 `409` 路径。

### 2.3 物流 purpose 安全分流

- `ShipmentPurpose` 已贯穿订单物流查询、创建/取消/主动查单命令、callback hint、worker 和供应商
  权威事实应用。
- purpose 只从当前商城本地 shipment 事实解析；callback body、客户端和供应商响应均不能选择或覆盖。
- 只有 `ORDER_OUTBOUND` 能产生原订单 `SHIP/DELIVER` 推进；
  `AFTER_SALE_RETURN`/`EXCHANGE_OUTBOUND` 不得复用该路径。
- 创建中的运单可以受理取消；取消 worker 在供应商运单号尚未回写时保留 operation `PENDING` 并
  交回可靠 outbox 重试，真正缺失的 operation 仍按永久错误处理。创建完成后，同一取消 operation
  会读取刚写回的供应商单号继续执行，不会留下因竞态而漏取消的活动供应商运单。
- 本切片不创建返件或换货运单；相应售后协调仍属于 M6.3-B。

## 3. 迁移与数据安全

| 迁移                                                     | 作用                                                                         |
| -------------------------------------------------------- | ---------------------------------------------------------------------------- |
| `20260728100000_m63_policy_snapshot_category_resolution` | 将快照数据库 guard 对齐最近主类目祖先解析                                    |
| `20260728101000_m63_policy_settings_rows`                | 为所有既有商城补齐稳定 `OFF/version=1` settings 行                           |
| `20260728102000_m63_policy_settings_lock`                | 提供只锁当前商城并返回 enforcement 布尔值的窄 definer 函数                   |
| `20260728103000_m63_policy_settings_provisioning`        | 由 `stores_after_sale_setting_provisioner` 为以后新增商城自动建立稳定 OFF 行 |

`app_security.lock_m63_after_sale_setting()` 是唯一有意允许 runtime 直接执行的 definer 例外。它固定
安全 `search_path`，只使用当前商城上下文，只读取并锁定单个布尔值，设置行缺失时失败关闭，不能
更新设置或访问其他商城。其他 definer 的 PUBLIC/runtime 直接 EXECUTE 边界保持不变。

四段 `down.sql` 仅供空事实 local/test。存在政策快照、活动类目 assignment、政策或任何非默认设置
事实时以 SQLSTATE `55000` 拒绝弱化边界；生产及已有事实环境只允许向前修复。若应用需要回滚到
没有快照 writer 的版本，已启用商城必须先通过受审命令关闭 enforcement，禁止直接改表。

## 5. 依赖审计与 moderate 风险结转

`corepack pnpm audit --prod --audit-level high` 已在用户明确允许发送生产依赖元数据后执行，退出码为 0，
满足项目 high 及以上门禁。随后用 JSON 结果复核到 3 项 moderate，均来自 Mini App 的
`react-router-dom/react-router@6.30.4`：

- `GHSA-wrjc-x8rr-h8h6`：`Link/useNavigate` 反斜杠开放重定向绕过；`react-router` 修复线为 7.18.0。
- `GHSA-jjmj-jmhj-qwj2`：开放重定向导致 XSS；`react-router-dom` 修复线为 6.30.5。
- `GHSA-337j-9hxr-rhxg`：SSR hydration `deserializeErrors()` constructor injection；
  `react-router` 修复线为 7.18.0。

当前 Mini App 使用纯客户端 `HashRouter`，没有 SSR hydration；现有 `Link/useNavigate` 目标均由本地
路由模板和受约束商品 code/UUID 构造，不接受任意外部跳转 URL。这降低当前可达性，但不消除依赖公告。
`zmp-ui@1.11.14` 同时固定引入 6.30.4，不能只升级直接依赖便宣称修复；应在生产发布前结合 ZMP UI
兼容性完成 React Router 升级和导航安全回归。该结转不阻塞本仓库规定的 high 门禁，也不得被表述为
“无已知漏洞”。
