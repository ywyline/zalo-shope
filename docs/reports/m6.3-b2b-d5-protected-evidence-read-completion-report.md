## 1. 阶段结论

D5 已完成两条默认关闭的 member/admin 凭证保护读取路由。它只为当前仍获授权的调用者签发已 claim、
`READY`、未超过普通访问期限的 ORIGINAL 短期 URL；管理员每次成功签发都与最终授权重验在同一事务内
写入最小审计。真实 PostgreSQL、Redis 与 MinIO 已验证商城、会员、case、RBAC、session、Bearer、状态、
期限、对象身份、限流和签名竞态边界。

该结论只允许将 **D5 default-disabled repository implementation + local/test protected-read
validation** 标记 `COMPLETE`。D5 没有 B3 transaction-scoped claim caller、legal-hold 管理、外部告警、
production IAM/KMS/versioning/Object Lock/lifecycle 验收、目标环境部署或 rollout；短期 bearer URL 的残余
窗口也尚未取得生产风险接受。完整 B2b/B2、M6.3、M6 与 P0 继续未完成。

## 2. 已实现范围

- 注册 `GET /v1/after-sales/{afterSaleId}/evidence/{evidenceId}` 与
  `GET /v1/admin/after-sales/{afterSaleId}/evidence/{evidenceId}`；能力由
  `AFTER_SALE_EVIDENCE_PROTECTED_READS_ENABLED=false` 默认关闭。
- member 入口绑定当前商城、当前会员和指定售后 case；admin 入口要求
  `store.after-sales.evidence.read`、显式 `store_id`，平台跨商城访问还要求固定 incident-reference 格式的
  `X-Access-Reason`。
- eligibility read 只使用 D0 evidence header 的 ORIGINAL key，依赖 deferred ORIGINAL-binding guard；
  member/admin 不获得 system-only object ledger、DERIVATIVE 或 SCAN_TEMPORARY 的读取权限。
- 签名在数据库事务外执行，并以数据库 `ordinary_access_deadline_at` 截断 D1 configured read TTL；响应
  仅包含 `url`/`expires_at`，发送 `Cache-Control: private, no-store` 与
  `Referrer-Policy: no-referrer`。
- 最终事务重新锁定并验证 ACTIVE 商城、当前 actor、Bearer、未撤销未到期 session、member 商城归属或
  admin direct/cross-store RBAC，再以 `FOR SHARE` 锁定 evidence；锁取得后再次校验 Bearer、session、
  signed URL 与普通访问期限。
- 错商城、错会员/case、未 claim、缺失 header key、过期、`PENDING`、`FAILED`、`QUARANTINED`、
  `DELETION_PENDING`、`DELETE_FAILED`、`DELETED` 及其他不可用事实统一映射为不可枚举 `404`。
- 成功 admin 读取在最终事务内恰写一条
  `after-sale.evidence.protected_read.issued` 审计；allowlist 不含 URL、object key、checksum、scanner/
  provider 详情或文件内容，并记录来自受信请求 peer 的规范化 `source_ip`。审计或跨商城授权审计持久化
  失败均回滚并返回 `503`，不签发 URL。
- 第 44-48 段迁移建立最小锁读、授权重验、member store 列级 grant 修复、锁后到期复验和提交截止
  绑定；不新增业务表、列、枚举或 STORE permission code，也不扩大 runtime 或 member 常规写权限。

## 3. 安全与事务不变量

- `zalo_shop_evidence_read_guard` 固定为 `NOLOGIN`、`NOINHERIT`、`NOSUPERUSER`、`NOCREATEDB`、
  `NOCREATEROLE`、`NOREPLICATION`、`NOBYPASSRLS` 且无角色关系；函数使用固定 `search_path` 和
  `row_security=on`。runtime 不能直接调用旧 evidence-only lock，也不能取得 guard role membership。
- guard 只有完成授权和锁读所需的精确列级权限。local/test 前向修正后，整表 `SELECT` 和
  `checksum_sha256` 读取均为 `false`，可读 evidence 列限制为计划规定的九列。
- prepare snapshot 或签名结果不是最终授权。session、商城、账号、RBAC、case/owner、状态、key、期限或
  版本在最终提交前漂移时，不返回 URL；仅 legal-hold-only version 漂移不会提前撤销仍有效的普通读取。
- `FOR SHARE` 与 lifecycle writer 冲突；等待写锁后以数据库当前时钟再次复验，防止已过期 Bearer、
  session、signed URL 或 ordinary deadline 被返回。
- member/admin 各复用既有 after-sales READ 限流。Redis、配置、storage signing、最终重验或审计不可用
  均失败关闭；日志和审计不记录 bearer URL 或对象敏感事实。
- D5 路由使用服务端生成的 correlation ID；客户端 correlation header 不进入 D5 审计，HTTP logger 始终
  脱敏原始 header，仅保留通过安全校验的 request identity，避免 checksum、访问密钥或其他任意客户端字符串
  成为日志事实，同时保留合法 correlation 的检索能力。

## 5. 已知限制与生产阻断项

1. **B3 claim caller 未实现**：D5 只读取已绑定售后 case 的 evidence；当前没有业务创建事务把会员凭证
   claim 到真实售后申请，不能据此声称完整凭证或售后流程可用。
2. **短期 bearer URL 残余窗口**：最终事务提交后的授权撤销不能使已签 URL 立即失效，窗口最长为受限
   TTL。D5 现在将 URL 截止绑定到 bearer/session 截止，并在最终 SQL/应用检查保留提交余量，但仍不能
   在提交后撤销已发行 URL；production 启用前必须由目标环境 owner 明确接受风险或提供更强的中止机制。
3. **生产对象存储未验收**：local/test MinIO 不能证明最小 read IAM 与 upload/delete 身份隔离、HTTPS、
   KMS、versioning/Object Lock/lifecycle、legal retention 或稳定 not-found 语义。
4. **部署需要受控 superuser**：第 44、45、47、48 段必须由 PostgreSQL `rolsuper` maintenance executor
   转移或替换 definer ownership；不能临时提升 application runtime 作为替代。
5. **运营控制面未完成**：没有 legal-hold 管理、删除 dead-letter 管理或外部告警接收方。D5 尊重当前
   hold 事实，但不提供设置或解除入口。
6. **来源 IP 依赖受信边界**：D5 记录应用看到的规范化 peer IP；生产反向代理必须由受控网络边界配置，
   不得把未经验证的 `X-Forwarded-For` 直接当作来源 IP。
7. **无专用 OpenAPI 3.1 语义 linter**：当前只证明严格 YAML 与本地引用完整。

## 6. 回滚与后续

- 首先设置 `AFTER_SALE_EVIDENCE_PROTECTED_READS_ENABLED=false`，等待在途请求结束和已签 URL 的最大
  短 TTL 过去；不得通过删除 evidence、对象、审计或 guard role 撤销已发行能力。
- 仅 local/test 且不存在任何 `after-sale.evidence.protected_read.issued` 审计事实时，才允许按
  `48 -> 47 -> 46 -> 45 -> 44` 逆序执行 `down.sql`；第 48、47 段的逆向脚本只做审计事实 guard，不恢复
  较弱函数。任一 issued-read audit 必须 fail-fast；生产或已有审计事实的数据库只允许经审查的前向修复。
- 下一阶段仍需单独规划并授权 B3 transaction-scoped claim caller。production storage、legal-hold
  管理、外部告警、bearer-URL 风险接受与 rollout 必须在各目标环境取得证据后才能启用。
