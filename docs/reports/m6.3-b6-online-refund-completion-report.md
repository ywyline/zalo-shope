## 1. 阶段结论

B6 已完成默认关闭的管理员 ONLINE 售后退款命令，以及 M5 权威 refund 事实向售后 settlement/case 的异步收敛。
命令只接收确认词、售后 expected version 和原因；退款金额、支付分支、商城归属、成功支付和剩余可退容量均由
服务端在 Serializable 事务内读取和重算。ONLINE settlement、M5 refund、售后唯一 link、两侧 transition、
审计和版本化 sync outbox 原子提交。

最终安全复审将锁序统一为售后命令幂等锁、共享 M5 订单退款 advisory lock、订单、唯一成功支付、售后聚合、
settlement/link。命令在锁等待后以 `FOR SHARE` 锁定并重验 ACTIVE 商城/管理员、有效 session、近期 MFA、
Bearer 到期、商城角色分配和四项直接权限，第一笔业务写入前失败关闭。并发回归证明等待 M5 订单锁时不会提前
持有售后行锁，且等待期间撤销 `store.refunds.create` 会原子返回授权失败，不留下资金或审计事实。

该结论仅将 **B6 default-disabled repository implementation + local/test validation** 标记为 `COMPLETE`。
`AFTER_SALE_REFUND_COMMANDS_ENABLED` 默认 `false`，production 配置和服务层均拒绝启用。真实 ZaloPay/其他
provider、沙箱凭据、COD 结算、返件验收、库存恢复、换货、UI、部署和 rollout 均为
`NOT_AUTHORIZED / NOT_RUN`，不能据此宣称完整售后、支付生产验收或 Production Ready。

## 2. 已实现范围

### 2.1 API、授权与金额

- 注册管理员 `POST /v1/admin/after-sales/{afterSaleId}/refund`，严格绑定 Store-Code、认证管理员、
  Idempotency-Key、来源 IP、服务端 correlation ID 和 expected aggregate version。
- 严格 DTO 拒绝客户端 `amount_vnd`、payment branch、状态、provider reference 和未知字段；金额只取冻结的
  `approved_total_vnd`，并复用 M5 refund capacity guard。
- 同时要求目标商城直接 `store.after-sales.review`、`store.refunds.create`、`store.after-sales.read` 和
  `store.refunds.read`、近期 MFA、有效 session/Bearer；cross-access-only 不能替代任一权限。
- 服务层预检之后仍在写事务最终重验授权。稳定错误映射将最终授权漂移返回 `403`，不会泄露跨商城售后事实。

### 2.2 事务、锁序与幂等

- 售后命令幂等 advisory lock 只串行相同命令；读取只读售后身份后，先取得既有
  `m62-refund:{store}:{order}` advisory lock，再锁订单、成功支付和售后聚合，消除 M5/B6 反向等待窗口。
- 在同一 Serializable 事务创建 `ONLINE_ORIGINAL` settlement、transaction-scoped M5 refund、唯一
  `after_sale_refunds` link、`QUEUE_REFUND/REFUND_REQUESTED` transition、审计及 sync outbox。
- 同键同参返回冻结 replay acknowledgement；同键异参、stale version、支付/金额/商城/link/capacity 不一致
  均稳定失败。仅 `P2034`/SQLSTATE `40001` 执行最多三次有界重试。
- M5 `createRefundInTransaction` 保留原 API 兼容，并导出共享订单退款锁原语；B6 重入同一 advisory lock 不会
  建立第二套退款账或绕过 M5 不变量。

### 2.3 Provider 结果收敛

- `after-sale.refund.sync` v1 payload 只包含 `store_id/refund_id/refund_version`，worker 重新读取数据库权威事实，
  不信任消息中的金额、状态或 provider 数据。
- M5 `SUCCEEDED/FAILED/CANCELLED/REVIEW_REQUIRED` 分别收敛 settlement 与售后状态；SYSTEM transition 使用
  独立 allowlist 身份。UNKNOWN、未来版本、金额、商城、payment 或 link 不一致进入人工复核或失败关闭。
- 重复和乱序消息幂等；命令 replay 与 M5 provider fact 均可补发缺失的当前版本 sync 消息。
- worker 无条件注册以继续收敛已提交事实；管理员创建命令仍由独立开关默认关闭且 production 拒绝。

## 3. 数据、兼容与回滚

- B6 不新增 schema 或迁移，复用 M6.2/B0 的 `after_sale_settlements`、`after_sale_refunds`、RLS、复合关系、
  SYSTEM transition allowlist 和完整性 guard，以及 M5 的 payment/refund/outbox 模型。
- settlement/refund/link/transition/outbox/audit 是不可逆资金事实。应用回滚只关闭新命令并继续消费 sync；
  不得删除、逆转或用脚本伪造历史资金结果。
- 第 52 段迁移仍是 B5 的返件可信事实迁移；B6 没有新增 down.sql。52 段完整升级、fresh/redeploy、历史边界、
  down/forward 和 facts guard 已重新演练。
- 多商城查询、写入、缓存消息身份和审计均显式包含 `store_id`；没有新增生产角色 grant 或跨商城写能力。
