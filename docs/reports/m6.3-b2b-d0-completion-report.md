## 1. 结论

M6.3-B2b-D0 已完成售后凭证的仓库内数据库生命周期与可靠排队底座：

- `after_sale_evidence_files` 已补齐 upload/confirm/scan generation、scanner identity、独立 ordinary
  access deadline 与删除耗尽元数据。
- 新的 `after_sale_evidence_objects` 以逐对象 ledger 表达 ORIGINAL、DERIVATIVE、SCAN_TEMPORARY 和
  删除事实；父行只有在全部活动对象 key 清空后才能 `DELETED`。
- evidence lifecycle 使用独立 SYSTEM scope/actor、FORCE RLS、列级 grant、trigger/constraint
  trigger 和 append-only transition，不复用管理员或普通售后 SYSTEM principal。
- 初始化、确认、SYSTEM 重扫请求、scan 结果、transaction-scoped claim、expire、逐对象删除、失败退避/耗尽和三类
  dead-letter reconciliation 原语已落地，并以 expected version、scan generation、deadline、hold 与
  固定锁序保护竞争。
- scan/expire/delete outbox 的 payload 精确只有 `store_id/evidence_id/expected_version`；数据库
  deferred guard 要求关键 lifecycle change 与对应消息同事务提交。
- B1 已 claim `READY` 的公共投影改用 `ordinary_access_deadline_at`，不再错误地用物理 retention 期限
  延长普通读取。

适用仓库门禁与数据库证据见第 5 节。因此只将 **D0 repository implementation** 标记
`COMPLETE`。该结论不表示真实文件曾上传、校验、扫描、读取或从 provider 删除，也不表示 B2b、
B2、B3-B7、M6.3、M6、M5 或 P0 完成。

## 2. 已实现事实

### 2.1 数据形状与对象 ledger

- `after_sale_evidence_files` 新增 `upload_deadline_at`、`confirmed_at`、`scan_requested_at`、
  `scan_completed_at`、正向 `scan_generation`、三项 scanner identity、
  `ordinary_access_deadline_at` 和 `delete_exhausted_at`；shape CHECK 与 lifecycle trigger 保护组合不变量。
- 初始化只能由当前商城 owner member 创建无售后归属的 `PENDING`，固定
  `{environment}/{store_id}/staged/{evidence_id}/original`，generation 为 0、version 为 1，且没有
  scan/claim/hold/delete 事实。
- ledger 使用 `(store_id,evidence_file_id)` 复合 FK、FORCE RLS、全局 key/hash 唯一和 role-scoped
  唯一索引。ORIGINAL 与父兼容 key 一致；DERIVATIVE/SCAN_TEMPORARY 只能由 evidence SYSTEM 写入
  `derived`/`scan` 命名空间。
- 未删除 ledger 行必须保留 key 且无 `deleted_at`；已删除行必须清空 key 并保留 SHA-256 hash、role、
  version 与删除时间。deferred binding guard 禁止父/子半状态。
- M6.2 父行 `object_key/derivative_object_keys/scan_temporary_object_key` 暂作兼容投影；D0 新删除原语
  只信任规范 ledger，不信任 JSON 数组或队列完成状态。

### 2.2 身份、隔离与状态竞争

- `AfterSaleEvidenceSystemContext` 固定
  `system_scope=after-sale-evidence-lifecycle`、SYSTEM actor
  `00000000-0000-4000-8000-000000000006`、当前 store 与 correlation ID。
  `withAfterSaleEvidenceSystemTransaction` 只把这些值设置为 transaction-local。
- member 初始化/确认/claim、admin legal hold 与 evidence SYSTEM lifecycle 使用分离 RLS policy；错误
  scope、普通 StoreContext、管理员冒用 SYSTEM、错商城/会员和越 allowlist 事件均失败关闭。
- evidence transition 由父 lifecycle 变化（含同状态重扫）自动追加并强制 correlation ID。除 member `CLAIM` 外，D0 状态
  transition 必须来自专用 SYSTEM；运行角色不能直接插入/修改/删除 transition 或执行 definer
  validator。
- 配额锁按 `(store_id,member_id)` 串行化。尚未 claim 且未 `DELETED` 的 PENDING、
  READY_UNCLAIMED、FAILED、QUARANTINED、DELETION_PENDING 与 DELETE_FAILED 都计入数量/字节；
  claim 与最终删除沿用同一锁序释放占用。
- scan 结果只有 current expected version + generation 可投影。精确 CLEAN 才进入
  `READY_UNCLAIMED`，恶意进入 `QUARANTINED`，超时/不可用/不确定进入 `FAILED`；stale/乱序安全 no-op。
- claim 同时冻结 `claimed_at/ordinary_access_deadline_at/retention_deadline_at`。普通读取到
  ordinary access 排他截止即失败；retention 与 legal hold 不延长读取。已 claim 对象晚到恶意结果仍
  使用 retention 截止清理，不回退到旧 claim 截止。

### 2.3 可靠消息、删除与 reconciliation

- 三类事件固定为 `after-sale.evidence.scan.requested`、
  `after-sale.evidence.expire.requested`、`after-sale.evidence.delete.requested`，aggregate 固定
  `AFTER_SALE_EVIDENCE`、event version 为 1。idempotency identity 绑定 event/evidence/current
  version。
- payload 键集合精确为 `store_id/evidence_id/expected_version`；对象 key/hash、MIME、checksum、
  scanner 结论、generation、deadline、hold、错误正文和供应商数据不能进入消息。未来 worker 仍须
  重读权威数据库，消息不是授权或状态真相。
- 初始化与 upload expire、确认/重扫与 scan、scan 结果/claim 与新 expire、首次到期与 delete、可重试删除失败
  与下一 delete 消息必须原子提交；任一步失败整笔回滚。
- 删除开始、列出对象、逐对象完成与记录失败每次都重锁并复核 store、expected version、deadline、
  hold 和 ledger 集合。第 5 次形成持久告警条件；第 8 次固定 `DELETE_FAILED +
delete_exhausted_at`，清空下一自动尝试。非耗尽退避至少 60 秒、最多 6 小时。
- scan dead letter 把仍待扫描对象收敛为不可 READY 的 `FAILED` 并排队清理；expire dead letter 按当前
  deadline/hold 重排或进入删除；delete dead letter 进入有界 retry/exhausted。已有更高版本身份时旧
  消息 `SUPERSEDED`，不能把 DEAD_LETTER 直接标成业务成功。

## 3. 迁移、兼容与回滚

- 前向迁移为 `20260729120000_m63_b2b_d0_evidence_lifecycle`。由于此前从未启用 B2b route，迁移要求
  evidence files/transitions、`AFTER_SALE_EVIDENCE`/`after-sale.evidence.*` outbox 和
  `after-sale-evidence-*` idempotency 四类事实全空；任一非空以 SQLSTATE `55000` 停止，不能猜测
  外部对象的确认、扫描或保留事实。
- `corepack pnpm --filter @zalo-shop/database preflight:m63-b2b-d0` 使用
  `REPEATABLE READ + READ ONLY + row_security=off`。该设置不会绕过 RLS；runtime URL 会以 `42501`
  失败，避免隐藏行导致零事实假通过。本地 owner 目标结果为
  `files=0, transitions=0, outbox=0, idempotency=0`。
- `down.sql` 额外检查 object ledger，只有 evidence/ledger/transition/outbox/idempotency 五类事实全空
  的 local/test 才允许恢复精确 M6.2 列、索引、RLS policy、trigger、FK update action 与 grant。
  production 与任何已有凭证事实环境只允许受审向前修复。
- 应用回滚不涉及注销 HTTP/worker，因为 D0 从未注册它们。若未来已有 D0 runtime 事实，必须保留
  schema/兼容原语与 worker 至安全终态，不能靠回滚删除对象、消息、transition 或审计。
- 本地精确测试目标为 `localhost:5432/zalo_shop`。初次 reset 遇到此前测试遗留的
  `app_security` schema；确认目标仅为该本地测试库后清除残留 schema 并 fresh 重建成功。最终全量
  integration 前又因先行定向测试留下旧夹具而重建同一测试库。旧测试数据不可恢复，未触及其他数据库
  或生产数据。

## 6. 关键判断、风险与限制

1. **数据库排队不等于文件能力**：D0 没有 storage/scanner adapter 或 worker。直接调用 scan-result
   原语只证明竞争语义，不能证明任何文件被扫描。
2. **确认尚未验证 provider 元数据**：confirm 锁定 owner evidence 并由 deferred binding guard 保护
   唯一匹配 ORIGINAL，但没有 provider HEAD/body/magic 读取，也不接收 provider 已验证 MIME、长度、
   checksum。完整 B2b 必须在签发/确认边界补齐真实验证后才能启用 capability。
3. **对象删除是数据库提交边界**：`completeAfterSaleEvidenceDeletion` 要求精确 ledger/version 集合，
   但 D0 不调用 provider。未来 worker 只有在 provider 成功或确认 not-found 后才可调用它。
4. **生产策略未批准**：15 分钟 upload、24 小时 claim、30 天普通访问、90 天 retention、12 个/
   200 MiB 配额等仅是自动化输入基线，D0 没有运行时默认配置。生产必须由越南业务、隐私/DPO 与
   合规审批并逐环境显式配置；缺失时失败关闭。
5. **legal hold 治理未交付**：数据库保留 admin hold 数据边界，但 D0 没有管理入口。hold 只能阻止
   物理删除，不能延长 ordinary access。
6. **外部网络故障证据缺失**：真实 provider 下的 upload、scanner timeout/malicious/unknown、删除后
   DB 崩溃、lease 丢失、外部告警和 KMS/lifecycle 尚未演练；数据库 dead-letter fixture 不能替代。
7. **目标库非空必须停止**：本地空库 preflight 不是 staging/production 证据。发现既有事实时不能
   强行迁移或补假时间，必须另行设计受审前向修复。
8. **M6.3 范围仍大幅未完成**：D0 没有申请/取消/审核/返件/退款/COD、会员状态读取、管理员保护读取
   或 UI。局部数据底座不能作为 P0 售后验收。

## 7. 后续门禁

完整 B2b 至少仍需另行计划、批准并取得以下证据：

1. 专用 evidence bucket/prefix、catalog/content 完全不可访问的上传/读/删 IAM、KMS 与 lifecycle。
2. 真实 MIME/magic/长度/checksum 校验、真实 scanner adapter、超时/恶意/不确定失败关闭与 worker。
3. owner 状态 HTTP、B3 同事务 claim、会员/管理员短期保护 URL 和每次管理员读取审计。
4. expire/delete worker、provider not-found 幂等、提交后崩溃/lease 丢失/重试耗尽与外部告警。
5. 获批且逐环境显式的 TTL/配额/retention/delete/alert 配置，以及目标库 preflight 与 rollout 证据。

任一项不可用时，未来要求 evidence 的 B3 申请必须稳定失败关闭且不创建售后单。本轮没有处理真实
用户文件、连接外部供应商、写生产配置、部署或发布。
