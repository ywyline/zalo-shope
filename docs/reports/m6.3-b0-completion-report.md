## 3. 冻结业务与安全语义

### 3.1 售后准入、政策和交付时间

- 非 legacy 单个售后单的全部订单行必须匹配同一 `policy_id`、不可变 version 和 canonical payload
  hash；不同政策必须拆为多个售后单，不能任取第一行。
- 每个订单行的权威 `delivered_at` 只来自 `shipment_items` 关联的 `ORDER_OUTBOUND` 运单；要求相关
  数量精确覆盖原订单行、运单已签收且时间可证明。多运单采用可证明事实中的最晚交付时间。
- 重复/冲突运单、数量不守恒、把非订单 purpose 当成交付依据、未签收或缺少交付时间均不得使用当前
  时间、订单状态时间或更新时间推断；无法证明的旧事实进入受审 `legacy_policy_review`。

### 3.2 数量、金额与证据

- 创建和审核都使用相同的安全整数 VND 余数算法。审核请求逐行提交 `approved_quantity`，客户端不提交
  批准金额；至少一行大于零，不能超出申请量/剩余数量，覆盖全部剩余数量时取得全部剩余 VND。
- 服务端继续锁定订单行并同时保护售后、订单、支付和 M5 refund 容量；运费权益独立且每订单最多一次。
- reason code 来自冻结政策 allowlist，是否要求证据由服务端解析。政策要求证据时，真实上传校验、
  magic bytes/大小/数量、恶意文件扫描、READY claim、受保护读取和删除补偿能力必须全部可用；任一
  能力缺失都失败关闭、不创建售后，不能使用未扫描对象、静态成功或手工数据库写入放行。

### 3.3 返件、验收和 SYSTEM

- 会员首次提交返件只原子保存/占用 `SUBMITTED` 返件记录并追加
  `START_RETURN: APPROVED -> RETURN_PENDING`。会员不能追加 `RETURN_SHIPPED` 或声明
  `IN_TRANSIT/DELIVERED`；后续运输/签收必须来自可信物流查询或受审管理员核验事实。
- 完整 `inspect-return` 写路由和 exactly-once 库存恢复整体延至 M6.4。B0/B1-B5 只保留数据基础、
  返件/待验收读取及可信物流事实，不因 inspection 表已存在而开放写路径。
- SYSTEM 事件只允许 `RETURN_EXPIRED`、`REFUND_SUCCEEDED`、`REFUND_FAILED`、
  `REFUND_CANCELLED`、`REQUIRE_REVIEW` 和 `COMPLETE`；审核、legacy 决定、COD 确认、
  `REFUND_REQUESTED` 和其他人工动作禁止。
- `COMPLETE` 只允许在不产生新资金、库存或物流副作用时做 `REFUNDED -> COMPLETED` 的确定性收口。

### 3.4 读取与公共 HTTP 契约

- 会员 locale：认证会员 `preferredLocale -> vi`；管理员 locale：显式 locale、商城默认、`vi`。
- `c1_` 游标使用独立可轮换 HMAC key，绑定版本、商城、主体、资源、过滤、排序/tie-breaker 和过期
  时间；篡改、过期或跨 scope 稳定 `400`，解码后仍显式限定当前商城/主体。
- 售后公开号为至少 128-bit 服务端随机的 `^ASC-[A-Z0-9]{16,32}$`。legacy 响应中的
  `reason_detail` 可为 null；所有新申请仍要求非空详情。
- 60 秒窗口限流：会员读 60、会员写 10、管理员读 120、管理员写 30，均绑定 `store_id + actor_id`；
  `429` 不泄露账户或跨商城资源存在性。
- 同一安全 correlation ID 贯穿 HTTP header/error body、事务、transition、audit 和日志。稳定公开错误
  为 `400/401/403/404/409/429/503`；`409` 详情只暴露已冻结 after-sale code allowlist。

## 6. 风险、兼容和下一步

- 管理员读取 query/OpenAPI 的 `locale` 已保持 optional，缺省时不会吞掉商城默认语言层级；契约回归
  已覆盖缺省参数与显式 `zh`。B1 仍需实现并验证“显式 locale → 商城默认 → `vi`”运行时 resolver。
- B0 前向迁移会对已有非 legacy 售后执行 fail-closed policy identity 证明；无法证明的环境不能靠跳过
  guard 上线，必须先做审计和独立向前修复。生产禁止执行 `down.sql`。
- `REFUND_FAILED/REFUND_CANCELLED` 当前数据库 guard 只要求同一售后单存在历史 FAILED/CANCELLED
  settlement。B6 启用协调器前必须把事件绑定到具体 settlement/outbox 版本，避免旧退款尝试错误证明当前结果。
- legacy 多行同政策 guard 在售后行写入时执行；异常流程若在售后事实之后补插订单行 policy snapshot，
  当前没有反向 trigger。正常业务顺序不会触发，但 B3 开放申请写路径前应补反向门禁。
- SYSTEM 纯领域 context 当前只校验 scope、actor、store 与 correlation 非空；未来 worker 在进入数据库前
  还应校验 UUID 与 correlation 长度/字符集，避免把 `22P02/22001` 暴露成内部错误。
- M6.3-A 的全部商城默认 OFF、生产政策/外部调用限制保持不变；M5.5-M5.7、M5 和 P0 的供应商与
  Zalo 宿主外部门禁也未改变。
- M6.3-A 结转的 3 项 React Router moderate 公告仍存在；B0 最终依赖审计必须报告实际链路和处置，
  不能描述为“零漏洞”。
- B0 已完成，但 M6.3、M6 与 P0 仍未完成。下一切片只能是另行批准的 B1 只读运行时；B0 完成不自动
