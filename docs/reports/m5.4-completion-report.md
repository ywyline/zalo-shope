## 1. 已交付

- `ONLINE` 报价只在 `NODE_ENV=test`、`PAYMENT_PROVIDER=test` 且当前商城存在 ACTIVE TEST/SANDBOX
  渠道时开放。渠道 ID、版本和支付窗口只进入服务端 quote hash，不作为公开报价字段；客户端仍
  不能提交或修改金额、运费、库存、商城、渠道和支付状态。
- 在线订单复用 M4 的商城/会员幂等、advisory lock、`SERIALIZABLE` 有界重试和服务端最终报价。
  `PENDING_PAYMENT` 订单、库存预留、首个 `CREATED` 支付尝试、初始转换和
  `payment.create.requested.v1` outbox 在同一事务提交，订单响应不伪造供应商成功或 launch。
- worker 从商城绑定事实构造创建请求，结束数据库事务后调用确定性 test-only provider，再在新的
  短事务校验商城、订单、attempt、整数 VND 金额、过期时间和 extradata 身份。数据库只保存 launch
  与 nonce 的 SHA-256、脱敏供应商引用和转换事实，不保存测试密钥或完整 launch。
- 买家可读取本人支付详情、获取已准备的短期 launch、主动查单，并在支付窗口内以独立幂等键创建
  新尝试。同订单数据库唯一索引保证最多一个 `CREATED/PROVIDER_PENDING` 尝试；单次失败不关闭
  仍可支付的订单。
- 主动查单与未来回调复用 `applyPaymentProviderFact`。命令先按统一的订单→支付尝试锁顺序核对
  `store_id`、attempt、order、provider order、VND 金额和币种；匹配成功只消费一次库存，再追加
  `PENDING_PAYMENT -> CONFIRMED -> PENDING_FULFILLMENT` 两条订单转换。重复成功不产生第二次
  库存动作。
- 会员/管理员取消和预留过期会先终止活动支付尝试，再释放预留或关闭订单。终态尝试的迟到成功、
  金额/商城/订单/attempt 篡改、未知状态及缺少交易号进入 `REVIEW_REQUIRED`，不能复活终态订单。
  取消发生在 worker 领取前时，过时 outbox 会完成且不调用 provider。
- 确定性 provider 不访问网络，稳定生成带 HMAC 的 sandbox launch 和 provider order 身份，可注入
  pending/success/failure/cancel/unknown 与身份篡改事实；非 test 构造、短密钥和非法输入硬失败。
  供应商异常通过脱敏 503 `UPSTREAM_UNAVAILABLE` 返回，不回显上游正文。

## 2. 配置、数据与迁移

新增运行时配置如下；开发和生产默认禁用，不存在从 production 回退到测试适配器的路径：

| 配置                           | 默认值     | 约束                                                |
| ------------------------------ | ---------- | --------------------------------------------------- |
| `PAYMENT_PROVIDER`             | `disabled` | 仅允许 `disabled/test`；`test` 要求 `NODE_ENV=test` |
| `PAYMENT_TEST_PROVIDER_SECRET` | 空         | `test` provider 必填，至少 32 字符，不进入前端/日志 |

M5.4 没有新增表或迁移，继续使用当前 21 条迁移中 M5.2/M5.3 已建立的渠道、支付、订单金额复合外键、
活动尝试部分唯一索引、outbox、RLS 和最小 UPDATE 权限。测试渠道和支付事实只在 loopback、固定名称
正则保护的独立 scratch PostgreSQL 中创建；用例结束时终止专用连接并删除 scratch，没有在共享库
持久化虚构商户或支付成功事实。数据库已有业务事实时仍只允许向前修复。
